# Step 0: sample-workbook-fixture

## 읽어야 할 파일

- `CLAUDE.md` — 보안·데이터 규칙(실업무 데이터 커밋 금지, 픽스처는 반드시 익명화),
  아키텍처 규칙의 `exceljs` import 제한 문구
- `docs/TICKETS.md` — `## T2` 절 전체. 특히 **리스크·미결**의 "픽스처에 유령 행 25건과
  하이퍼링크 셀을 반드시 포함시켜야 `E1`·`E2`가 실제로 검증된다"
- `docs/PLAN.md` — `E1`(유령 행 25개) · `E2`(`cell.value` 6가지 형태) · `E3`(퍼센트 0.66) ·
  `E6~E8`(세로 병합·숨김 행·대시보드 탭) · 「A. 엑셀」 탭 5종 구조
- `scripts/smoke/RESULT.md` — `A7` 절. 시트 5개 이름과 실측 셀 수, `rowCount` 팽창 현상
- `scripts/smoke/README.md`, `.gitignore` — 픽스처 예외(`!src/lib/fixtures/*.xlsx`)가 이미 있다

## 배경

T2의 나머지 5개 step과 T3의 어댑터 3종이 **전부 이 픽스처 하나 위에서 검증된다.**
실업무 파일(`smoke-input/`)은 실명·연락처·문의자 계정이 들어 있어 커밋할 수 없다.
그래서 **구조는 실제 시트와 같고 내용만 익명인** xlsx를 만든다.

**바이너리를 손으로 만들어 커밋하지 않는다.** 리뷰어가 diff에서 내용을 볼 수 없고,
"픽스처에 무엇이 들어 있는가"가 곧 파서 테스트의 전제인데 그것이 불투명해진다.
**생성 스크립트가 픽스처의 명세이고, xlsx는 그 산출물이다.**

아래 「실제 시트 구조」는 T1 스모크와 그 후속 실측에서 확인된 사실이다. **다시 재도록
지시하지 않는다 — 그대로 쓴다.** 실업무 파일을 다시 열 필요가 없다.

### 실제 시트 구조 (실측 확인됨)

모든 팀 탭이 같은 골격을 쓴다. **헤더는 1행이 아니라 8·9행이다.**

| 행 | 내용 |
|---|---|
| r1 | 탭 간 이동 링크 행 — 짧은 문자열 몇 개 |
| r2 | 전체 폭 가로 병합 배너 (`[VAN LOGO] …`) |
| r3 | 전체 폭 가로 병합 영문 배너 |
| r4~r5 | KPI 라벨 행 + 수식 행 |
| r6 | 전체 폭 가로 병합 안내 문구 |
| r7 | (촬영·기획팀만) 기준 주차·팀 책임자·`이번 주 핵심 목표` 블록 |
| **r8** | **그룹 헤더 — 가로 병합된 단계 묶음** |
| **r9** | **하위 헤더 — 실제 컬럼명** |
| r10~ | 데이터 |

- `01_편집팀` 16컬럼(A~P) / `02_촬영·기획팀` **71컬럼(A~BS)** / `03_마케팅·관리팀` 30컬럼 /
  `99_설정` 28컬럼 / `00_통합 대시보드` 10컬럼
- `03_마케팅·관리팀`은 **한 탭에 헤더 행이 두 개**다. 섹션 순서가 A/B/C가 아니라
  **C(브리핑) → A(문의) → B(성과)** 순으로 세로로 놓여 있다.
- `99_설정`은 **컬럼 하나가 enum 그룹 하나**다. r3이 그룹명, r4부터 값이 아래로 내려간다.
- `00_통합 대시보드`는 `rowCount`가 1001인데 `dimensions`는 `A1:J60`이다. Google Sheets가
  기본 그리드를 서식만 채워 통째로 내보낸 탓이다. **이 현상을 픽스처가 재현해야
  step 2의 `workbook-reader`가 `dimensions` 기준으로 자르는지 검증할 수 있다.**

### 실제 셀 값에서 확인된 형태 — `PLAN.md` E2의 6가지가 전부가 아니다

`01_편집팀`·`02_촬영·기획팀`에서 실측으로 나온 것:

```
"문자열"                                    원시값
2026-07-20T00:00:00.000Z (Date)             날짜 (numFmt: "yyyy. mm. dd.")
{ formula: "…", result: 0.33 }              수식 + 캐시된 결과 (numFmt: "0%")
{ formula: "COUNTIFS(#REF!,…)" }            수식인데 result가 없다  ← 주의
{ sharedFormula: "C10" }                    공유 수식 슬레이브. result가 없다  ← 주의
{ text: "https://…", hyperlink: "https://…" }  하이퍼링크
{ richText: [ … ] }                          리치텍스트
{ error: "#REF!" }                           오류
"2026.07.22"                                 날짜인데 문자열로 들어온 셀
true / false                                 불리언 (체크박스 컬럼)
```

`{ sharedFormula }`와 `result` 없는 `{ formula }`는 `PLAN.md` E2 표에 없다.
**픽스처는 이 두 형태를 반드시 담는다.** (문서 반영은 step 1이 한다 — 여기서는 만들기만.)

## 작업

### 1. `CLAUDE.md`의 `exceljs` import 예외를 `scripts/`로 넓힌다

현재 문구는 예외가 `scripts/smoke/`에만 해당한다고 못 박혀 있다. 픽스처 생성 스크립트는
`scripts/fixtures/`에 놓이므로 그대로면 규칙 위반이 된다.

- 예외 범위를 **`scripts/` 아래 스크립트 전체**로 바꾼다. 근거는 동일하다 —
  제품 번들에 들어가지 않는다.
- 규칙의 본체(`src/` 제품 코드에서는 `workbook-reader.ts`·`assignment-writer.ts` 두 파일만)는
  **그대로 둔다.** 넓히는 것은 예외의 경로뿐이다.
- 이 한 줄 외에 `CLAUDE.md`의 다른 부분을 고치지 마라.

### 2. `scripts/fixtures/build-sample-workbook.mjs` 작성

Node ESM 스크립트다. TypeScript로 쓰지 마라 (실행에 빌드 단계가 생긴다).

```
node scripts/fixtures/build-sample-workbook.mjs            # 생성
node scripts/fixtures/build-sample-workbook.mjs --verify   # 생성된 파일을 다시 읽어 자체 점검
```

- 출력 경로는 `src/lib/fixtures/sample-workbook.xlsx` 고정.
- **재생성이 바이트 안정적이도록** `wb.created` · `wb.modified`를 고정 상수 날짜로 박는다
  (예: `new Date(Date.UTC(2026, 0, 1))`). 안 그러면 재생성할 때마다 무의미한 diff가 난다.
- `--verify`는 쓴 파일을 `exceljs`로 다시 읽어 **아래 「자체 점검 항목」을 전부 출력하고,
  하나라도 어긋나면 exit 1** 한다. 이 모드가 픽스처의 계약을 문서보다 강하게 고정한다.

### 3. 익명화 규칙

- 사람 이름은 `담당자1`·`기획자1`·`승인자1` 같은 **역할+번호**로 쓴다. 실명 금지.
- 업무명·프로젝트명은 `[샘플] 카드뉴스 A` 식으로 쓴다.
- 연락처·계정 값은 `010-0000-0000`·`sample_account_1` 같은 명백한 더미로 쓴다.
- **컬럼 헤더 이름은 실제 시트 그대로 쓴다.** 헤더는 개인정보가 아니고, 어댑터가
  매칭할 대상이 실제 문자열이기 때문이다. `출연자 연락처 (내부용)` 같은 민감 키 헤더도
  그대로 넣는다 — T6의 `extras` 마스킹 테스트가 이 헤더를 필요로 한다.
- enum 값(`진행 중`·`승인 대기` 등)도 **실제 값 그대로** 쓴다. 정규화의 근거다.

### 4. 탭 5개 명세

탭 이름은 실제와 동일하게 — `00_통합 대시보드` · `01_편집팀` · `02_촬영·기획팀` ·
`03_마케팅·관리팀` · `99_설정`.

r1~r7의 장식 행(네비·배너·KPI·안내 문구)은 **모든 팀 탭에 넣는다.** 이것이 있어야
step 3의 헤더 행 탐색이 실제 난이도로 검증된다. 배너는 전체 폭 가로 병합으로 만든다.

#### `01_편집팀` — 16컬럼 A~P

| r14~r15 | **세로 병합** `A14:A15` — 업무명 하나를 두 행이 공유한다. 담당자는 행마다 다르게 둔다 |

  - 25건 전부 같은 모양이어도 된다. **개수 25가 계약이다.**

#### `03_마케팅·관리팀` — 30컬럼

섹션 순서는 실제와 같이 **C → A → B**로 둔다. 행 번호는 압축해도 되지만
**섹션 사이에 빈 행 2개 이상**을 반드시 남긴다 (T3의 `section-splitter`가 그것으로 자른다).

- C 섹션: 제목 행 `C. 주간 회의 브리핑` (전체 폭 병합) + 라벨 행 `직전 주 핵심 마케팅 성과` +
  자유 텍스트 행 3~5개
- A 섹션: 제목 행 `A. 상시 문의·SNS 관리` (전체 폭 병합) + 헤더 20컬럼 + 데이터 3행
  ```
  문의 ID | 문의 접수일 | 접수 시간 | 채널 | 계정·문의자 | 문의 유형 | 문의 내용 요약 | 긴급도 | 담당자 | 답변 필요 여부
  답변 기한 | 답변 상태 | 실제 답변일 | 답변 내용 요약 | 추가 확인 필요사항 | 후속 담당자 | 후속 조치 기한 | 후속 조치 상태 | 완료 여부 | 비고
  ```
  `계정·문의자`에는 더미 계정을 넣는다 (민감 키 마스킹 대상).
- B 섹션: 제목 행 `B. 주간 마케팅 실행·성과 관리` (전체 폭 병합) + 헤더 30컬럼 + 데이터 3행

### 6. 커밋 가능 여부 확인

```bash
# 픽스처가 생겼고 git이 추적할 수 있다 (check-ignore가 아무것도 못 찾아야 하므로 exit 1)
test -f src/lib/fixtures/sample-workbook.xlsx
```

## 금지사항

- `src/lib/sheet/`에 파서를 만들지 마라. 이유: step 1~5의 범위다. 여기는 픽스처만이다.
- `src/types/sheet.ts`를 만들지 마라. 이유: 타입은 그것을 쓰는 step이 정의한다.

- 실업무 `.xlsx`를 복사하거나 그것을 읽어 변환하는 스크립트를 쓰지 마라. 이유: 익명화
  누락이 한 셀만 있어도 개인정보가 커밋된다. **처음부터 짜서 만든다.**

  먼저 `git check-ignore -v`로 확인하라.
- `git commit`을 직접 실행하지 마라. 이유: 커밋은 하네스가 확정된 제목으로 처리한다.
