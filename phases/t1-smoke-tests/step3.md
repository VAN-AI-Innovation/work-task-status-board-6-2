# Step 3: plan-reflect

## 읽어야 할 파일

먼저 아래 파일들을 읽고 프로젝트의 기획 의도를 파악하라:

- `CLAUDE.md` — **결정이 바뀌면 코드보다 `docs/PLAN.md`를 먼저 고친다**는 규칙
- `scripts/smoke/RESULT.md` — **이 step의 유일한 사실 근거다.** 여기 적힌 판정과 숫자만 쓴다
- `docs/PLAN.md` — 아래 4곳을 정확히 찾아 읽어라
  - 「가설과 검증 방법」 절의 **「해소된 가설」 표**와 **「남은 가설」 표**(`H8` 행이 여기 있다)
  - 「5. 독스 → 배정표 — `.docx` 단일 입력」 절의 **「⚠ T2 착수 전 선행 작업」** 문단
  - `#### 🟡 A7. 5MB 업로드 한도가 배포 환경과 어긋날 수 있다` 절
  - 문서 끝의 **「확인 필요 (진행하며 해소)」** 절 1·2번
- `docs/TICKETS.md` — `## T1` 절, `## T5` 절의 완료 기준 5·6, `## T7` 절의 리스크·미결
- `scripts/smoke/docx-headings.mjs` · `scripts/smoke/sheet-metrics.mjs` — 어떤 방법으로 쟀는지

## 배경

step 1·2가 실측을 끝냈다. 이 step은 **코드를 한 줄도 쓰지 않는다.** 실측 결과를 근거 문서에
옮겨 담아 `H8`·`A7`을 가설에서 확정으로 이동시키는 것이 전부다.

이게 왜 별도 step인가: `PLAN.md`는 이 프로젝트의 근거 문서이고 하네스가 매 step 프롬프트에
주입한다. 여기에 옛 가설이 남아 있으면 **T5·T7 세션이 이미 판정 난 것을 다시 가설로 취급**한다.
실측만 하고 문서를 안 고치면 T1의 값이 절반으로 준다.

## 작업

### 1. `docs/PLAN.md` — `H8` 이동

「남은 가설」 표에서 `H8` 행을 제거하고, 「해소된 가설」 표에 결과와 함께 추가하라.
그 표의 기존 형식(`| ~~H8~~ | 내용 | 결과 |`, 취소선 + ✅/❌)을 따른다.

결과 칸에 담을 것 — `RESULT.md`의 판정에 따라 갈린다:

- **PASS(기본 옵션)** — 기본 옵션에서 인식됨. `h2`/`h3` 개수. T7 예상(L) 유지
- **PASS(styleMap 필요)** — 확정된 styleMap 문자열을 **그대로 쓸 수 있게** 남긴다.
  T7의 `docx-reader.ts`가 이걸 복사해 쓴다
- **FAIL** — 문단 텍스트 패턴 매칭이 확정 경로가 됨을 명시. 번호 접두사(`N.`·`N-M.`) 매칭
  통계가 그 경로의 실현 가능성 근거이므로 함께 적는다

### 2. `docs/PLAN.md` — 「⚠ T2 착수 전 선행 작업」 문단 갱신

"스모크 테스트부터 한다. 30분이면 확인된다"는 **앞으로 할 일로 적혀 있다.** 이미 했으므로
**결과 문장으로 교체**하라. `scripts/smoke/RESULT.md`를 근거로 가리키고, styleMap이 필요했다면
그 문자열을 여기에도 남긴다 (T7 세션이 이 절을 읽는다).

### 3. `docs/PLAN.md` — `A7` 절에 실측 기록

`A7` 절의 **확정 문장(앱 한도 4MB)은 유지**하고, 그 아래에 실측 결과를 덧붙여라:

- 실제 시트 `.xlsx` 크기 (MB) 와 4MB 한도 대비 여유
- 시트 수·전체 셀 수
- 4MB를 넘었다면: **탭별 분할 업로드(UC-04)가 예외가 아니라 기본 경로**임을 명시
  (T1 완료 기준 3). 4MB 아래라면 단일 업로드가 기본 경로이고 분할은 예외임을 명시
- `S2` 한도(시트 20개·셀 20,000개) 대비 판정. 실측이 한도를 넘었다면 **정상 파일이
  오탐된다**는 사실과 상향해야 할 값을 적는다

`S2` 절(압축 폭탄 방어)에도 실측 대비 판정 한 줄을 남겨라. 숫자를 고칠 필요가 생겼다면
`PLAN.md`의 `S2`와 `docs/TICKETS.md` T5 완료 기준 6의 숫자를 **함께** 고친다.
둘 중 하나만 고치면 T5 세션이 서로 다른 한도를 본다.

### 4. `docs/PLAN.md` — 「확인 필요」 절 정리

1·2번을 해소 처리하라. 이 절의 기존 형식(3번 항목이 `~~취소선~~ → **해소.**` 형태)을 따른다.
「T2 착수 전 반드시 (30분)」이라는 소제목도 이미 끝난 일이므로 그에 맞게 고친다.
4번(노션 스프린트 날짜)은 미해소이므로 **건드리지 마라.**

### 5. `docs/TICKETS.md` — T7·T1 갱신

- `## T7` 리스크의 "mammoth의 Google Docs 스타일 인식(`H8`)이 최대 변수이며 **T1에서 이미
  판정이 나 있어야 한다.** T1이 실패로 끝났다면 이 티켓의 예상을 재산정한다" 문장을
  **실제 판정 결과로 교체**하라. 예상(L) 유지 여부를 명시적으로 적는다 (T1 리스크 항목이
  "그 판단을 여기서 내린다"고 요구한다).
- `## T1` 절 끝에 **「실측 결과」** 소절을 추가해 두 판정을 한 줄씩 요약하고
  `scripts/smoke/RESULT.md`를 가리켜라. 완료 기준을 고치지는 마라.
- 의존 그래프와 예상 시간 표에서 T7의 예상을 바꿔야 한다면 **표와 본문을 함께** 고친다.

### 6. 판정이 문서와 어긋날 때

실측이 기존 확정을 뒤집는 경우(예: 실제 시트가 4MB 초과, 셀 20,000개 초과)에는
**숫자를 조용히 맞추지 말고 무엇이 바뀌었는지 문장으로 남겨라.** `PLAN.md`는 결정 이력을
읽는 문서다. 다만 `docs/ADR.md`는 건드리지 마라 — ADR은 결정의 기록이고, 이번 건은
기존 결정의 근거 보강이지 결정 변경이 아니다.

## Acceptance Criteria

```bash
# H8이 남은 가설 표에서 사라지고 해소된 가설로 옮겨졌다
grep -n 'H8' docs/PLAN.md

# 실측 숫자가 문서에 들어갔다 (RESULT.md의 값과 일치해야 함 — 눈으로 대조)
grep -n 'A7' -A 12 docs/PLAN.md | grep -iE 'MB|셀|시트'

# 확인 필요 절의 선행 확인 2건이 해소 표시됐다
grep -n -A 12 '확인 필요' docs/PLAN.md

# 스모크 결과 문서로의 링크가 있다
grep -q 'scripts/smoke' docs/PLAN.md
grep -q 'scripts/smoke' docs/TICKETS.md

# 문서에 미해결 플레이스홀더가 남지 않았다 (T0 완료 기준 6)
grep -nE '\{[가-힣A-Za-z_]+\}' docs/PLAN.md docs/TICKETS.md ; test $? -eq 1

# 게이트
npm run lint && npm run build && npm run test
```

## 검증 절차

1. 위 AC 커맨드를 전부 실행하고, 문서에 적은 숫자를 `scripts/smoke/RESULT.md`와 **눈으로 대조**한다.
   숫자 하나라도 다르면 실측이 아니라 창작이다.
2. 체크리스트를 확인한다:
   - `src/` 아래에 파일이 생기거나 바뀌지 않았는가? (이 step은 문서만 고친다)
   - `docs/ADR.md`를 건드리지 않았는가?
   - `PLAN.md`의 다른 가설(`H3`·`H4`·`H5`·`H7`)과 다른 검증 항목(`A1`~`A6`·`A8`)을
     건드리지 않았는가?
   - `S2` 한도를 고쳤다면 `PLAN.md`와 `TICKETS.md` T5를 **함께** 고쳤는가?
   - 문서에 실명·연락처·셀 값·과제 본문이 들어가지 않았는가?
3. 결과에 따라 `phases/t1-smoke-tests/index.json`의 step 3을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "H8 판정과 A7 실측치를 어느 문서 어느 절에
     반영했는지 + T7 예상 유지/재산정 여부"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- `scripts/smoke/RESULT.md`에 없는 숫자를 문서에 적지 마라. 이유: 근거 없는 수치가
  근거 문서에 들어가면 이후 모든 티켓이 그걸 사실로 취급한다.
- 스크립트를 다시 실행해 값을 바꾸려 하지 마라. 실측은 step 1·2에서 끝났다.
  `RESULT.md`와 스크립트 출력이 어긋난다면 그것 자체를 `error`로 보고하라.
- `src/`에 코드를 쓰지 마라. 이유: T1 범위 Out — 제품 코드는 T2 이후다.
- `docs/ADR.md`에 새 ADR을 추가하지 마라. 이유: 이번 건은 기존 결정의 근거 보강이다.
- T1의 완료 기준을 실측 결과에 맞춰 고치지 마라. 이유: 기준을 결과에 맞추면 검증이 무의미해진다.
- FAIL 판정을 완곡하게 적지 마라. "인식이 다소 불안정함" 대신 "인식 실패 —
  styleMap 필요" 또는 "인식 실패 — 문단 패턴 매칭으로 대체" 로 단정해 적어라.
  이유: T7 세션이 이 문장을 읽고 구현 경로를 고른다.
- `git commit`을 직접 실행하지 마라. 이유: 커밋은 하네스가 확정된 제목으로 처리한다.
- 기존 테스트를 깨뜨리지 마라.
