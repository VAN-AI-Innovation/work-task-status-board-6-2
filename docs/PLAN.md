# 전사 업무 현황판 고도화 (6-2) 구현 계획

> 최초 작성 2026-08-13
> 이 문서는 이후 발행되는 모든 티켓(T0~T9)의 근거다. 결정이 바뀌면 티켓보다 **이 문서를 먼저** 고친다.
> 계획·규약 문서라 `main`에 직접 올린다. 실제 작업은 T0부터 이슈 → 브랜치 → PR 절차를 따른다 (`docs/TEAM_RULES.md` 2.5절).

## Context

VAN AI Innovation 학회 과제 **6-2. 전사 업무 현황판 고도화 (中上)**. 1인 개발(갠플), 웹 형식.

**해결하려는 문제**: 현재 조직의 업무 현황이 Google Sheets 한 파일에 흩어져 있다. 실제 시트(`[VAN] 26-2 컨텐츠마케팅부 업무_`)를 열어보면 팀별 탭의 컬럼 스키마가 **16 / 70 / 20개로 완전히 다르다**. 사람이 탭을 넘나들며 눈으로 취합해야 하고, 마감 임박·지연·담당자 미지정을 자동으로 알 방법이 없다.

**담당자가 준 구체적 지시가 최우선 기준이다** (과제 원문보다 우선):

> "엑셀 시트 **입력 시 업무 파악을 빠르게 조회하거나 파악**할 수 있는 기능 추가해주시면 될 것 같습니다. 그리고 **독스 파일 입력 시 저희 업무 배정표처럼 엑셀시트로 뽑을 수 있는** 기능 이렇게 추가하면 됩니다"

따라서 평가 대상 산출물은 **두 개**로 못박는다:

1. **엑셀 넣으면 → 빠르게 조회·파악** (파서 + 대시보드 + 조회 UX)
2. **독스 넣으면 → 업무 배정표 엑셀이 나옴** (아웃라인 파서 + xlsx 생성)

과제 원문의 나머지(알림·목표 대비 성과·주간 보고·권한)는 위 둘을 떠받치는 형태로만 구현한다.

**의도한 결과**: `npm run dev` 한 번으로 실제 시트를 올려 통합 대시보드가 뜨고, 독스를 올려 드롭다운이 붙은 배정표 xlsx가 떨어진다. 두 기능이 한 바퀴로 닫힌다 — 뽑은 배정표를 그대로 입력해 다시 시스템에 올릴 수 있다.

### ⚠ 명시적으로 밝히는 가정

**8/31 초안 시점에 Supabase는 붙지 않는다.** 오늘(8/13)부터 18일인데 크리티컬 패스(T0~T6)만으로 18.5일이다. Supabase 이관·인증·RLS는 9월 첫 주로 미룬다.

대신 **`TaskRepository` 인터페이스 + 메모리 드라이버**로 전 기능을 먼저 완성한다. 이건 타협이 아니라 리스크 대응이다 — 일정이 밀려도 잘라내는 것이 Supabase지 기능이 아니게 된다. 또한 Supabase 무료 티어는 7일 미접속 시 프로젝트를 일시중지하므로, 발표장에서 조용히 죽는 것을 막는 안전망이기도 하다.

이 판단이 마음에 안 들면 T5(대시보드 UI)를 축소하고 T7을 당기는 방법이 있으나, 그러면 "빠르게 조회·파악"이라는 담당자 지시 ①이 약해진다. 권장하지 않는다.

## 입력 데이터 실제 구조 (직접 확인함)

### A. 엑셀 — `[VAN] 26-2 컨텐츠마케팅부 업무_` (탭 5개)

| 탭 | 구조 |
|---|---|
| `00_통합 대시보드` | KPI 10종 + 팀별 요약표 + 확인 필요 업무 + 마감 일정 + 승인 대기함 + 주간 회의 브리핑 |
| `01_편집팀` | 16컬럼. 단계 3개(컨셉+2일 / 제작+5일 / 최종본+7일)가 **컬럼 그룹으로 펼쳐진 wide 포맷** |
| `02_촬영·기획팀` | **약 70컬럼.** 섭외·촬영준비·초안·완성본·촬영실행·편집이관 단계별 |
| `03_마케팅·관리팀` | A(문의 20컬럼) / B(주간 성과) / C(회의 브리핑) 세 섹션이 한 탭에 세로로 |
| `설정` | 팀별 구성원, 공통 enum 4종, 팀 전용 enum 다수, **기본 SLA 일수 표** |

`설정` 탭이 정규화의 근거다. `공통_진행 상태` 10단계(업무 배정→준비 중→진행 중→검토 요청→승인 대기→수정 중→게시·이관 대기→완료→보류→취소), SLA(컨셉 공유 1일 / 섭외 5일 / SNS 답변 1일 …)가 여기 있다.

### B. 독스 — `[VAN] AI혁신부 26-2 워크로드`

산문형이지만 구조가 규칙적이다. `## N. 대분류` → `### N-M. 과제명 (난이도)` → 불릿 세부항목. 난이도는 `上/中上/中/中下/下`, 일부에 `(9/1까지 완성)` 형태 마감. 뒷부분 「워크로드 공유」에 P0/P1과 ①②③④ 블록이 별도로 있다.

## 사용자 여정 (User Journey)

### 이 시스템의 위치 — 가장 중요한 전제

**이 웹은 Google Sheets를 대체하지 않는다.** 담당자가 "엑셀시트 **입력 시**"라고 규정한 순간, 데이터 입력은 여전히 시트에서 일어나고 이 웹은 그것을 **읽고 해석하는 층**이 된다.

```
 [입력 계층]  Google Sheets      ← 팀원이 평소처럼 입력. 바뀌지 않는다.
      ↓            (내보내기)
 [해석 계층]  이 웹              ← 정규화 · 판정 · 시각화 · 조회
      ↓
 [소비 계층]  대시보드 · 주간 브리핑 · 배정표 xlsx
```

- **강점**: 기존 업무 습관을 안 바꾼다. 채택률의 전부가 여기 달렸다.
- **약점**: 업로드하지 않으면 데이터가 낡는다. 이 약점은 설계로 감출 수 없으므로 **화면에 드러낸다** — 모든 페이지에 "마지막 반영: 8/29 14:20 (3일 전)"을 상시 표시하고, 5일 이상 경과하면 경고색으로 바꾼다.

### 페르소나 4종

| 역할 | 누구 | 빈도 | 목적 | 성공 기준 |
|---|---|---|---|---|
| **운영자** | AI혁신부 담당 (본인) | 주 1~2회 | 시트·독스를 올려 데이터 갱신 | 드롭 → 확정까지 3분 |
| **대표·실장** `admin` | 조직 임원 | 주 1회 (회의 직전) | 전사 현황 파악, 의사결정 필요사항 추출 | 한 화면에서 5분 안에 브리핑 완성 |
| **팀장** `lead` | 편집 / 촬영·기획 / 마케팅·관리 | 주 2~3회 | 우리 팀 병목·지연자 특정 | 지연 건과 담당자를 즉시 지목 |
| **부원** `member` | 학회원 | 주 1~2회 | 내 업무·마감 확인 | 진입 후 3초 안에 "내 마감" 확인 |

**운영자는 과제 원문에 없는 페르소나다.** 하지만 데이터가 들어오는 유일한 경로이므로 실제로는 가장 중요하다. 이 사람이 귀찮으면 시스템 전체가 죽는다.

### 주간 운영 루프

```
        ┌──────────────────────────────────────────────────┐
        │  Google Sheets  (입력은 계속 여기서)                │
        │  01_편집팀   02_촬영·기획팀   03_마케팅·관리팀       │
        └────────────────────┬─────────────────────────────┘
                             │ ① 팀원이 평소대로 입력
                             ▼
                     ┌───────────────┐
                     │  xlsx 내보내기  │
                     └───────┬───────┘
                             │ ② 운영자(또는 팀장) 업로드
                             ▼
   ┌──────────────────────────────────────────────────────┐
   │  /upload    드롭 → 파싱 → 미리보기 → 확정              │
   │             신규 N · 변경 M · 유지 K · 경고 W          │
   └────────────────────────┬─────────────────────────────┘
                             │ ③ upsert  (+ task_events 기록)
                             ▼
   ┌──────────────────────────────────────────────────────┐
   │  현황판                                               │
   │    /             통합 대시보드    ← 대표·실장           │
   │    /teams/[팀]   부서별 탭        ← 팀장·부원          │
   │    ?task=id      사이드 패널      ← 전 역할            │
   └────────────────────────┬─────────────────────────────┘
                             │ ④ 회의 직전
                             ▼
                     ┌────────────────┐
                     │  주간 브리핑 복사 │ → 회의록 · 카톡
                     └────────────────┘
```

**루프의 진입점은 ②다.** ②가 안 돌면 ③④가 전부 낡는다. 그래서 ②를 3분 안에 끝나게 만드는 것이 T4의 성공 기준이다.

### 독스 추출 루프 — 고리가 닫히는 지점

```
   [VAN] AI혁신부 워크로드 (Google Docs)
               │  .docx 내보내기
               ▼
   ┌───────────────────────────────────────┐
   │  /extract   드롭 → 아웃라인 파싱 → 미리보기 │
   │             카테고리·과제명·난이도·마감·세부 │
   └───────────────────┬───────────────────┘
                       │ 다운로드
                       ▼
   ┌───────────────────────────────────────┐
   │  배정표 xlsx                            │
   │  상태·난이도·우선순위에 드롭다운 내장       │
   └───────────────────┬───────────────────┘
                       │ 사람이 담당자·마감·진행률 채워넣음
                       ▼
   ┌───────────────────────────────────────┐
   │  /upload  재업로드                      │
   └───────────────────┬───────────────────┘
                       │
                       └──▶ 현황판에 반영  ★ 고리가 닫힌다
```

**이 고리가 데모의 클라이맥스다.** "산문 문서 → 배정표 → 현황판"이 한 번에 이어지면, 담당자가 요청한 두 기능이 실은 하나의 파이프라인이었다는 것이 드러난다. 드롭다운을 넣는 이유가 이것이다 — 드롭다운이 없으면 사람이 자유 입력해서 재업로드 시 enum 매칭이 깨진다.

### 역할별 진입 경로

```
                          로그인 (T8 이후)
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
      admin                 lead                member
         │                    │                    │
         ▼                    ▼                    ▼
  /  통합 대시보드      /teams/{내 팀}       / ?owner=나
  ─────────────       ─────────────        ─────────────
  전 팀 KPI 10종       우리 팀 태스크 표      "내 업무" 프리셋
  팀별 완료율 비교      지연 · 미지정 강조     마감 임박 배지
  승인 대기함          담당자별 그룹핑        상태·진행률 수정
  주간 브리핑 카드      다음 조치 목록        (본인 건만)
```

T8 이전(초안 시점)에는 로그인이 없으므로 **`?as=admin|lead|member` 쿼리로 역할을 전환**해 세 경로를 모두 시연한다. 이건 개발 편의가 아니라 **심사·데모용 정식 기능**이다.

### 화면 전이도

```
   ┌─────────────────────────────────────────────────────┐
   │                        /                            │
   │                  통합 대시보드                        │
   │   [KPI] [팀 요약+차트] [확인 필요] [마감] [알림] [브리핑] │
   └──┬──────────┬──────────┬──────────┬─────────────────┘
      │          │          │          │
      │          │          │          └──▶ /report   주간 보고 (T9)
      │          │          └─────────────▶ /extract  독스 → 배정표
      │          └────────────────────────▶ /upload   시트 업로드
      ▼
   /teams/[teamSlug]   부서별 탭
   [필터바] [태스크 표] ─── 행 클릭 ──▶ ?task=id  사이드 패널
      │                                    │ 공통 필드 + extras 전량
      │ 필터 조합                           │ stage 타임라인
      ▼                                    │ 최근 변경 이력
   URL 쿼리에 유지 ──▶ 링크 복사 ──▶ 공유    └── Esc / 오버레이 ▶ 닫기
```

**필터 상태를 URL에 유지하는 이유는 기술적 편의가 아니라 UC-11 때문이다** — 팀장이 "이거 봐" 하고 부원에게 링크를 던지는 행위가 실제로 가장 자주 일어난다.

### 업로드 상태 전이 (실패 경로 포함)

```
   idle
    │ 파일 드롭
    ▼
   validating ──✗ 확장자·매직넘버·5MB 초과 ──▶ rejected ──▶ idle
    │ ✓
    ▼
   parsing ──✗ 워크북 손상·탭 판별 실패 ──▶ failed (사유 표시) ──▶ idle
    │ ✓
    ▼
   previewing   신규 N · 변경 M · 유지 K · 경고 W
    │      └────── 취소 ──▶ idle   ★ 저장소 무변경
    │ 확정
    ▼
   committing ──✗ 저장 실패 ──▶ failed ──▶ previewing (재시도 가능)
    │ ✓
    ▼
   done ──▶ / 이동 + "N건 반영" 토스트 + "마지막 반영" 갱신
```

`previewing`에서 취소하면 **저장소에 아무것도 쓰이지 않는다.** 이 성질이 "잘못된 파일로 DB 오염" 시나리오(UC-02)를 막는다.

### 온보딩 여정 — 첫 5분

빈 상태(empty state)를 설계하지 않으면 심사자가 클론해서 열었을 때 백지를 본다. **첫 화면이 곧 평가다.**

```
  클론 → npm install → npm run dev
       │
       ▼
  데이터 없음?
       │
       ├─ YES ─▶ 빈 상태 화면
       │          "아직 데이터가 없습니다"
       │          [샘플 데이터 불러오기]  ← 원클릭, seed-tasks.json
       │          [시트 업로드하기]      ← /upload
       │
       └─ NO ──▶ 통합 대시보드
```

`STORAGE_DRIVER=memory`가 기본이면 **키 없이 클론 직후 바로 데이터가 있는 화면**이 뜬다. 심사자가 `.env` 설정 없이 평가할 수 있는지가 점수에 직결된다.

| 상황 | 처리 |
|---|---|
| 탭 이름이 바뀜 | 헤더 시그니처(필수 컬럼 3개 이상)로 판별. 실패 시 `unknown` → 수동 매핑 UI |

| 진행률이 빈칸 | `null` 유지. 평균에서 **제외** (0으로 치면 팀 진행률이 바닥으로 끌림) |

| 완료·취소된 과거 업무 | 유지하되 완료율 모수에서 `cancelled` 제외 |
| 두 사람이 동시 업로드 | 마지막 쓰기 승리. `uploads` 이력에 남아 추적 가능 |
| 데이터가 오래됨 | 모든 페이지에 "마지막 반영: N일 전" 상시 표시, 5일 초과 시 경고색 |

### 여정에서 도출된 설계 요구 (기존 계획에 추가)

## 설계

### 1. 데이터 모델 — 공통 컬럼 + `extras jsonb` + `task_stages`

팀별 16/70/20 컬럼을 담는 방법 중 **공통 컬럼 + JSONB + 자식 테이블**을 택한다. 팀별 전용 테이블 3개는 통합 대시보드가 3-way UNION이 되고, 완전 EAV는 집계 쿼리가 지옥이다.

핵심 성질: **매핑되지 않은 컬럼은 자동으로 `extras`로 흘러들어간다.** 이것이 70컬럼 대응의 전부다.

```
departments  · teams  · members(auth_user_id nullable)

tasks
  id, team_id, department_id
  source_key            -- 자연키. 업무ID 있으면 그것, 없으면 slug(업무명)+담당자
  title, owner_member_id, owner_name_raw, co_owner_names[]
  status                -- 설정 탭 원문 그대로 보존
  approval_status, priority, risk_status
  progress smallint     -- null 허용 (빈 셀과 0을 반드시 구분)
  assigned_at, due_at, next_action, next_action_owner, next_action_due
  delay_reason, note
  extras jsonb          -- 팀 전용 필드
  raw jsonb             -- 원본 행 통째 (감사·복원)
  last_progress_at      -- 장기 미갱신 판정 기준
  source_upload_id, source_sheet_tab, source_row_index
  UNIQUE (team_id, source_key)

task_stages   task_id, seq, stage_key, stage_label,
              planned_date, actual_date, content, confirm_status, sla_days
              -- 편집팀 3개 컬럼 그룹, 촬영팀 5개 접두사 그룹을 같은 모양으로 언피벗

task_events   task_id, upload_id, changed_fields jsonb, occurred_at
enum_options  group_key, value, sort_order, semantic
sla_rules     team_id(null=공통), stage_key, label, days
uploads       kind, filename, parse_result jsonb, status, summary
doc_extractions  upload_id, order_index, category, task_no, title,
                 difficulty, deadline_raw, deadline_date, priority, details jsonb
```

**`enum_options.semantic`이 설계의 급소.** 판정 로직이 한글 상태 문자열을 직접 알면 시트에서 이름이 바뀔 때 코드가 깨진다. 매핑층을 둔다:

```
업무 배정·준비 중 → planned      검토 요청 → review     게시·이관 대기 → pending_release
진행 중          → in_progress   승인 대기 → approval   완료 → done
수정 중          → rework        보류 → hold            취소 → cancelled
```

**「지연」은 상태값이 아니라 파생 판정이다** (`due_at < today && semantic ∉ {done, cancelled}`), 여기에 시트의 `리스크 상태 = 지연`을 OR로 합친다. 이 구분을 흐리면 완료율이 틀린다.

### 2. 디렉토리 구조 — TDD 가드를 역이용

`.claude/hooks/tdd-guard.sh`는 `src/lib/`·`src/services/`에서만 테스트를 강제하고, `src/components/`·`app/**/page.tsx`·`src/types/`는 무검사 통과한다. 이 성질을 그대로 이용한다: **판단이 들어가는 코드는 전부 `src/lib/`, 컴포넌트는 props 받아 JSX만 뱉는다.**

```

├── app/
│   ├── page.tsx                      # 통합 대시보드
│   ├── teams/[teamSlug]/page.tsx     # 부서별 탭

│   ├── extract/page.tsx              # 독스 → 배정표

├── lib/

│   │            section-splitter · cell-normalizer
│   │            adapter-edit-team · adapter-shoot-team
│   │            adapter-marketing-team · adapter-settings-tab · sheet-pipeline

**⚠ TDD 가드 함정 2개** — 파일명 규칙에 반영했다:

- 가드는 **basename만 보고** `src/__tests__/{basename}.test.ts`까지 탐색한다. `lib/domain/status.ts`와 `lib/sheet/status.ts`가 동시에 있으면 테스트 파일 하나로 둘 다 통과해버린다. → **모든 lib 파일명을 전역 유니크하게** 지었다 (`task-semantic.ts`, `assignment-mapper.ts` 식). 미관이 아니라 가드 무력화 방지다.
- `*.config.*`는 무조건 통과다. `store-factory.config.ts` 같은 이름으로 우회하지 않는다.

### 3. 라이브러리 — ExcelJS 단독

| 후보 | 판단 |
|---|---|
| SheetJS(`xlsx`) | npm 레지스트리판 0.18.5에 프로토타입 오염 CVE. 최신은 자체 CDN 배포라 CI가 번거롭다 |
| **ExcelJS** | `cell.isMerged`/`cell.master`로 병합셀 명시적 처리. **데이터 검증 드롭다운** 생성 가능 |

**ExcelJS 단독 채택.** (a) 독스→배정표에서 드롭다운이 붙은 xlsx를 만들어야 하는데 — 배정표는 사람이 이어서 입력할 파일이므로 이게 실질 가치다 — SheetJS로는 어렵다. (b) 읽기·쓰기를 하나로 통일하면 의존성·학습 비용이 절반이다. ADR에 기록.

추가: `mammoth`(docx), `zod`, `chart.js` + `react-chartjs-2`.

### 4. 엑셀 파싱 파이프라인

```
업로드(5MB 제한, 확장자+매직넘버 검증)
  ↓ workbook-reader     시트별 cells[][] + merges[]
  ↓ header-resolver     병합셀 forward-fill → 2단 헤더를 "컨셉·레퍼런스 / 예정일" 경로로 결합
  ↓ tab-detector        탭 이름 정규식 + 헤더 시그니처(필수 컬럼 3개 이상 일치) 이중 판별
  ↓ [설정 탭 먼저]       enum/SLA 레지스트리 확보
  ↓ section-splitter    마케팅 탭 A/B/C 분할 (빈 행 2개 이상 + "A." 헤더 패턴)
  ↓ 팀별 어댑터          선언적 FIELD_MAP + STAGE_GROUPS
  ↓ zod 검증            실패는 warnings[]에 담고 값은 보존 (하드 실패 금지)
  ↓ 미리보기 반환        { 신규 N / 변경 M / 유지 K / 경고 }
  ↓ [사용자 확정] → upsert ON CONFLICT (team_id, source_key)
```

**어댑터는 선언적 맵으로 쓴다.** 절차적 if문으로 70컬럼을 처리하면 유지 불가능하다.

```
FIELD_MAP    : 헤더 패턴 → 공통 필드 (매칭 실패 컬럼은 자동으로 extras)
STAGE_GROUPS : { key:'concept', label:'컨셉·레퍼런스', slaDays:2,
                 cols:{ planned:'예정일', actual:'실제', content:'내용', confirm:'확인' } }
```

편집팀 3개 그룹과 촬영팀 5개 접두사 그룹이 **동일한 언피벗 함수 하나**로 `task_stages`가 된다. 어댑터 3개가 공유하는 코드가 이 함수다.

**미리보기→확정 2단계**를 쓰는 이유: 즉시 반영은 단순하지만 잘못된 파일 하나로 DB가 오염되고 되돌리기 어렵다. 파싱 결과를 `uploads.parse_result`에 넣고 확정 시 그것을 소스로 upsert하면 서버 세션 상태 없이 2단계가 된다.

**자연키 불안정 위험**: 업무ID 없는 탭은 `slug(업무명)+담당자`가 키라 오타 한 번에 중복 행이 생긴다. 완화는 자동화가 아니라 **미리보기의 "신규 N건" 숫자** — 예상보다 크면 사람이 알아챈다.

### 5. 독스 → 배정표 — `.docx` 단일 입력

**제품이 받는 입력은 `.docx` 하나다** (사용자 확정). Google Docs에서 내보낸 파일을 그대로 올린다.

- `.docx` → mammoth(`convertToHtml` + styleMap) → `node-html-parser` 순회 → `OutlineNode[]`

`markdown-reader.ts`는 **테스트 픽스처 전용으로만 남긴다.** 제품 경로가 아니다. 이유는 두 가지다:

1. **`.docx`는 바이너리라 픽스처로 최악이다.** git diff가 안 되고 테스트가 뭘 검증하는지 읽을 수 없다. `.md` 픽스처로 아웃라인 로직을 검증하고, `.docx`는 리더 계층만 스모크 테스트한다.
2. mammoth 파싱이 흔들릴 때(H8) 이미 만들어둔 탈출구가 된다. 추가 비용은 파일 하나다.

경계: `docx-reader.ts`와 `markdown-reader.ts`가 **같은 `OutlineNode[]`를 뱉고**, 그 아래(`outline-builder` → `assignment-mapper`)는 입력 형식을 모른다.

**⚠ T1 착수 전 선행 작업**: 실제 Google Docs를 `.docx`로 내보내 mammoth가 `### 6-2. …` 같은 heading을 `h3`으로 인식하는지 **스모크 테스트부터 한다.** Google Docs 내보내기의 스타일 이름은 표준이 아닐 수 있어, 여기서 막히면 T6 전체가 밀린다. 30분이면 확인된다.

**미리 박아두는 주의점 3개:**

- **난이도 정규식 순서**: `上|中上|中|中下|下` 그대로 쓰면 `中上`이 `中`에 먼저 걸린다. **긴 것부터 정렬** (`中上|中下|上|中|下`). 실제로 나는 버그다.
- **연도 추론**: `9/1`에 연도가 없다. 하드코딩 금지 — `baseYear`를 파라미터로 주입, UI에서 기본값 제공. 실패 시 `deadline_raw`만 보존하고 `deadline_date`는 null.
- **「워크로드 공유」 섹션**: P0/P1과 ①②③④가 별도 블록이므로 `workload-parser.ts`로 분리 파싱 후 과제 번호로 조인해 `priority`를 채운다. 조인 실패는 무시.

**생성물은 사람이 이어서 입력할 파일이어야 한다:**

```
카테고리 | 번호 | 과제명 | 난이도 | 마감 | 우선순위 | 세부항목 | 담당자 | 상태 | 진행률 | 비고
                                                            ↑빈칸   ↑드롭다운 ↑% 서식
```

1행 틀고정, 열너비, 헤더 굵게. `상태`·`난이도`·`우선순위`에 **데이터 검증 드롭다운** — 값은 `설정` 탭에서 읽은 `enum_options` 재사용. **이러면 뽑은 배정표를 그대로 입력해 다시 시스템에 올릴 수 있다.** 두 기능이 한 바퀴로 닫힌다. 데모의 클라이맥스다.

**왕복 테스트**: `sample-workload.md` → rows → xlsx 버퍼 → 시트 파서로 다시 읽기 → rows 동일. 두 파이프라인을 한 번에 검증하는 가장 가치 있는 통합 테스트.

**LLM은 옵션.** `ENABLE_LLM=false`가 기본. 키가 없으면 보조 필드만 빈칸이고 나머지는 그대로 동작한다. 이 경계를 넘지 않는다.

### 6. 집계·판정 — `src/lib/domain/` 순수 함수

**`now`는 반드시 인자로 주입한다** (`Date.now()` 직접 호출 금지 — 테스트가 날짜에 따라 깨진다).

```
toSemantic(statusRaw, registry)              → semantic
deriveTaskFlags(task, ctx)                   → { isOverdue, isDueSoon, dday, isStale, hasNoOwner }
summarizeTeam(tasks, ctx)                    → { total, active, done, overdue, completionRate, delayRate, ... }
buildKpiStrip(tasks, ctx)                    → KPI 10종
collectAlerts(tasks, stages, ctx)            → Alert[]
buildWeeklyReport(tasks, events, ctx)        → 마크다운
```

판정 규칙 중 **틀리기 쉬운 것들** — 테스트를 명시적으로 쓴다:

- **완료율** = `done / (전체 − cancelled)`. 취소 건을 모수에 넣으면 완료율이 영구히 100%에 못 미친다.
- **평균 진행률**: `progress`가 null인 행은 **제외**. 0으로 취급하면 미입력 많은 팀의 진행률이 바닥으로 끌려간다.
- **마감 임박**: 기본 D-3, 해당 단계에 SLA 규칙이 있으면 그 값(SNS 문의 1차 답변 1일 → D-1).
- **장기 미갱신**: `today − last_progress_at > 7일` && semantic이 진행형. `last_progress_at`은 **실제로 값이 바뀐 경우에만** 갱신한다 — 같은 파일 재업로드로 갱신되면 판정이 무의미해진다. 이래서 `task_events`가 필요하다.
- **담당자 미지정**: 빈값/`미정`/`TBD`/`-`. 추가로 **레지스트리 팀원 목록에 없는 이름**은 `unknown_owner` 경고로 분류(오타 잡기).
- **D-DAY**: 날짜 문자열(`YYYY-MM-DD`) 비교로만 계산. `Date` 객체 뺄셈은 UTC 오프셋 때문에 KST에서 하루가 어긋난다.

### 7. 화면

**통합 대시보드 `/`** — 시트의 `00_통합 대시보드` 탭을 **1:1로 옮긴다.** 담당자가 만든 레이아웃과 대응시키는 것이 "우리 시트를 이해했다"는 가장 강한 신호다.

팀별 요약 테이블 + 도넛/바  ← 시트 팀별 요약표
이번 주 확인 필요 업무      ← 시트 동명 섹션 (D-DAY, 다음 조치 포함)
이번 주 마감 일정 · 승인 대기함
알림 패널                 ← 마감 임박 / 장기 미갱신 / 담당자 미지정
```

**부서별 탭 `/teams/[teamSlug]`** — "각 부서마다 new tabs" 요구를 라우트로 충족. **70컬럼을 표에 뿌리지 않는다.** 표는 공통 8~10컬럼, 팀 전용 필드는 사이드 패널 "상세"에서 `extras`를 라벨-값으로 나열. 이 결정이 촬영팀 탭을 쓸 수 있게 만든다.

**빠른 조회 UX** (과제 원문엔 없지만 담당자 지시의 본체) — 필터 바(팀/상태 칩/담당자/마감 범위/지연만/검색), **필터 상태를 URL 쿼리에 유지**(링크 공유 + 서버 컴포넌트와 맞물림), 마감 임박순 기본 정렬, 담당자별·상태별 그룹핑 토글.

**시각화** — Chart.js(도넛=팀별 상태 분포, 가로 바=팀별 완료율). Overdue는 행 좌측 3px 붉은 보더 + 배지. `docs/UI_GUIDE.md` 안티패턴 준수: **글로우 애니메이션·gradient-text·보라/인디고·backdrop-filter blur 금지.** 사이드 패널은 `translate-x` 200ms + Esc 닫기. 리프레시는 `router.refresh()` + `isPending` 스켈레톤 + "마지막 갱신 HH:mm".

### 발견한 문제 8건

#### 🔴 A1. 집계를 SQL로 할지 앱에서 할지가 모순돼 있다

6장은 `summarizeTeam(tasks[], ctx)`를 **순수 함수**로 두는데, 예시 이슈 BE4는 "집계 쿼리 로직"이고 Supabase 선택지 설명에도 "집계 SQL"이 있었다. T7에서 SQL 집계를 짜면 **메모리 구현과 결과가 갈라지고 "같은 계약 테스트 통과"가 깨진다.**

**확정**: 집계는 **전부 `src/lib/domain/`의 JS 순수 함수**로 한다. 리포지토리는 CRUD와 필터링된 조회만 담당한다.

```
TaskRepository        (저장/조회만)          domain/           (판정/집계만)
  listTasks(filter)   → Task[]        →      summarizeTeam(tasks, ctx)
  getTask(id)         → Task          →      buildKpiStrip(tasks, ctx)
  upsertTasks(tasks)                  →      collectAlerts(tasks, ctx)
  listStages(taskIds) → Stage[]
```

근거: 조직 전체 업무가 **수백~수천 행 규모**다. 이 크기에서 SQL 집계의 이점은 없고, 두 구현의 결과 일치를 보장하는 값이 훨씬 크다. 행이 수만을 넘어가면 재검토한다 — 그 시점은 이 과제 범위 밖이다.

#### 🔴 A2. Supabase→메모리 자동 폴백이 쓰기를 삼킨다

9장의 자동 폴백은 조회에는 안전하지만, T8의 `PATCH /api/tasks/[id]`(부원이 본인 상태 수정)가 폴백 중에 들어오면 **메모리에 쓰이고 재시작 시 소실된다.** 사용자는 저장됐다고 믿는다. 조용한 데이터 유실이다.

**확정**: 폴백은 **읽기 전용**이다.
- 폴백 상태에서 모든 쓰기 경로(업로드 확정, PATCH)는 `503 + "읽기 전용 모드입니다"`를 반환하고 UI는 편집 버튼을 비활성화한다.
- 배너 문구도 "데모 데이터 모드"가 아니라 **"읽기 전용 — 저장소 연결 실패"**로 구분한다. 의도된 데모 모드(`STORAGE_DRIVER=memory`)와 사고를 섞으면 안 된다.

#### 🔴 A3. 서버 컴포넌트 / API 라우트 경계가 정의돼 있지 않고, CLAUDE.md CRITICAL 규칙과 충돌한다

계획엔 API 9종과 서버 컴포넌트 페이지가 둘 다 있는데 **누가 무엇을 쓰는지가 없다.** 서버 컴포넌트에서 자기 API를 `fetch`하면 불필요한 HTTP 왕복이 생긴다(Next.js 흔한 안티패턴).

게다가 `CLAUDE.md`의 CRITICAL 규칙 **"모든 API 로직은 `src/app/api/` 라우트 핸들러에서만 처리할 것"**을 문자 그대로 지키면 서버 컴포넌트가 `lib/store`를 직접 못 읽는다. 규칙과 설계가 충돌한다.

**확정 — 경계 규칙:**

```
서버 컴포넌트 (page.tsx)  ──직접──▶  lib/store · lib/domain     ← HTTP 왕복 없음
                                          │
클라이언트 컴포넌트         ──HTTP──▶  app/api/**  ──▶  lib/…
(업로드·PATCH·리프레시·필터)
```

- 초기 렌더 데이터는 서버 컴포넌트가 `lib/`를 **직접 호출**한다.
- API 라우트는 **클라이언트에서 발생하는 상호작용**(파일 업로드, 상태 수정, 외부 소비)만 담당한다.
- `T0`에서 CLAUDE.md·AGENTS.md의 해당 CRITICAL 규칙을 다음으로 교체한다:
  > CRITICAL: 비즈니스 로직은 `src/lib/`에만 둔다. 라우트 핸들러와 서버 컴포넌트는 `src/lib/`를 호출만 하고 계산하지 않는다. 서버 컴포넌트는 자기 API 라우트를 fetch하지 않는다.

#### 🟡 A4. ExcelJS가 20개월째 정체돼 있다

확인 결과: **`exceljs@4.4.0`, 최종 수정 2024-12-20** (오늘 기준 약 20개월). 의존성 9개 — `unzipper@0.10`, `uuid@8`, `archiver@5`, `saxes@5`, `jszip`, `fast-csv` 등 오래된 트리다. `4.4.1-prerelease.0`이 있으나 정식 릴리스는 없다.

대안도 확인했다:
- `xlsx`(SheetJS) npm 레지스트리판은 **여전히 0.18.5** — 프로토타입 오염 CVE 버전 그대로다. 최신은 자체 CDN 배포.
- `write-excel-file@4.1.1`(2026-06)은 활발하지만 **쓰기 전용**이고, `xlsx-populate@1.21.0`(2025-09)도 병합셀 읽기·데이터 검증 조합이 불확실하다.

**판단: ExcelJS를 유지한다.** 병합셀 읽기 + 데이터 검증 드롭다운 쓰기를 한 라이브러리로 하는 대안이 없고, 이 프로젝트에서 xlsx는 **신뢰된 내부 파일**만 다룬다(임의 사용자 업로드 아님).

**단, 교체 비용을 2파일로 묶는다** — 이건 이미 설계에 있던 성질을 의도적으로 못박는 것이다:
- 읽기는 `src/lib/sheet/workbook-reader.ts` **한 곳에서만** ExcelJS를 import
- 쓰기는 `src/lib/xlsx/assignment-writer.ts` **한 곳에서만**
- 나머지 코드는 `{ sheetName, cells[][], merges[] }` 같은 자체 타입만 안다
- 버전을 정확히 고정(`4.4.0`, `^` 없이)하고 ADR에 정체 사실과 교체 경로를 기록

`next.config.ts`에 `serverExternalPackages: ['exceljs']`를 넣어 번들링 문제를 피한다.

#### 🟡 A5. zod가 전이 의존성이라 언제든 사라질 수 있다

`zod@4.4.3`이 `node_modules`에 있지만 **`package.json`에는 없다.** 다른 패키지가 끌고 온 것이라, 그 패키지가 버전을 올리거나 zod를 떼면 빌드가 깨진다.

**확정**: `npm i zod`로 직접 의존성에 명시한다. 추가로 **zod v4는 v3와 API가 다르다**(`z.string().email()` → `z.email()` 등). 예제나 기억에 의존하지 말고 v4 문법으로 쓴다.

#### 🟡 A6. Vitest가 `@/*` 경로를 못 푼다

`tsconfig.json`에 `@/*` → `./src/*`가 있지만 **Vitest는 tsconfig paths를 자동으로 읽지 않는다.** 첫 테스트에서 바로 `Cannot find module '@/lib/...'`이 난다.

**확정**: `vitest.config.ts`에 `vite-tsconfig-paths` 플러그인을 넣거나 `resolve.alias`를 직접 지정한다. **T0의 완료 기준에 "`@/` import를 쓴 테스트가 통과한다"를 추가**해 이걸 조기에 잡는다.

#### 🟡 A7. 5MB 업로드 한도가 배포 환경과 어긋날 수 있다

Next.js 공식 문서 확인 결과: **Route Handler는 프레임워크 차원의 본문 크기 제한이 없다.** `bodySizeLimit`은 Server Actions 전용이고, Route Handler에서 `request.formData()`는 제한을 우회한다. 즉 **5MB 제한은 우리가 직접 구현해야 한다** (계획대로 맞다).

문제는 배포처다. Vercel 서버리스 함수는 요청 본문에 자체 한도(4.5MB로 알려짐)가 있어 **5MB 파일이 라우트에 닿기도 전에 잘릴 수 있다.**

**확정**: 앱 한도를 **4MB로 낮춘다**(플랫폼 한도보다 확실히 아래). 실제 시트가 4MB를 넘으면 탭별 분할 업로드(이미 지원하는 UC-04)로 유도한다. 배포 시 실측으로 재확인한다.

#### 🟢 A8. 자잘한 것

- `docs/ARCHITECTURE.md`가 `src/services/`를 규정하는데 계획은 쓰지 않는다. Supabase 클라이언트 래퍼를 여기 두거나, ARCHITECTURE.md에서 제거해 일치시킨다 (T0).
- `uploads.parse_result jsonb`에 70컬럼 × N행 파싱 결과를 통째로 넣는다. 이 규모면 Postgres TOAST로 감당되지만, 메모리 드라이버에선 RAM에 상주한다. **확정 후 `parse_result`를 비우고 `summary`만 남긴다.**
- `src/app/api/**`는 Node 런타임이어야 한다(ExcelJS·mammoth가 Node 내장 모듈 사용). Route Handler 기본값이 Node지만 명시적으로 `export const runtime = 'nodejs'`를 둔다.

### 검증 결론

**스택 셋업은 문제없고, 아키텍처의 뼈대(계층 분리·리포지토리 추상화·어댑터 격리)도 방향이 맞다.** 다만 **인터페이스 경계 3곳이 모호했다** — 집계의 소재지(A1), 폴백의 쓰기 정책(A2), 서버/클라이언트 데이터 경로(A3). 셋 다 지금 못박지 않으면 T7·T8에서 되돌리기 비싼 결정이 된다. 위에서 확정했다.

나머지 5건은 착수 전 설정으로 해소되며 대부분 T0에 흡수된다.

## 엣지·에러·보안 검증

### 🔴 E1. 실제 시트에 "유령 행" 25개가 있다 — 확인된 사실

`02_촬영·기획팀` 탭의 빈 행 25개를 실제로 열어보니, **업무ID·프로젝트명은 비어 있는데 수식이 만든 값이 25개 컬럼에 들어차 있다.**

```
| (업무ID 빈칸) | (프로젝트명 빈칸) | … | FALSE | FALSE | FALSE | … |
  1900. 01. 01. | … | 1899. 12. 31. | … | 0% | … | FALSE | FALSE |
```

- `1900. 01. 01.` / `1899. 12. 31.` — 빈 셀에 걸린 날짜 수식이 엑셀 시리얼 0·1로 떨어진 것 (각 25회 등장)
- `FALSE` — 불리언 수식 결과
- `0%` — 진행률 수식 결과

**"셀에 값이 있으면 데이터 행"이라는 흔한 판정을 쓰면 유령 태스크 25건이 생긴다.** 그러면 전체 활성 업무가 1이 아니라 26이 되고, 완료율이 바닥으로 떨어지고, **1900년 기한의 "지연" 업무 25건**이 대시보드를 덮는다. 대시보드가 통째로 무의미해진다.

**확정 — 행 판정은 신원 컬럼으로만 한다:**

```
isDataRow(row) = 신원 컬럼(업무명·프로젝트명 / 담당자) 중 하나 이상에 실제 값이 있다
                 ※ 수식 결과 컬럼은 판정에 쓰지 않는다
```

추가로 `cell-normalizer`가 **1900-01-01 이전 날짜를 전부 null로** 떨어뜨린다 (엑셀 시리얼 0/1 아티팩트). T2 완료 기준에 "픽스처의 유령 행 25건이 태스크로 생성되지 않는다"를 넣는다.

### E2. ExcelJS `cell.value`는 최소 6가지 모양으로 온다

`00_통합 대시보드` 탭은 KPI가 전부 **수식**이고, `01_편집팀`에는 Google Docs·Canva **하이퍼링크** 셀이 있다. 원시값만 기대하면 `[object Object]`가 그대로 저장된다.

| 셀 종류 | `cell.value` 형태 | 처리 |
|---|---|---|
| 숫자·문자열 | 원시값 | 그대로 |
| 날짜 | `Date` | KST 기준 `YYYY-MM-DD` |
| **수식** | `{ formula, result }` | **`result`를 쓴다** |
| **하이퍼링크** | `{ text, hyperlink }` | `text`는 값, `hyperlink`는 별도 필드 |
| 리치텍스트 | `{ richText: [...] }` | 조각을 이어붙임 |
| 오류 | `{ error: '#REF!' }` | null + warning |

`cell-normalizer.ts`가 이 6가지를 **전부** 처리하고, 각각 테스트를 쓴다. 미처리 형태가 오면 `warnings`에 기록하고 null로 떨어뜨린다 — 절대 `String(value)`로 뭉개지 않는다.

### E3. 퍼센트는 0.66으로 저장된다

엑셀에서 `66%`는 셀 값이 **`0.66`**이다. 그대로 `progress`에 넣으면 전 조직 진행률이 1% 미만으로 표시된다. 서식이 percent면 ×100, 이미 정수(0~100)면 그대로 — **두 경우를 서식으로 구분**하고 양쪽 테스트를 쓴다.

### E4. KST 날짜 계산

서버가 UTC로 돌면 `new Date().toISOString().slice(0,10)`은 **KST 00:00~09:00 구간에서 하루 전 날짜**를 준다. D-DAY·마감 임박·지연 판정이 전부 하루씩 어긋난다.

**확정**: `today`는 `Asia/Seoul` 기준으로 산출하는 함수 하나(`lib/domain/kst-today.ts`)를 두고, 모든 도메인 함수는 이 값을 **인자로 주입**받는다. 도메인 함수 안에서 시간을 읽지 않는다.

### E5. `source_key` 충돌은 조용히 덮어쓴다

업무ID가 없는 탭은 `slug(업무명)+담당자`가 키다. 같은 팀에 동명 업무가 두 건이면 **한 건이 다른 건을 덮어쓰고 아무도 모른다.** 미리보기의 "신규 N건"은 오히려 *줄어들어서* 감지가 더 어렵다.

**확정**: 파싱 단계에서 키 중복을 직접 검출해 **"중복 키 N건"을 경고로 따로 표시**한다. 자동 병합하지 않고 사람에게 보여준다.

### E6~E8. 나머지 엣지

| 상황 | 처리 |
|---|---|
| **세로 병합 셀** | 헤더뿐 아니라 데이터 행에도 세로 병합이 있을 수 있다. `cell.master`로 원본 셀을 따라가 값을 채운다 |
| **숨김 행·열** | 숨김 행은 **건너뛴다**(작업용 임시 행일 가능성). 숨김 열은 읽되 warning |
| **`00_통합 대시보드` 탭** | 수식 결과라 **읽지 않는다.** 우리가 원시 데이터에서 다시 계산한다. 단 배포 후 **대조 검증용**으로만 파싱해 우리 계산과 불일치하면 경고 — 이게 파서 정확성의 실측 지표가 된다 |

### 보안

#### 🔴 S1. 수식 주입 — 우리가 만든 xlsx가 무기가 될 수 있다

**이게 가장 위험하다.** `/extract`가 만든 배정표 xlsx는 **조직 사람들에게 배포되는 파일**이다. 독스 본문의 값이 그대로 셀에 들어가는데, `=`·`+`·`-`·`@`·탭·개행으로 시작하는 문자열은 엑셀이 **수식으로 해석**한다. `=cmd|'/c calc'!A1` 같은 값이 문서에 있으면 받는 사람 PC에서 실행된다.

**확정 — 양방향 처리:**
- **쓰기**: 모든 문자열 셀을 명시적으로 텍스트 타입으로 넣고, 위험 문자로 시작하면 `'` 프리픽스를 붙인다. `assignment-writer.ts` 한 곳에서 강제한다.
- **읽기**: 수식 셀은 `result`만 쓰고 `formula` 문자열은 **저장하지도, 화면에 렌더하지도 않는다.**

#### 🔴 S2. 압축 폭탄 (zip bomb)

`.xlsx`와 `.docx`는 둘 다 ZIP이다. **수십 KB 파일이 수 GB로 팽창**할 수 있고, 서버가 OOM으로 죽는다. 4MB 업로드 제한은 **압축된 크기**만 막을 뿐 이걸 못 막는다.

**확정 — 3중 상한:**
```
압축 해제 총량   ≤ 50MB      (초과 시 즉시 중단)
시트 수          ≤ 20
행 × 열          ≤ 20,000 셀/시트
파싱 타임아웃     8초         (Vercel 함수 타임아웃보다 짧게)
```
초과 시 파싱을 **중단하고 명확한 에러**를 낸다. 부분 결과를 저장하지 않는다.

#### 🟡 S3. 매직넘버만으로는 xlsx와 docx를 구분 못 한다

계획의 "매직넘버 검증"은 불충분하다. **둘 다 `PK\x03\x04`(ZIP)로 시작**한다. `.docx`를 `/upload`에, `.xlsx`를 `/extract`에 넣으면 매직넘버 검사를 통과하고 파서가 예상 못 한 지점에서 터진다.

**확정**: ZIP 내부 엔트리로 판별한다 — `xl/workbook.xml`이 있으면 xlsx, `word/document.xml`이 있으면 docx. 확장자·MIME·매직넘버는 **1차 필터일 뿐** 최종 판별은 내부 구조로 한다.

#### 🔴 S4. `?as=` 역할 전환이 프로덕션에 나가면 인증 우회다

T5에서 넣기로 한 `?as=admin`은 **URL만 치면 관리자가 되는 기능**이다. T8에서 인증을 붙인 뒤에도 남아 있으면 완전한 권한 우회다.

**확정 — 이중 차단:**
```
if (process.env.NODE_ENV === 'production' && driver !== 'memory') → ?as= 무시
```
즉 **메모리 드라이버에서만** 동작한다. Supabase에 붙는 순간 자동으로 죽는다. T8 완료 기준에 "프로덕션 빌드 + Supabase 연결 상태에서 `?as=admin`이 무시된다"를 명시한다.

#### 🟡 S5. 키 관리와 RLS 함정 두 가지

- **`service_role` 키에 `NEXT_PUBLIC_` 접두사를 붙이면 브라우저에 그대로 노출된다.** 이건 실제로 가장 흔한 Supabase 사고다. → ESLint 규칙 또는 CI 스크립트로 `NEXT_PUBLIC_.*SERVICE_ROLE` 패턴을 **빌드 실패**로 막는다.
- **`security definer` 함수는 `search_path`를 고정하지 않으면 권한 상승 경로가 된다.** A2에서 정한 `my_role()`·`my_team()`에 반드시 `set search_path = ''`를 붙이고 스키마를 명시적으로 적는다.

#### 🟡 S6. `raw`·`parse_result`에 개인정보가 통째로 들어간다

시트에는 **실명, 출연자 연락처(내부용), 문의자 SNS 계정**이 있다. 설계상 `tasks.raw jsonb`가 원본 행을 통째로 보관하고 `uploads.parse_result`도 마찬가지다. `tasks` SELECT 권한이 전원에게 열려 있으므로(A1) **부원 누구나 API로 연락처를 긁을 수 있다.**

**확정:**
- `GET /api/tasks`는 **`raw`를 절대 직렬화하지 않는다.** 응답 스키마에서 제외 (zod로 강제).
- `extras` 중 민감 키(`연락처`, `계정`, `이메일`, `전화`)는 **admin·lead에게만** 내려보낸다. 키 이름 패턴 기반 마스킹 목록을 `lib/domain/`에 둔다.
- 확정 후 `parse_result`는 비운다(A8과 동일 조치).
- **에러 메시지·로그에 셀 값을 담지 않는다.** 위치(`시트명!행:열`)와 사유만 남긴다.

#### 🟡 S7. 하이퍼링크 셀의 `javascript:` 스킴

`01_편집팀`에는 URL 셀이 실제로 있다. 사이드 패널에서 `<a href={hyperlink}>`로 렌더하면 `javascript:` URL이 XSS가 된다.

**확정**: `http`·`https`만 허용하는 스킴 검사를 통과한 링크만 앵커로 렌더하고, 나머지는 **텍스트로만** 표시. 외부 링크에는 `rel="noopener noreferrer"`.

React가 기본 이스케이프하므로 태스크 제목·비고의 XSS 위험은 낮다. 단 **주간 브리핑 마크다운을 HTML로 렌더하게 되면** 그때 sanitize가 필요하다 — 현재 계획은 "복사"만이라 해당 없음. 렌더로 바꾸면 재검토.

### 에러 핸들링

#### X1. 에러 코드 체계

`{ error: { code, message } }`만 있고 코드 목록이 없었다. 확정:

```
FILE_TOO_LARGE · FILE_TYPE_MISMATCH · ARCHIVE_LIMIT_EXCEEDED · PARSE_TIMEOUT
WORKBOOK_CORRUPT · NO_KNOWN_TAB · SETTINGS_TAB_MISSING
UPLOAD_NOT_FOUND · UPLOAD_ALREADY_COMMITTED
STORAGE_READONLY · STORAGE_UNAVAILABLE · FORBIDDEN · VALIDATION_FAILED
```

`message`는 **사용자에게 보여줄 한국어 문장**이고, 스택·내부 경로·셀 값을 담지 않는다.

#### X2. 실패 강도 3단계 — 뭉개지 말 것

| 강도 | 예 | 동작 |
|---|---|---|
| **경고** (진행) | 미등록 enum, 담당자 오타, 날짜 파싱 실패 1건 | 값 보존 + `warnings[]`, 미리보기에 표시, 확정 가능 |
| **부분 실패** (진행) | 탭 하나 판별 실패 | 해당 탭만 건너뛰고 나머지 확정. **어떤 탭이 빠졌는지 명시** |
| **중단** (불가) | 아카이브 한도 초과, 워크북 손상, 타임아웃 | 저장소 무변경, 코드+사유 반환 |

**중요**: "알려진 탭이 하나도 없음"은 중단이다. 빈 결과를 성공으로 처리하면 **기존 데이터가 0건으로 덮이는** 최악의 사고가 난다. 부분 업로드를 지원하기 때문에 이 구분이 더 중요하다.

#### X3. 빈 상태 ≠ 에러 상태

계획엔 빈 상태만 있었다. 셋을 구분한다:

```
데이터 없음      → "아직 데이터가 없습니다"  [샘플 불러오기] [시트 업로드]
저장소 연결 실패  → "읽기 전용 — 저장소 연결 실패"  배너 + 편집 비활성 (A2)
조회 실패        → error.tsx 바운더리 + [다시 시도]
필터 결과 0건    → "조건에 맞는 업무가 없습니다"  [필터 초기화]
```

Next.js `error.tsx`를 `app/`과 `app/teams/`에 둔다. 하나 터졌다고 전체 화면이 백지가 되면 안 된다.

#### X4. 업로드 실패의 되돌림

`committing` 중 실패하면 **일부만 반영된 상태**가 남는다. 4MB 규모에서 트랜잭션을 감당할 수 있으므로 upsert를 **단일 트랜잭션**으로 묶는다(메모리 드라이버는 스냅샷 후 교체). 실패 시 `previewing`으로 되돌아가 재시도 가능 — 이미 상태 전이도에 있는 경로다.

  6. **압축 폭탄 방어**: 해제 총량 50MB / 시트 20개 / 셀 20,000개 / 타임아웃 8초 초과 시 중단하고 부분 결과를 저장하지 않는다 (S2)
  7. **"알려진 탭 0개"는 성공이 아니라 중단이다** — 빈 결과로 기존 데이터를 덮지 않는다 (X2)
  8. 실패 강도 3단계(경고/부분 실패/중단)가 구분되고, 부분 실패 시 **빠진 탭이 명시**된다 (X2)
  9. `GET /api/tasks` 응답에 **`raw`가 포함되지 않는다** (zod 스키마로 강제, S6)
  10. 에러 응답이 X1 코드 체계를 따르고 **셀 값·스택·내부 경로를 담지 않는다**
  11. 데이터가 없을 때 빈 상태 화면과 `[샘플 데이터 불러오기]` 버튼이 뜬다
  12. 서버 컴포넌트는 `lib/`를 직접 호출하고, API는 클라이언트 상호작용에만 쓰인다 (A3)
  13. 확정 후 `uploads.parse_result`가 비워지고 `summary`만 남는다 (A8·S6)
  14. upsert가 단일 트랜잭션으로 묶여 실패 시 부분 반영이 남지 않는다 (X4)
- **리스크·미결**: Next 16에서 동적 세그먼트 `params`는 Promise다 (`const { id } = await params`). Route Handler에는 프레임워크 본문 크기 제한이 없으므로 **4MB 제한을 직접 구현**해야 한다. 부분 업로드는 사용자 확정 요구사항이므로 완료 기준 4번은 타협 대상이 아니다.
