# 전사 업무 현황판 고도화 (6-2) 구현 계획

> 최초 작성 2026-08-13
> 이 문서는 이후 발행되는 모든 티켓(T0~T9)의 근거다. 결정이 바뀌면 티켓보다 **이 문서를 먼저** 고친다.
> 계획·규약 문서라 `main`에 직접 올린다. 실제 작업은 T0부터 이슈 → 브랜치 → PR 절차를 따른다 (`docs/TEAM_RULES.md` 2.5절).

## Context

VAN AI Innovation 학회 과제 **6-2. 전사 업무 현황판 고도화 (中上)**. 1인 개발(갠플), 웹 형식.

**해결하려는 문제**: 현재 조직의 업무 현황이 Google Sheets 한 파일에 흩어져 있다. 실제 시트(`[VAN] 26-2 컨텐츠마케팅부 업무_`)를 열어보면 팀별 탭의 컬럼 스키마가 **16 / 70 / 20개로 완전히 다르다**. 사람이 탭을 넘나들며 눈으로 취합해야 하고, 마감 임박·지연·담당자 미지정을 자동으로 알 방법이 없다.

**담당자가 준 구체적 지시가 최우선 기준이다** (과제 원문보다 우선):

> "엑셀 시트 **입력 시 업무 파악을 빠르게 조회하거나 파악**할 수 있는 기능 추가해주시면 될 것 같습니다. 그리고 **독스 파일 입력 시 저희 업무 배정표처럼 엑셀시트로 뽑을 수 있는** 기능 이렇게 추가하면 됩니다"

따라서 평가 대상 산출물은 **두 개**로 못박는다:

1. **엑셀 넣으면 → 빠르게 조회·파악** (파서 + 대시보드 + 조회 UX)
2. **독스 넣으면 → 업무 배정표 엑셀이 나옴** (아웃라인 파서 + xlsx 생성)

과제 원문의 나머지(알림·목표 대비 성과·주간 보고·권한)는 위 둘을 떠받치는 형태로만 구현한다.

**의도한 결과**: `npm run dev` 한 번으로 실제 시트를 올려 통합 대시보드가 뜨고, 독스를 올려 드롭다운이 붙은 배정표 xlsx가 떨어진다. 두 기능이 한 바퀴로 닫힌다 — 뽑은 배정표를 그대로 입력해 다시 시스템에 올릴 수 있다.

### Supabase를 처음부터 붙인다

메모리로 만들었다가 옮기는 2단계를 쓰지 않는다. **T4에서 바로 Supabase 스키마를 잡고 붙인다.** 부수 효과로 "이관" 티켓이 통째로 사라진다.

`TaskRepository` 인터페이스와 메모리 드라이버는 **그대로 유지한다.** 다만 역할이 바뀐다 — 마이그레이션 경로가 아니라 **시연 안전망**이다:

- Supabase 무료 티어는 7일 미접속 시 프로젝트를 일시중지한다. 발표장에서 조용히 죽는 것을 막아야 한다.
- 심사자가 클론해서 **`.env` 없이 바로 실행**할 수 있어야 한다 (`STORAGE_DRIVER=memory`).
- 두 구현이 같은 계약 테스트를 통과하므로 도메인 로직 검증이 저장소와 분리된다.

메모리 드라이버 자체는 배열 몇 개라 비용이 거의 없다. 값어치는 위 세 가지다.

### 과제 원문 7개 요구사항 대조

| # | 요구사항 | 어디서 |
|---|---|---|
| 1 | 부서·팀·담당자·업무·기한·진행률·지연 사유 통합 관리 | 데이터 모델 (T3·T4) |
| 2 | 예정·진행·검토·완료·지연 상태 시각적 구분 | semantic 5색 파생 + 배지 (T6) |
| 3 | 마감 임박·장기 미갱신·담당자 미지정 자동 알림 | 알림 패널 4종 (T6). **발송은 추후** |
| 4 | **부서별 목표와 실제 성과 비교** | `goal_metrics` + 성과 화면 (T3·T6) |
| 5 | 회의 전 자동 요약 및 대표·실장용 주간 보고서 | `weekly-report` + 브리핑 카드 (T4·T6) |
| 6 | 권한별 열람·수정 범위 구분 | Supabase Auth + RLS (T8) |
| 7 | 향후 출결·평가·경고·활동인증서 연계 | `members`를 신원 단일 소스로 (T4) |

3번의 "자동 알림"은 **대시보드 알림 패널까지**를 초안 범위로 본다. 디스코드 웹훅 발송은 여유가 생기면 붙인다 (T10, 반나절).

7개 요구를 모두 다루되, **담당자 지시 2건(엑셀→조회 / 독스→엑셀)이 여전히 최우선**이다. 무언가를 잘라야 하는 상황이 오면 T10 → T9 → T8 순으로 밀고, T5·T6·T7은 사수한다.

## 입력 데이터 실제 구조 (직접 확인함)

### A. 엑셀 — `[VAN] 26-2 컨텐츠마케팅부 업무_` (탭 5개)

| 탭 | 구조 |
|---|---|
| `00_통합 대시보드` | KPI 10종 + 팀별 요약표 + 확인 필요 업무 + 마감 일정 + 승인 대기함 + 주간 회의 브리핑 |
| `01_편집팀` | 16컬럼. 단계 3개(컨셉+2일 / 제작+5일 / 최종본+7일)가 **컬럼 그룹으로 펼쳐진 wide 포맷** |
| `02_촬영·기획팀` | **약 70컬럼.** 섭외·촬영준비·초안·완성본·촬영실행·편집이관 단계별 |
| `03_마케팅·관리팀` | A(문의 20컬럼) / B(주간 성과) / C(회의 브리핑) 세 섹션이 한 탭에 세로로 |
| `설정` | 팀별 구성원, 공통 enum 4종, 팀 전용 enum 다수, **기본 SLA 일수 표** |

`설정` 탭이 정규화의 근거다. `공통_진행 상태` 10단계(업무 배정→준비 중→진행 중→검토 요청→승인 대기→수정 중→게시·이관 대기→완료→보류→취소), SLA(컨셉 공유 1일 / 섭외 5일 / SNS 답변 1일 …)가 여기 있다.

### B. 독스 — `[VAN] AI혁신부 26-2 워크로드`

산문형이지만 구조가 규칙적이다. `## N. 대분류` → `### N-M. 과제명 (난이도)` → 불릿 세부항목. 난이도는 `上/中上/中/中下/下`, 일부에 `(9/1까지 완성)` 형태 마감. 뒷부분 「워크로드 공유」에 P0/P1과 ①②③④ 블록이 별도로 있다.

## 사용자 여정 (User Journey)

### 이 시스템의 위치 — 가장 중요한 전제

**이 웹은 Google Sheets를 대체하지 않는다.** 담당자가 "엑셀시트 **입력 시**"라고 규정한 순간, 데이터 입력은 여전히 시트에서 일어나고 이 웹은 그것을 **읽고 해석하는 층**이 된다.

```
 [입력 계층]  Google Sheets      ← 팀원이 평소처럼 입력. 바뀌지 않는다.
      ↓            (내보내기)
 [해석 계층]  이 웹              ← 정규화 · 판정 · 시각화 · 조회
      ↓
 [소비 계층]  대시보드 · 주간 브리핑 · 배정표 xlsx
```

- **강점**: 기존 업무 습관을 안 바꾼다. 채택률의 전부가 여기 달렸다.
- **약점**: 업로드하지 않으면 데이터가 낡는다. 이 약점은 설계로 감출 수 없으므로 **화면에 드러낸다** — 모든 페이지에 "마지막 반영: 8/29 14:20 (3일 전)"을 상시 표시하고, 5일 이상 경과하면 경고색으로 바꾼다.

### 페르소나 4종

| 역할 | 누구 | 빈도 | 목적 | 성공 기준 |
|---|---|---|---|---|
| **운영자** | AI혁신부 담당 (본인) | 주 1~2회 | 시트·독스를 올려 데이터 갱신 | 드롭 → 확정까지 3분 |
| **대표·실장** `admin` | 조직 임원 | 주 1회 (회의 직전) | 전사 현황 파악, 의사결정 필요사항 추출 | 한 화면에서 5분 안에 브리핑 완성 |
| **팀장** `lead` | 편집 / 촬영·기획 / 마케팅·관리 | 주 2~3회 | 우리 팀 병목·지연자 특정 | 지연 건과 담당자를 즉시 지목 |
| **부원** `member` | 학회원 | 주 1~2회 | 내 업무·마감 확인 | 진입 후 3초 안에 "내 마감" 확인 |

**운영자는 과제 원문에 없는 페르소나다.** 하지만 데이터가 들어오는 유일한 경로이므로 실제로는 가장 중요하다. 이 사람이 귀찮으면 시스템 전체가 죽는다.

### 주간 운영 루프

```
        ┌──────────────────────────────────────────────────┐
        │  Google Sheets  (입력은 계속 여기서)                │
        │  01_편집팀   02_촬영·기획팀   03_마케팅·관리팀       │
        └────────────────────┬─────────────────────────────┘
                             │ ① 팀원이 평소대로 입력
                             ▼
                     ┌───────────────┐
                     │  xlsx 내보내기  │
                     └───────┬───────┘
                             │ ② 운영자(또는 팀장) 업로드
                             ▼
   ┌──────────────────────────────────────────────────────┐
   │  /upload    드롭 → 파싱 → 미리보기 → 확정              │
   │             신규 N · 변경 M · 유지 K · 경고 W          │
   └────────────────────────┬─────────────────────────────┘
                             │ ③ upsert  (+ task_events 기록)
                             ▼
   ┌──────────────────────────────────────────────────────┐
   │  현황판                                               │
   │    /             통합 대시보드    ← 대표·실장           │
   │    /teams/edit   부서별 탭        ← 팀장·부원          │
   │    ?task=id      사이드 패널      ← 전 역할            │
   └────────────────────────┬─────────────────────────────┘
                             │ ④ 회의 직전
                             ▼
                     ┌────────────────┐
                     │  주간 브리핑 복사 │ → 회의록 · 카톡
                     └────────────────┘
```

**루프의 진입점은 ②다.** ②가 안 돌면 ③④가 전부 낡는다. 그래서 ②를 3분 안에 끝나게 만드는 것이 T5의 성공 기준이다.

### 독스 추출 루프 — 고리가 닫히는 지점

```
   [VAN] AI혁신부 워크로드 (Google Docs)
               │  .docx 내보내기
               ▼
   ┌───────────────────────────────────────┐
   │  /extract   드롭 → 아웃라인 파싱 → 미리보기 │
   │             카테고리·과제명·난이도·마감·세부 │
   └───────────────────┬───────────────────┘
                       │ 다운로드
                       ▼
   ┌───────────────────────────────────────┐
   │  배정표 xlsx                            │
   │  상태·난이도·우선순위에 드롭다운 내장       │
   └───────────────────┬───────────────────┘
                       │ 사람이 담당자·마감·진행률 채워넣음
                       ▼
   ┌───────────────────────────────────────┐
   │  /upload  재업로드                      │
   └───────────────────┬───────────────────┘
                       │
                       └──▶ 현황판에 반영  ★ 고리가 닫힌다
```

**이 고리가 데모의 클라이맥스다.** "산문 문서 → 배정표 → 현황판"이 한 번에 이어지면, 담당자가 요청한 두 기능이 실은 하나의 파이프라인이었다는 것이 드러난다. 드롭다운을 넣는 이유가 이것이다 — 드롭다운이 없으면 사람이 자유 입력해서 재업로드 시 enum 매칭이 깨진다.

### 역할별 진입 경로

```
                          로그인 (T8 이후)
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
      admin                 lead                member
         │                    │                    │
         ▼                    ▼                    ▼
  /  통합 대시보드      /teams/{내 팀}       / ?owner=나
  ─────────────       ─────────────        ─────────────
  전 팀 KPI 10종       우리 팀 태스크 표      "내 업무" 프리셋
  팀별 완료율 비교      지연 · 미지정 강조     마감 임박 배지
  승인 대기함          담당자별 그룹핑        상태·진행률 수정
  주간 브리핑 카드      다음 조치 목록        (본인 건만)
```

T8 이전(초안 시점)에는 로그인이 없으므로 **`?as=admin|lead|member` 쿼리로 역할을 전환**해 세 경로를 모두 시연한다. 이건 개발 편의가 아니라 **심사·데모용 정식 기능**이다.

      │                                    │ 공통 필드 + extras 전량
      │ 필터 조합                           │ stage 타임라인
      ▼                                    │ 최근 변경 이력
   URL 쿼리에 유지 ──▶ 링크 복사 ──▶ 공유    └── Esc / 오버레이 ▶ 닫기
```

**필터 상태를 URL에 유지하는 이유는 기술적 편의가 아니라 UC-11 때문이다** — 팀장이 "이거 봐" 하고 부원에게 링크를 던지는 행위가 실제로 가장 자주 일어난다.

### 업로드 상태 전이 (실패 경로 포함)

```
   idle
    │ 파일 드롭
    ▼
   validating ──✗ 확장자·매직넘버·5MB 초과 ──▶ rejected ──▶ idle
    │ ✓
    ▼
   parsing ──✗ 워크북 손상·탭 판별 실패 ──▶ failed (사유 표시) ──▶ idle
    │ ✓
    ▼
   previewing   신규 N · 변경 M · 유지 K · 경고 W
    │      └────── 취소 ──▶ idle   ★ 저장소 무변경
    │ 확정
    ▼
   committing ──✗ 저장 실패 ──▶ failed ──▶ previewing (재시도 가능)
    │ ✓
    ▼
   done ──▶ / 이동 + "N건 반영" 토스트 + "마지막 반영" 갱신
```

`previewing`에서 취소하면 **저장소에 아무것도 쓰이지 않는다.** 이 성질이 "잘못된 파일로 DB 오염" 시나리오(UC-02)를 막는다.

### 여정에서 도출된 설계 요구 (기존 계획에 추가)

여정을 그려보고 나서 새로 필요해진 것들. 해당 티켓에 반영했다.

1. **"마지막 반영" 상시 표시** — 수동 업로드의 약점을 숨기지 않고 드러냄 → T6
2. **부분 업로드 지원** — 사용자 확정 요구사항. 팀장이 자기 탭만 올려도 나머지 유지 → T5
3. **"기한 미설정" 알림** — 담당자 미지정과 대칭인데 빠져 있었음 → T4
4. **빈 상태 + 샘플 데이터 원클릭** — 첫 5분이 평가를 좌우 → T5
5. **`?as=` 역할 전환** — 로그인 없이 권한 구분을 시연 (H7 헤지) → T6
6. **주간 브리핑을 대시보드 카드로 선노출** — 전용 화면(`/report`)은 T9지만, admin 여정의 종착점이라 초안에 최소 형태로 필요 → T6
7. **`?owner=` 프리셋과 `?task=` 딥링크** — UC-11·UC-14의 실체 → T6

## 설계

### 1. 데이터 모델 — 공통 컬럼 + `extras jsonb` + `task_stages`

팀별 16/70/20 컬럼을 담는 방법 중 **공통 컬럼 + JSONB + 자식 테이블**을 택한다. 팀별 전용 테이블 3개는 통합 대시보드가 3-way UNION이 되고, 완전 EAV는 집계 쿼리가 지옥이다.

핵심 성질: **매핑되지 않은 컬럼은 자동으로 `extras`로 흘러들어간다.** 이것이 70컬럼 대응의 전부다.

```
departments  · teams  · members(auth_user_id nullable)

tasks
  id, team_id, department_id
  source_key            -- 자연키. 업무ID 있으면 그것, 없으면 slug(업무명)+담당자
  title, owner_member_id, owner_name_raw, co_owner_names[]
  status                -- 설정 탭 원문 그대로 보존
  approval_status, priority, risk_status
  progress smallint     -- null 허용 (빈 셀과 0을 반드시 구분)
  assigned_at, due_at, next_action, next_action_owner, next_action_due
  delay_reason, note
  extras jsonb          -- 팀 전용 필드
  raw jsonb             -- 원본 행 통째 (감사·복원)
  last_progress_at      -- 장기 미갱신 판정 기준
  source_upload_id, source_sheet_tab, source_row_index
  UNIQUE (team_id, source_key)

task_stages   task_id, seq, stage_key, stage_label,
              planned_date, actual_date, content, confirm_status, sla_days
              -- 편집팀 3개 컬럼 그룹, 촬영팀 5개 접두사 그룹을 같은 모양으로 언피벗

task_events   task_id, upload_id, changed_fields jsonb, occurred_at
enum_options  group_key, value, sort_order, semantic
sla_rules     team_id(null=공통), stage_key, label, days
uploads       kind, filename, parse_result jsonb, status, summary
doc_extractions  upload_id, order_index, category, task_no, title,
                 difficulty, deadline_raw, deadline_date, priority, details jsonb

goal_metrics     team_id, period_label            -- "2026-07 4주차"
                 title                            -- 마케팅 과제명
                 goal_text, kpi_name              -- 목표 / 목표 KPI
                 target_value numeric, actual_value numeric
                 achievement_rate numeric         -- 달성률 (시트 값도 보존)
                 prev_period_delta text           -- 직전 주 대비 변화
                 channel, owner_member_id, exec_status
                 analysis, went_well, needs_improvement
                 started_at date, due_at date
                 extras jsonb, source_upload_id
                 UNIQUE (team_id, period_label, title)

team_period_goals  team_id, period_label, goal_text, risk_text
                 -- 촬영·기획팀 헤더 블록의 "이번 주 핵심 목표 / 주요 리스크"
```

**`goal_metrics`가 과제 요구 4번("부서별 목표와 실제 성과 비교")의 실체다.** 이 데이터는 새로 만드는 게 아니라 **시트에 이미 있다** — `03_마케팅·관리팀`의 B섹션(주간 마케팅 실행·성과 관리)에 `목표 | 목표 KPI | 목표 수치 | 실제 성과 | 달성률 | 직전 주 대비 변화 | 성과 분석 | 잘된 점 | 개선 필요사항` 컬럼이 그대로 있다. `02_촬영·기획팀` 헤더에도 `이번 주 핵심 목표: [목표 입력]`이 있다.

`tasks`와 별도 테이블인 이유: **업무가 아니라 성과 지표다.** 진행 상태·마감·담당자 축이 아니라 목표값 대 실적값 축으로 움직인다. `tasks`에 억지로 넣으면 `extras`가 비대해지고 집계가 꼬인다.

**`enum_options.semantic`이 설계의 급소.** 판정 로직이 한글 상태 문자열을 직접 알면 시트에서 이름이 바뀔 때 코드가 깨진다. 매핑층을 둔다:

```
업무 배정·준비 중 → planned      검토 요청 → review     게시·이관 대기 → pending_release
진행 중          → in_progress   승인 대기 → approval   완료 → done
수정 중          → rework        보류 → hold            취소 → cancelled
```

**「지연」은 상태값이 아니라 파생 판정이다** (`due_at < today && semantic ∉ {done, cancelled}`), 여기에 시트의 `리스크 상태 = 지연`을 OR로 합친다. 이 구분을 흐리면 완료율이 틀린다.

### 4. 엑셀 파싱 파이프라인

```
업로드(5MB 제한, 확장자+매직넘버 검증)
  ↓ workbook-reader     시트별 cells[][] + merges[]
  ↓ header-resolver     병합셀 forward-fill → 2단 헤더를 "컨셉·레퍼런스 / 예정일" 경로로 결합
  ↓ tab-detector        탭 이름 정규식 + 헤더 시그니처(필수 컬럼 3개 이상 일치) 이중 판별
  ↓ [설정 탭 먼저]       enum/SLA 레지스트리 확보
  ↓ section-splitter    마케팅 탭 A/B/C 분할 (빈 행 2개 이상 + "A." 헤더 패턴)
                        A → tasks(문의)   B → goal_metrics(성과)   C → 브리핑 텍스트
  ↓ 팀별 어댑터          선언적 FIELD_MAP + STAGE_GROUPS
  ↓ zod 검증            실패는 warnings[]에 담고 값은 보존 (하드 실패 금지)
  ↓ 미리보기 반환        { 신규 N / 변경 M / 유지 K / 경고 }
  ↓ [사용자 확정] → upsert ON CONFLICT (team_id, source_key)
```

**어댑터는 선언적 맵으로 쓴다.** 절차적 if문으로 70컬럼을 처리하면 유지 불가능하다.

```
FIELD_MAP    : 헤더 패턴 → 공통 필드 (매칭 실패 컬럼은 자동으로 extras)
STAGE_GROUPS : { key:'concept', label:'컨셉·레퍼런스', slaDays:2,
                 cols:{ planned:'예정일', actual:'실제', content:'내용', confirm:'확인' } }
```

편집팀 3개 그룹과 촬영팀 5개 접두사 그룹이 **동일한 언피벗 함수 하나**로 `task_stages`가 된다. 어댑터 3개가 공유하는 코드가 이 함수다.

**미리보기→확정 2단계**를 쓰는 이유: 즉시 반영은 단순하지만 잘못된 파일 하나로 DB가 오염되고 되돌리기 어렵다. 파싱 결과를 `uploads.parse_result`에 넣고 확정 시 그것을 소스로 upsert하면 서버 세션 상태 없이 2단계가 된다.

**자연키 불안정 위험**: 업무ID 없는 탭은 `slug(업무명)+담당자`가 키라 오타 한 번에 중복 행이 생긴다. 완화는 자동화가 아니라 **미리보기의 "신규 N건" 숫자** — 예상보다 크면 사람이 알아챈다.

### 5. 독스 → 배정표 — `.docx` 단일 입력

**제품이 받는 입력은 `.docx` 하나다** (사용자 확정). Google Docs에서 내보낸 파일을 그대로 올린다.

- `.docx` → mammoth(`convertToHtml`, **옵션 없음** — T1에서 styleMap이 불필요하다고 판정됐다) → `node-html-parser` 순회 → `OutlineNode[]`

`markdown-reader.ts`는 **테스트 픽스처 전용으로만 남긴다.** 제품 경로가 아니다. 이유는 두 가지다:

1. **`.docx`는 바이너리라 픽스처로 최악이다.** git diff가 안 되고 테스트가 뭘 검증하는지 읽을 수 없다. `.md` 픽스처로 아웃라인 로직을 검증하고, `.docx`는 리더 계층만 스모크 테스트한다.
2. mammoth 파싱이 흔들릴 때(H8) 이미 만들어둔 탈출구가 된다. 추가 비용은 파일 하나다.

경계: `docx-reader.ts`와 `markdown-reader.ts`가 **같은 `OutlineNode[]`를 뱉고**, 그 아래(`outline-builder` → `assignment-mapper`)는 입력 형식을 모른다.

**✅ 선행 스모크 테스트 완료 (T1)**: 실제 Google Docs를 `.docx`로 내보내 실측했다. mammoth **기본 옵션에서 heading이 인식된다 — styleMap 커스터마이즈가 필요 없다.** `h2` 12건(`N.` 접두사 9건) · `h3` 50건(`N-M.` 접두사 20건)이 잡혀 `## N. 대분류` → `h2`, `### N-M. 과제명` → `h3` 매핑이 그대로 성립했다. 따라서 `docx-reader.ts`는 `mammoth.convertToHtml`을 **옵션 없이** 호출한다. 다만 인자는 `{ path }`가 아니라 **`{ buffer }`**다 — 라우트가 받는 것은 업로드된 바이트이고, 디스크에 임시 파일을 쓰면 그 파일에 사람 이름이 남는다 (`S6`). 측정 방법과 전체 수치는 `scripts/smoke/RESULT.md`「H8」에 있다.

단 `h3` 50건 중 **아웃라인 과제는 `N-M.` 접두사를 가진 20건이고 나머지 30건은 과제가 아닌 절 제목**이다. `outline-builder`는 태그 깊이만이 아니라 **번호 접두사도 함께** 봐야 한다 (T7 범위).

**미리 박아두는 주의점 3개:**

- **난이도 정규식 순서**: `上|中上|中|中下|下` 그대로 쓰면 `中上`이 `中`에 먼저 걸린다. **긴 것부터 정렬** (`中上|中下|上|中|下`). 실제로 나는 버그다.
- **난이도 표기(2026-08-24 확정)**: 문서 원문은 한자지만 **배정표에 담기는 값은 한글**이다 (`상`·`중상`·`중`·`중하`·`하`). 배정표는 팀에 배포되는 파일이고 드롭다운에서 고르는 값이라, 한자 표기는 고를 때마다 「중상이 중보다 위인가」를 다시 생각하게 한다. **매칭 규칙은 그대로다** — 원문이 한자이므로 `DIFFICULTY_MATCH_ORDER`(긴 것부터)가 진실이고, 변환표(`DIFFICULTY_LABELS`)가 그 뒤에 붙는다. 한글을 매칭 목록에 넣지 않는 이유는 `(상세 협의 필요)` 같은 정당한 괄호에서 `상`이 걸리기 때문이다.
- **연도 추론**: `9/1`에 연도가 없다. 하드코딩 금지 — `baseYear`를 파라미터로 주입, UI에서 기본값 제공. 실패 시 `deadline_raw`만 보존하고 `deadline_date`는 null.
- **「워크로드 공유」 섹션**: P0/P1과 ①②③④가 별도 블록이므로 `workload-parser.ts`로 분리 파싱 후 과제 번호로 조인해 `priority`를 채운다. 조인 실패는 무시.

**생성물은 사람이 이어서 입력할 파일이어야 한다:**

```
카테고리 | 번호 | 과제명 | 난이도 | 마감 | 우선순위 | 세부항목 | 담당자 | 상태 | 진행률 | 비고
                                                            ↑빈칸   ↑드롭다운 ↑% 서식
```

1행 틀고정, 열너비, 헤더 굵게. `상태`·`난이도`·`우선순위`에 **데이터 검증 드롭다운** — 값은 `설정` 탭에서 읽은 `enum_options` 재사용. **이러면 뽑은 배정표를 그대로 입력해 다시 시스템에 올릴 수 있다.** 두 기능이 한 바퀴로 닫힌다. 데모의 클라이맥스다.

> 위 문장의 「`설정` 탭에서 읽은 `enum_options` 재사용」은 **T7 시점에 성립하지 않는다** — 아래
> 「T7 착수 시 확정」 결정 B를 본다. 원래 의도가 근거로 남아야 해서 문장은 지우지 않았다.

**왕복 테스트**: `sample-workload.md` → rows → xlsx 버퍼 → 시트 파서로 다시 읽기 → rows 동일. 두 파이프라인을 한 번에 검증하는 가장 가치 있는 통합 테스트.

**LLM은 옵션.** `ENABLE_LLM=false`가 기본. 키가 없으면 보조 필드만 빈칸이고 나머지는 그대로 동작한다. 이 경계를 넘지 않는다.

#### T7 착수 시 확정 (2026-08-23)

위 문단들은 T2 시점의 설계다. T7에 착수하면서 **뒤 단계 열 개가 갈라지지 않도록** 네 가지를
못박는다. 기존 문단은 근거로 남기고 여기에 이어 붙인다.

**결정 A — 우선순위는 시트 enum 값으로 옮겨 적는다.** 문서의 「워크로드 공유」 절은 우선순위를
`P0`·`P1`로 적지만, 배정표의 `우선순위` 컬럼은 시트 `공통_우선순위` 드롭다운을 달고 나간다.
`P0`을 그대로 쓰면 셀 값이 드롭다운 목록 밖이라 엑셀이 경고를 띄우고, 그 파일을 `/upload`에
재업로드하면 `task-semantic.ts`의 `UNREGISTERED_PRIORITY` 경고가 뜬다. **고리가 닫히지 않는다.**

| 문서 | 배정표 `우선순위` |
|---|---|
| `P0` | `긴급` |
| `P1` | `높음` |
| `P2` | `보통` |
| `P3` | `낮음` |
| 그 밖 · 조인 실패 | 빈칸 (경고도 내지 않는다 — `TICKETS.md` T7 「조인 실패는 무시」) |

원문(`P0`)을 버리지는 않는다. 행이 `priorityRaw`로 들고 있고 배정표 셀에는 매핑된 값만 쓴다.
결정 이력은 `ADR-021`.

**결정 B — 드롭다운 목록은 `assignment-writer`가 인자로 받는다.** 위 문단의 「`설정` 탭에서 읽은
`enum_options` 재사용」은 T7 시점에 읽을 곳이 없다 — `enum_options` 테이블은 있지만
`TaskRepository`에 읽기 메서드가 없고, `/extract`는 시트 업로드와 무관하게 단독으로 돈다
(`TICKETS.md`가 T7을 T2 직후에 두는 이유다). 기본값은 **코드에 이미 있는 단일 출처**에서 만든다.

| 컬럼 | 기본 목록 | 출처 |
|---|---|---|
| `상태` | 시트 10단계 | `STATUS_SEMANTIC_MAP`의 키 순서 (`lib/domain/task-semantic.ts`) |
| `난이도` | `上`·`中上`·`中`·`中下`·`下` | `assignment-mapper.ts`의 `DIFFICULTY_LEVELS` |
| `우선순위` | `긴급`·`높음`·`보통`·`낮음` | `assignment-mapper.ts`의 `PRIORITY_LEVELS` (`공통_우선순위` 실측값) |

**상태 문자열을 `assignment-writer.ts`에 다시 적지 않는다.** 한 글자만 달라져도
(`게시·이관 대기`의 가운뎃점은 `·`) 재업로드에서 조용히 미매핑된다 — `ADR-009`가 상태 원문의
출처를 한 곳으로 몰아 둔 이유가 그것이고, 배정표도 그 규칙 밖이 아니다.

**결정 C — `/extract`는 아무것도 저장하지 않는다. 왕복 두 번이다.** `TICKETS.md` T7 범위 Out에
「DB 저장」이 있으므로 `ADR-008`의 미리보기→확정 2단계를 쓰지 않는다 — 확정할 저장소가 없다.
라우트는 둘이며 이름은 `ARCHITECTURE.md`가 이미 적어 둔 것을 그대로 쓴다.

```
POST /api/uploads/doc        .docx  → 배정표 행 미리보기(JSON). uploads 행을 만들지 않는다
POST /api/export/assignment  행 JSON → 배정표 .xlsx 바이트 (Content-Disposition: attachment)

`uploads` 행을 만들지 않는 이유는 스코프만이 아니다. 그 행의 `parse_result`에 문서 본문이
통째로 남는데 **워크로드 문서에는 사람 이름이 들어 있다** (`S6`). 결정 이력은 `ADR-022`.

**결정 D — 에러 코드 2개를 추가한다.** 아래 두 코드를 `X1` 목록에 넣는다. ADR을 만들지 않는

|---|---|---|

#### T7 구현 중 확정 (2026-08-24, step 10 감사)

착수 시점에 못박은 A~D는 그대로 섰다. 구현하면서 **새로 갈린 것 둘**을 여기 잇는다.

**결정 E — `.docx` 픽스처를 커밋하되, 진짜 원본은 그것을 만드는 스크립트다.** 위
「독스 → 배정표」 절은 「`.docx`는 바이너리라 픽스처로 최악이다 — git diff가 안 되고
테스트가 뭘 검증하는지 읽을 수 없다」고 적었고 그 판단은 **지금도 맞다.** 그래서 바이너리를
손으로 만들어 넣는 대신 `scripts/fixtures/build-sample-workload-docx.mjs`(`npm run fixture:docx`)가
생성한다 — ZIP 엔트리 3개·무압축·CRC-32 직접 계산·타임스탬프 고정이라 **재실행해도 같은
바이트**이고, 리뷰어가 읽을 것은 `.docx`가 아니라 그 스크립트다. `markdown-reader`가 픽스처
전용이라는 `ADR-010`은 **바뀌지 않았다** — `.md`가 여전히 아웃라인 로직을 검증하고 `.docx`는
리더 계층만 본다. 늘어난 것은 「리더 계층을 실제 바이너리로 한 번 밟는다」는 자리 하나다.

**결정 F — `/extract`는 읽기 전용 모드에서도 정상 동작한다.** `ADR-005`가 「폴백 중 모든 쓰기
경로는 `503`」이라고 정했지만 이 화면에는 **쓰기 경로가 없다**(결정 C). 그래서 화면이
`readOnly`를 패널에 넘기지 않고 드롭존을 잠그지 않는다 — 잠그면 「저장소가 죽어도 배정표는
뽑을 수 있다」는 사실을 화면이 스스로 부정한다. 배너는 그대로 뜬다: 배너가 말하는 것은
**저장소 상태**이지 이 화면의 가용성이 아니다.

### 6. 집계·판정 — `src/lib/domain/` 순수 함수

**`now`는 반드시 인자로 주입한다** (`Date.now()` 직접 호출 금지 — 테스트가 날짜에 따라 깨진다).

```
toSemantic(statusRaw, registry)              → semantic
toDisplayStatus(semantic, flags)             → 예정 | 진행 | 검토 | 완료 | 지연   ← 요구 2번
deriveTaskFlags(task, ctx)                   → { isOverdue, isDueSoon, dday, isStale, hasNoOwner }
summarizeTeam(tasks, ctx)                    → { total, active, done, overdue, completionRate, delayRate, ... }
buildKpiStrip(tasks, ctx)                    → KPI 10종
collectAlerts(tasks, stages, ctx)            → Alert[]
summarizeGoals(metrics, ctx)                 → 팀별 목표 대비 달성률          ← 요구 4번
buildWeeklyReport(tasks, metrics, events, ctx) → 마크다운
```

**`toDisplayStatus`가 요구 2번("예정·진행·검토·완료·지연 5색 구분")의 실체다.** 시트의 진행 상태는 10단계인데 화면은 5색이므로 매핑층이 하나 더 필요하다:

```
planned                        → 예정
in_progress · rework           → 진행
review · approval              → 검토
done · pending_release         → 완료
(semantic 무관) isOverdue      → 지연     ← 파생 판정이 다른 색을 덮어쓴다
hold · cancelled               → 무채색 (5색에 속하지 않음)
```

**「지연」은 상태값이 아니라 파생이므로 최우선 적용**된다. 진행 중이면서 마감이 지난 업무는 "진행"이 아니라 "지연"으로 보여야 한다.

**`summarizeGoals`가 요구 4번의 계산부다.** 시트의 `달성률`을 그대로 쓰지 않고 `actual/target`으로 재계산한 뒤, 시트 값과 다르면 `warnings`에 남긴다 — 시트 수식이 깨져 있을 수 있고 이 불일치가 파서 정확성의 실측 지표가 된다.

판정 규칙 중 **틀리기 쉬운 것들** — 테스트를 명시적으로 쓴다:

- **완료율** = `done / (전체 − cancelled)`. 취소 건을 모수에 넣으면 완료율이 영구히 100%에 못 미친다.
- **평균 진행률**: `progress`가 null인 행은 **제외**. 0으로 취급하면 미입력 많은 팀의 진행률이 바닥으로 끌려간다.
- **마감 임박**: 기본 D-3, 해당 단계에 SLA 규칙이 있으면 그 값(SNS 문의 1차 답변 1일 → D-1).
- **장기 미갱신**: `today − last_progress_at > 7일` && semantic이 진행형. `last_progress_at`은 **실제로 값이 바뀐 경우에만** 갱신한다 — 같은 파일 재업로드로 갱신되면 판정이 무의미해진다. 이래서 `task_events`가 필요하다.
- **담당자 미지정**: 빈값/`미정`/`TBD`/`-`. 추가로 **레지스트리 팀원 목록에 없는 이름**은 `unknown_owner` 경고로 분류(오타 잡기).
- **D-DAY**: 날짜 문자열(`YYYY-MM-DD`) 비교로만 계산. `Date` 객체 뺄셈은 UTC 오프셋 때문에 KST에서 하루가 어긋난다.

### 7. 화면

**통합 대시보드 `/`** — 시트의 `00_통합 대시보드` 탭을 **1:1로 옮긴다.** 담당자가 만든 레이아웃과 대응시키는 것이 "우리 시트를 이해했다"는 가장 강한 신호다.

```
KPI 스트립 (10 타일)      ← 시트 KPI 행
팀별 요약 테이블 + 도넛/바  ← 시트 팀별 요약표
목표 대비 성과 섹션        ← goal_metrics. 목표 수치 대 실제 성과 + 달성률 (요구 4번)
이번 주 확인 필요 업무      ← 시트 동명 섹션 (D-DAY, 다음 조치 포함)
이번 주 마감 일정 · 승인 대기함
알림 패널                 ← 마감 임박 / 장기 미갱신 / 담당자 미지정
```

**부서별 탭 `/teams/[teamSlug]`** — "각 부서마다 new tabs" 요구를 라우트로 충족. **70컬럼을 표에 뿌리지 않는다.** 표는 공통 8~10컬럼, 팀 전용 필드는 사이드 패널 "상세"에서 `extras`를 라벨-값으로 나열. 이 결정이 촬영팀 탭을 쓸 수 있게 만든다.

**슬러그는 ASCII다** — `/teams/edit` · `/teams/shoot` · `/teams/marketing` (T6에서 확정). 이 화면의 존재 이유가 링크 복사·공유(UC-11)인데, 한글 경로는 복사하면 `/teams/%ED%8E%B8%EC%A7%91%ED%8C%80`이 되어 사람이 읽을 수 없고 메신저·이슈 본문에서 줄이 깨진다. 팀 키(`edit`·`shoot`·`marketing`)는 이미 `TeamKey`로 코드 전체에 있으므로 새 어휘를 만드는 것도 아니다. 모르는 슬러그는 **404**다 — 전사 대시보드로 넘기면 오타 링크가 조용히 다른 화면을 보여 주고 사람이 데이터를 의심한다. **경로가 `?team=`을 이긴다**: `/teams/edit?team=shoot`이 촬영팀을 보여주는 링크는 거짓말이다.

**빠른 조회 UX** (과제 원문엔 없지만 담당자 지시의 본체) — 필터 바(팀/상태 칩/담당자/마감 범위/지연만/검색), **필터 상태를 URL 쿼리에 유지**(링크 공유 + 서버 컴포넌트와 맞물림), 마감 임박순 기본 정렬, 담당자별·상태별 그룹핑 토글.

**시각화** — Chart.js(도넛=팀별 상태 분포, 가로 바=팀별 완료율). Overdue는 행 좌측 3px 붉은 보더 + 배지. `docs/UI_GUIDE.md` 안티패턴 준수: **글로우 애니메이션·gradient-text·보라/인디고·backdrop-filter blur 금지.** 사이드 패널은 `translate-x` 200ms + Esc 닫기. 리프레시는 `router.refresh()` + `isPending` 표시(불투명도 페이드 150ms)까지다. **클라이언트 시계로 찍는 "갱신 시각"은 두지 않는다** (T6 step 9 확정) — 화면에는 이미 서버가 준 "마지막 반영: N일 전"이 있고, 두 시각이 나란히 있으면 어느 쪽이 데이터의 신선도인지 사용자가 혼동한다. 이 시스템에서 낡는 것은 화면이 아니라 데이터다.

### 8. 권한 — 초안 범위 (T8)

`profiles.role`: `admin`(대표·실장) / `lead`(팀장) / `member`(부원). RLS 정책 5개 남짓.

**⚠ RLS 재귀 함정**: 정책 안에서 `profiles`를 직접 select하면 무한루프다. `security definer` 함수(`my_role()`, `my_team()`)로 감싼다.

**`service_role` 키는 서버의 업로드 커밋·시드에만** 쓰고, 조회는 사용자 JWT를 실은 클라이언트로 해서 RLS가 실제로 걸리게 한다. 전부 service_role로 처리하면 RLS를 만들어도 의미가 없다.

#### T8 착수 시 확정 (2026-08-27)

위 세 문단은 T2 시점의 설계다. T8에 착수하면서 **뒤 step 열둘이 갈라지지 않도록** 여섯 가지를
못박는다. 기존 문단은 근거로 남기고 여기에 이어 붙인다. T8은 앞의 어느 티켓보다 되돌리기가
비싸다 — 조회 경로 전환은 `getStorage()` 싱글턴을 건드리고, RLS 정책은 원격 DB에 적용된다.

**결정 A — 세션은 `@supabase/ssr` 쿠키이고, 게이트는 `src/proxy.ts`다.**
직접 쿠키를 굽는 대신 `@supabase/ssr`을 쓰는 이유는 **리프레시 토큰 회전** 하나다. access token은
1시간이면 만료되고, 갱신을 우리가 짜면 「조용히 로그아웃되는 버그」가 이 프로젝트에서 가장
재현하기 어려운 종류가 된다. 그리고 **Next.js 16에서 `middleware.ts`는 `proxy.ts`로 이름이
바뀌었다** — 파일은 `src/proxy.ts`, export 이름은 `proxy`다. `middleware`라고 쓰면 아무 일도
일어나지 않고, 그 실패는 조용하다.

**결정 B — 조회는 사용자 JWT로 나가고, `service_role`은 업로드 확정·시드에만 쓴다.**
위 문단이 이미 적은 원칙의 실행 표다. **전부 `service_role`로 처리하면 RLS를 만들어도 의미가 없다.**

| 경로 | 클라이언트 | 이유 |
|---|---|---|
| 대시보드·팀 탭·조회 라우트 6종 | anon 키 + 사용자 JWT | RLS가 실제로 걸린다 |
| `PATCH /api/tasks/[id]` | anon 키 + 사용자 JWT | 서버 판정이 뚫려도 DB가 한 번 더 막는다 |
| 업로드 확정 · `/api/uploads/seed` | `service_role` | 시트 전체를 쓴다. 올린 사람의 범위 밖 행도 쓴다 |
| `/extract` 두 라우트 | 저장소를 부르지 않는다 | `ADR-022` |

`getStorage()`는 **프로세스 전역 싱글턴**이라 사용자 JWT를 담을 수 없다(요청마다 다르다).
그래서 `getStorage()`는 `service_role` 경로 전용으로 남기고, 조회용 **요청 스코프** 핸들을
`src/lib/store/viewer-storage.ts`가 따로 만든다. **싱글턴에 JWT를 밀어 넣지 않는다** — 한
사용자의 토큰이 다음 요청의 다른 사용자에게 새는 자리다. 결정 이력은 `ADR-024`.

**결정 C — `security definer` 함수는 둘이 아니라 셋이다.**
위 문단과 `ARCHITECTURE.md`가 적은 것은 `my_role()`·`my_team()` 둘인데, **`member` 범위를 그
둘로는 표현할 수 없다.** `member`가 보는 것은 「본인이 담당인 건」이고 그 판정은
`tasks.owner_member_id = (내 members 행의 id)`다. 정책 안에서 `members`를 직접 select하면
`members`의 정책이 다시 걸려 재귀·성능 함정으로 들어간다 — `profiles`를 감싼 이유와 같다.

```
my_role()       → text   -- profiles.role. 없으면 null (로그인했지만 프로필이 없는 계정)
my_team()       → text   -- profiles.team_id. admin은 null일 수 있다
my_member_id()  → uuid   -- members.auth_user_id = auth.uid() 인 행의 id. 없으면 null
```

셋 다 `language sql` · `stable` · `security definer` · **`set search_path = ''`** 이고 테이블
이름에 스키마를 명시한다(`public.profiles`). `search_path`를 고정하지 않으면 호출자가 같은
이름의 테이블을 자기 스키마에 만들어 함수를 속일 수 있다 — **권한 상승 경로다**(`S5`).
결정 이력은 `ADR-025`.

**결정 D — 매칭 실패는 `unknown_owner`이고, `member` 범위에서 빠진다.**
시트의 담당자는 자유 입력 문자열이라 `members` 행에 붙지 않는 이름이 남는다. 그런 태스크는
`owner_member_id`가 `null`이고 **`member`에게 보이지 않는다.** `null`을 「내 것」으로 치면
담당자 미상 업무가 전원에게 보이고, 그것은 범위 구분이 아니다. `admin`·`lead`에게는 그대로
보인다. 화면이 이것을 숨기지 않는다 — `member` 화면의 빈 상태 문구가 「담당자가 연결되지
않았을 수 있습니다」를 한 줄 알린다. (`TICKETS.md` T8「리스크·미결」이 이미 정한 값이라
ADR을 따로 만들지 않는다.)

**결정 E — 데모 모드는 인증을 요구하지 않는다.**
`.env` 없이 클론해 바로 도는 경로(`STORAGE_DRIVER=memory`)가 죽으면 심사자가 아무것도 못 본다
(`PRD.md` 성공 기준 1번). **`proxy`는 Supabase 자격증명이 없거나 `STORAGE_DRIVER=memory`면
리다이렉트하지 않는다.** 그 모드에서는 지금처럼 `?as=`가 역할을 정한다(`ADR-013` 그대로).
그래서 `?as=` 차단 규칙이 **한 줄 늘어난다** — 표는 아래 `S4`에 함께 붙였다.
「프로덕션에서만 무시」로 두면 개발 서버에서 로그인한 `member`가 `?as=admin`으로 남의 팀을
읽는다. **세션이 있는데 URL이 이기는 경우는 없다.** 결정 이력은 `ADR-026`.

**결정 V (2026-08-29) — 팀장의 열람 범위는 전사이고, 수정 범위만 자기 팀이다.**
`viewer-scope.ts`가 오래도록 「열람 범위와 수정 범위가 같은 함수」였고 머리말에 「갈릴 근거가
생기면 그때 나눈다」고 적혀 있었다. 그때가 왔다 (`ADR-040` · `0012`).

| 역할 | 업무 열람 | 업무 수정 | 만들기 | 지우기 | 목표 지표 |
|---|---|---|---|---|---|
| `admin` | 전부 | 전부 | 아무 팀 | 전부 | 전부 |
| `lead` | **전부** | 같은 팀 | **자기 팀** | 같은 팀 | **전부** |
| `member` | 담당 건 + **공동 담당 건** | 같은 조건 | ✕ | ✕ | 같은 팀 |

근거는 화면이 **거짓말을 하고 있었다**는 것이다 — 팀장의 팀별 현황표가 「남의 팀 0건」으로
서는데 0은 「없다」로 읽힌다. **명부는 넓히지 않았다**: 팀장이 남의 팀 사람의 카드를 눌러
그 사람의 진행 상황을 보는 것은 그대로 막혀 있다(`members/page.tsx`의 `openable`).
`member` 줄의 공동 담당은 `ADR-041` — **이름 + 팀**으로 재고, id 컬럼을 만들지 않는다.

**뒤집어 말하면 — 데모 모드에서는 범위가 갈리지 않는다.** `?as=lead`에 붙일 팀도 구성원도
없으므로(메모리 저장소에 `profiles`·`members`가 없다) 데모에서 `?as=`가 바꾸는 것은 **섹션
배치와 민감 `extras` 마스킹**뿐이고, **범위 구분은 로그인했을 때만 일어난다.**

**결정 F — 에러 코드 `UNAUTHENTICATED`(401) 하나를 더한다. PATCH 허용 필드는 둘이다.**
`X1` 목록에 `UNAUTHENTICATED`를 넣는다. `FORBIDDEN`(403)은 이미 있고 **둘을 뭉개지 않는다** —
「로그인하세요」와 「당신은 이걸 못 합니다」는 사용자가 할 일이 정반대다.

| 코드 | 상태 | 문구 |
|---|---|---|
| `UNAUTHENTICATED` | 401 | 로그인이 필요합니다. |
| `FORBIDDEN` (기존) | 403 | 이 작업을 수행할 권한이 없습니다. |

`PATCH /api/tasks/[id]`가 받는 필드는 **`status`·`progress` 둘뿐이다**(`UC-16` 「내 업무
상태·진행률 수정」). `note`·`dueAt`·`ownerNameRaw`를 열지 않는다 — 시트가 진실의 원천이라
(`ADR-001`·`ADR-008`) 재업로드가 덮어쓸 필드를 화면에서 고치게 하면 사용자는 **자기 수정이
사라지는 것**을 본다. 되돌릴 수 있는 구현 선택이라 ADR을 만들지 않고 이 표에 남긴다.

> **2026-08-28에 셋이 됐다.** `ownerMemberId`가 더해졌다 (`ADR-035`). 위 기준은 그대로다 —
> 담당자 재지정도 「다음 업로드가 되돌린다」는 성질을 그대로 지고, 그 사실을 화면이 한 줄로
> 적는다. `ownerNameRaw`는 **여전히 클라이언트에서 받지 않는다**: 라우트가 id에서 유도한다.
>
> **2026-08-29에 업무 내용 전체로 넓혔다** (`ADR-042`). 열린 칸은 업무명·상태·진행률·우선순위·
> 리스크·승인·배정일·마감·다음 조치(셋)·지연 사유·비고 열셋 + 담당자 둘이다. 「사자가 오늘
> 바꾸는 것과 다음 업로드가 가져오는 것이 겹치는 자리인가」라는 기준은 **그대로**이고,
> 결론만 바뀌었다 — 회의 중에 마감을 옮겨 적는 일이 실제로 일어나는데 그때마다 시트를
> 왕복하는 것이 이 제품의 약속과 어긋난다. **덮어쓴다는 사실은 감추지 않고 화면이 적는다.**
> `extras`·`raw`·`source_*`는 **여전히 닫혀 있다** — 그 셋을 여는 날 이 화면은 시트 편집기가
> 된다. 같은 목록을 DB의 컬럼 GRANT가 진다 (`0013` 5절).
>
> **같은 날 `POST /api/tasks`(생성)와 `DELETE /api/tasks/[id]`(삭제)가 생겼다** (`ADR-042`).
> 둘 다 **대표·실장과 팀장만** 할 수 있고(팀장은 자기 팀), 만든 업무의 자연키는 서버가
> `manual::<uuid>`로 지어 **다음 업로드와 부딪히지 않게** 한다.

#### T8 구현 중 확정 (2026-08-27, step 12 감사)

착수 시점에 못박은 A~F는 **그대로 섰다** — 세션은 `@supabase/ssr` 쿠키이고 게이트는
`src/proxy.ts`이며, 조회는 사용자 JWT로 나가고 `service_role`은 업로드 확정·시드에만 쓰이며,
`security definer` 함수는 셋이고, 매칭 실패는 `member` 범위에서 빠지고, 데모는 인증을
요구하지 않으며, `UNAUTHENTICATED`(401)와 `PATCH` 필드 둘이 들어갔다. 구현하면서 **새로
갈린 것 넷**을 여기 잇는다.

**결정 G — `PATCH`는 없는 id에도 `403`이다. `GET`만 `404`를 유지한다.** 결정 F는 코드 둘을
가르라고만 했지 **같은 자원에서 둘이 부딪히는 경우**를 정하지 않았다. 인증된 사용자에게
`PATCH /api/tasks/[id]`는 `TASK_NOT_FOUND`를 내지 않는다 — 「그 id는 있지만 당신 것이 아니다」와
「그런 id가 없다」를 구분해 답하면 **부원이 id를 훑어 전사 업무의 존재와 개수를 셀 수 있다**
(`S6`). 읽기에서 `404`를 유지하는 것은 그쪽이 덜 흘리기 때문이다: 가리킨 것이 없다는 사실
하나만 알려주고, RLS가 범위 밖 행을 이미 `null`로 돌려주므로 두 경우는 서버에서도 같은
모양이다. 되돌릴 수 있는 구현 선택이라 ADR을 만들지 않고 `ARCHITECTURE.md`「같은 자원,
다른 코드」와 이 문단에 남긴다.

**결정 H — 로그인은 서버 액션이 아니라 라우트 핸들러다. `proxy`는 API와 화면을 다르게 막는다.**
서버 액션으로 만들면 요청 본문이 Next 내부 포맷이라 **`curl`로 세션 쿠키를 만들 수 없고**,
그러면 완료 기준 2(「`curl`로 직접 검증한다」)를 **티켓이 정한 방법으로** 증명할 수 없다.
그리고 `proxy`가 미인증을 막는 방법이 경로에 따라 갈린다 — 화면은 `307 → /login?next=…`,
`/api/**`는 **`401 JSON`**이다. `fetch`가 `302`를 따라가면 로그인 HTML을 JSON으로 파싱하려
들기 때문이다. 결정 이력은 `ADR-027`.

**결정 I — 로그인 뒤에는 범위가 먼저 잘라서 민감 `extras` 마스킹이 발동할 자리가 거의 없다.**
`S6`은 민감 키(`연락처`·`계정`·`이메일`·`전화`)를 `admin`·`lead`에게만 내려보내라고 했는데,
그 값이 든 행은 마케팅·촬영팀 것이고 **`member`는 애초에 그 행을 보지 못한다**(RLS + `scopeTasks`).
감사 실측이 그렇다 — 라이브에서 `admin`은 민감 값 4건을 받고 `lead`·`member`는 **0건**인데,
`lead`의 0건은 마스킹이 아니라 **범위**다. **마스킹을 지울 이유는 되지 않는다**: 데모
모드에는 RLS도 범위 구분도 없어서 `?as=member`가 9건을 전부 보는데, 거기서는 마스킹이 유일한
층이고 실제로 그 4건이 `null`로 내려간다. **층이 둘이고 어느 쪽도 혼자서는 부족하다.**

**결정 J — `?as=`를 막는 것은 이제 환경이 아니라 세션이다.** `S4`의 이중 차단
(`NODE_ENV === 'production' && driver !== 'memory'`)은 **그대로 남아 있지만**, 실제로 그 줄에
닿는 경우는 **미인증 상태뿐**이다. 로그인했으면 세션이 이기고(`ADR-026`), 미인증으로
보호 라우트에 오면 `proxy`가 `/login`으로 보내 그 줄까지 가지 않는다. 남는 경로는 데모·폴백
하나이고 거기서는 `?as=`가 사는 것이 의도다. **즉 `S4`는 죽은 규칙이 아니라 마지막 그물이다** —
`proxy`의 공개 목록이 늘어나면 그 자리가 다시 열린다.

#### T11 착수·구현 확정 (2026-08-27) — 상태 축이 하나 붙는다

T8까지 사람은 **역할** 하나만 가졌다. T11이 더하는 것은 축 하나다 — **승인되었는가.**
이 절은 `docs/TICKETS.md` T11과 GitHub 이슈 #29에 대응하며, **적혀 있는 것은 계획이 아니라
결과다**(구현이 끝난 뒤에 쓴다). 결정 문자는 T9가 `P`까지 썼으므로 **`Q`부터** 잇는다.

**새 축과 기존 범위 표는 이렇게 겹친다.** 아래 표는 `src/lib/domain/viewer-scope.ts`의
머리말 표와 **나란히 놓여야 한다** — 저쪽은 `status='active'`인 사람의 범위만 말하고,
이쪽은 그 앞에 상태 갈래를 얹는다.

| `status` | `role` | 볼 수 있는 것 | 화면 |
|---|---|---|---|
| `pending` | **무시된다** | **없음** | `/pending` (승인 대기 안내) |
| `rejected` | **무시된다** | **없음** | `/pending` (재요청 폼) |
| `active` | `admin` | 전부 | 지금까지와 같다 |
| `active` | `lead` | 자기 팀 | 〃 |
| `active` | `member` | 자기 업무 + **자기 팀 목표 지표** | 〃 |

「무시된다」는 화면이 숨긴다는 뜻이 아니다. `my_role()`이 `null`을 돌려주므로 **DB가 한 행도
주지 않는다**(`ADR-030`). `member`의 목표 지표만 업무와 규칙이 다른 이유는 T8 그대로다 —
`GoalMetric`에는 담당자 축이 없다.

**흐름 둘.**

```
가입 → 대기 → 승인                     거절
  /signup                               [팀원 요청] 탭에서 [거절]
    · signUp() 한 번. 앱은 profiles를 쓰지 않는다      ↓
    · 트리거가 role='member' · status='pending'   status='rejected'
    ↓                                     · members 연결은 건드리지 않는다
  /pending  (어느 경로로 들어와도 여기로 온다)    · 계정은 살아 있다
    ↓                                        ↓
  리더·admin의 [팀원 요청] 탭에 뜬다        /pending 에서 팀을 다시 골라 재요청
    ↓ 시트 담당자를 고르거나 새로 만들고 [승인]   ↓ request_join(team)
  approve_join(target, member_id | new_member_name)   status='rejected' → 'pending'
    · profiles.status = 'active'                      · 'active'로는 절대 못 간다
    · members.auth_user_id = 그 계정   ★ 같은 트랜잭션
    ↓
  평범한 member 화면. 이후로는 그냥 로그인한다
```

**결정 Q — 승인은 `members` 연결과 같은 자리에서 일어난다. 나중으로 미루지 않는다.**
`approve_join`은 `profiles.status='active'`와 `members.auth_user_id` 갱신을 **한 함수 안에서**
한다. 리더는 승인할 때 **시트 담당자를 반드시 고른다** — 후보 드롭다운에서 고르거나
(`member_id`), 없으면 이름을 적어 새 행을 만든다(`new_member_name`). 둘 중 **정확히 하나**가
아니면 예외다.
**이것이 안 되면 승인된 사람이 자기 업무 0건인 화면을 본다.** `member` 범위는
`tasks.owner_member_id = my_member_id()`이고, `my_member_id()`는 `members.auth_user_id`가
붙은 행에서만 나온다. 상태만 `active`로 바꾸고 연결을 미루면 그 사람은 **로그인은 되는데
아무것도 없는** 화면을 보고, 그것은 대기 화면보다 나쁘다 — 대기 화면은 무엇을 기다리는지
말하지만 빈 대시보드는 아무 말도 하지 않는다. **다음 사람이 이 자리를 「나중에 자동으로
되겠지」라고 읽지 않도록 적어 둔다: 자동으로 되지 않는다.** 시트 담당자는 자유 입력 문자열이라
(`ADR-001`) 이름만으로는 계정과 이어지지 않고, 그 판단은 사람만 할 수 있다.
연결이 남의 것을 빼앗지 못하게 셋을 막는다 — 대상과 **같은 팀**의 행이어야 하고, 이미 다른
계정에 붙은 행이면 예외이며, 새로 만들 때 `unique (team_id, name)`에 걸리면 조용히 기존 행을
쓰지 않고 그대로 예외를 올린다.
**승인은 승격이 아니다** — `approve_join`은 `role`을 건드리지 않는다.

**결정 R — 대기 판정은 `proxy`가 아니라 `lib/auth/pending-gate.ts`가 진다.**
`proxy`는 여전히 **DB를 조회하지 않는다**(T8 그대로). 대기 여부는 `profiles` 행을 읽어야 알고
그 조회는 `resolveSession`이 자기 자리에서 이미 한다. 그래서 `route-guard.ts`(「로그인 없이
열려 있는가」)와 `pending-gate.ts`(「로그인은 했는데 범위가 없는 사람이 지나갈 수 있는가」)를
**합치지 않았다** — 두 함수가 아는 것이 다르다.

```
ok · anonymous                        → allow   앞단이 이미 처리한 상태다
/pending 또는 그 아래                  → allow   ★ 자기를 막으면 리다이렉트 고리가 된다
/api/auth/** (로그아웃·재요청)          → allow   나갈 문을 막으면 계정이 갇힌다
pending·rejected·no_profile + /api/**  → deny    403 PENDING_APPROVAL
pending·rejected·no_profile + 그 밖     → redirect /pending
```

**`no_profile`을 같은 갈래에 태운다.** 트리거가 어떤 이유로 실패해 `profiles` 행이 없는 계정은
T8까지 「부원인데 아무것도 없는」 화면에 갇혀 있었다. `/pending`이 그 계정에도 할 말을 갖는다.
`route-guard`의 공개 목록에 더한 것은 **`/signup` 하나뿐**이다 — `/api/auth/signup`은 기존
`/api/auth` 접두사에 이미 걸리고, **`/pending`은 공개가 아니다**(대기 사용자는 로그인한
상태다. 공개로 두면 로그아웃 상태에서도 열리고 `proxy`가 세션 갱신을 건너뛴다).

**결정 S — `PENDING_APPROVAL`(403)을 더한다. `UNAUTHENTICATED`로 대신할 수 없다.**
승인을 기다리는 사람은 **이미 로그인했다.** 401을 주면 화면이 로그인 폼을 다시 띄우고 그
사람은 같은 계정으로 다시 들어와 같은 화면을 본다. `FORBIDDEN`과 갈라 두는 것도 사용자가 할
일이 다르기 때문이다 — 「당신은 이걸 못 합니다」는 끝난 이야기이고 「승인을 기다린다」는
기다리면 바뀐다. 문구는 「아직 승인되지 않은 계정입니다. 승인 후에 이용할 수 있습니다.」다.
`X1` 목록이 이 코드로 **18개**가 됐다.

**결정 T — 상태 변경 `POST`는 출처(`Origin`)를 본다. 다만 `Origin`이 없으면 통과시킨다.**
규칙은 둘뿐이다: **없으면 통과, 있는데 다르면 거부.** 걸린 라우트는 일곱이다 —
`login` · `logout` · `signup` · `rejoin` · 승인 · 거절 · 승격.
없으면 통과시키는 근거는 `TICKETS.md` T8 완료 기준 2가 「`curl`로 직접 검증한다」를 명시하고
**`curl`은 `Origin`을 붙이지 않는다**는 것이다 — 「없으면 거부」로 조이면 방어 하나를 얻고
**그 방어를 확인할 방법을 잃는다.** 그러고도 CSRF는 막힌다: 브라우저는 cross-site `POST`에
언제나 `Origin`을 붙이고, 폼에도 `fetch`에도 그것을 지울 수단이 없다. 빈 문자열과 문자열
`"null"`(샌드박스 iframe)은 「없음」이 아니라 **거부**다. `x-forwarded-host`는 보지 않는다 —
프록시가 겹쳐 쓰지 않는 배치에서는 요청자가 정할 수 있는 값이라 대조 기준이 되지 못한다.
헤더 이름을 아는 자리는 `lib/api/same-origin.ts`의 `requestIsSameOrigin` **하나**다.

**결정 U — 데모 모드에 가입 화면이 뜨지만, 가입은 되지 않는다.** 이슈 #29의 착수 초안은
「데모·폴백 모드에는 가입 화면이 없다」였는데, 실제로는 **화면을 감추지 않았다.**
`route-guard`가 데모에서 모든 경로를 열기 때문에(`ADR-026` 결정 E) `/signup`도 열리고, 폼을
보내면 라우트가 **자격증명이 없어** `?error=unavailable`(「지금은 가입할 수 없습니다」)로
되돌린다. 화면 하나를 조건부로 감추는 코드를 더하는 것보다, **붙을 Auth 서버가 없다는 사실을
서버가 말하게** 두는 편이 규칙이 적다 — 감추면 「왜 데모에서만 링크가 없나」를 설명하는 자리가
`route-guard`·사이드바·로그인 화면 셋으로 늘어난다. `?as=` 규칙은 **한 줄도 바뀌지 않았다**:
세션이 있으면 세션이 이기고(`ADR-026`), 대기·거절 세션은 `status !== 'ok'`라 `?as=admin`으로도
`member`를 넘지 못한다.

**`task_events`가 0행인 것이 이 티켓의 함정이다.** 지금 보고서의 「변경 건수 0」에는 **두 사실이
겹쳐 있다** — (a) 읽을 길이 없어 `events: []`를 넘긴다, (b) 원격에 이력이 실제로 0행이다.
step 1~4가 (a)를 없애도 **숫자는 여전히 0으로 나온다.** 0행인 이유는 확정이 멱등이라 같은
시트를 다시 올리면 전건 `unchanged`가 되고 이벤트가 0건이기 때문이다(`UC-03`·`X4`). 그러니
step 9의 감사는 **이력을 먼저 만들어 놓고**(값을 바꾼 시트를 올려 `updated`를 내고) 재야 하며,
그러지 않으면 「고쳤는데 0이니 안 고쳐진 것」이라고 오판한다. **0을 보고 되돌리지 마라.**

**결정 K — `task_events`는 자기 정책을 갖지 않는다. 부모 `tasks` 정책을 다시 탄다.**
`0003_auth_rls.sql`의 `task_stages_select_via_task`와 **같은 모양**이다.

```sql
create policy task_events_select_via_task on task_events
  for select to authenticated
  using (exists (select 1 from public.tasks t where t.id = task_events.task_id));
```

#### 🔴 A1. 집계를 SQL로 할지 앱에서 할지가 모순돼 있다

6장은 `summarizeTeam(tasks[], ctx)`를 **순수 함수**로 두는데, 예시 이슈 BE4는 "집계 쿼리 로직"이고 Supabase 선택지 설명에도 "집계 SQL"이 있었다. T4에서 SQL 집계를 짜면 **메모리 구현과 결과가 갈라지고 "같은 계약 테스트 통과"가 깨진다.**

**확정**: 집계는 **전부 `src/lib/domain/`의 JS 순수 함수**로 한다. 리포지토리는 CRUD와 필터링된 조회만 담당한다.

```
TaskRepository        (저장/조회만)          domain/           (판정/집계만)
  listTasks(filter)   → Task[]        →      summarizeTeam(tasks, ctx)
  getTask(id)         → Task          →      buildKpiStrip(tasks, ctx)
  upsertTasks(tasks)                  →      collectAlerts(tasks, ctx)
  listStages(taskIds) → Stage[]
```

근거: 조직 전체 업무가 **수백~수천 행 규모**다. 이 크기에서 SQL 집계의 이점은 없고, 두 구현의 결과 일치를 보장하는 값이 훨씬 크다. 행이 수만을 넘어가면 재검토한다 — 그 시점은 이 과제 범위 밖이다.

#### 🔴 A2. Supabase→메모리 자동 폴백이 쓰기를 삼킨다

9장의 자동 폴백은 조회에는 안전하지만, T8의 `PATCH /api/tasks/[id]`(부원이 본인 상태 수정)가 폴백 중에 들어오면 **메모리에 쓰이고 재시작 시 소실된다.** 사용자는 저장됐다고 믿는다. 조용한 데이터 유실이다.

**확정**: 폴백은 **읽기 전용**이다.
- 폴백 상태에서 모든 쓰기 경로(업로드 확정, PATCH)는 `503 + "읽기 전용 모드입니다"`를 반환하고 UI는 편집 버튼을 비활성화한다.
- 배너 문구도 "데모 데이터 모드"가 아니라 **"읽기 전용 — 저장소 연결 실패"**로 구분한다. 의도된 데모 모드(`STORAGE_DRIVER=memory`)와 사고를 섞으면 안 된다.

**후속 (T9 step 7에서 확정) — 폴백이 걸리는 조건을 좁혔다. 걸렸을 때의 규칙은 그대로다** (`ADR-029`).
`STORAGE_DRIVER`를 정하지 않았고 Supabase 키가 **하나도** 없으면 `demo`다. `.env` 없이 클론한
심사자에게 이 경로가 지금까지 **사고 배너와 `503`**을 보여 주고 있었고, 그래서 「성공 기준 1번」이
문서로만 성립했다 (실측은 `TICKETS.md` T9「키 없는 클론 실측」). 붙어 볼 저장소가 없는 환경에는
**유실될 실데이터가 없으므로** 이 조항이 지키려던 것이 없다. `STORAGE_DRIVER=supabase`라고 적어
두고 키가 없거나, 키가 **일부만** 있는 경우는 **그대로 사고**이며 위 두 줄이 한 글자도 바뀌지 않고
적용된다.

#### 🔴 A3. 서버 컴포넌트 / API 라우트 경계가 정의돼 있지 않고, CLAUDE.md CRITICAL 규칙과 충돌한다

계획엔 API 9종과 서버 컴포넌트 페이지가 둘 다 있는데 **누가 무엇을 쓰는지가 없다.** 서버 컴포넌트에서 자기 API를 `fetch`하면 불필요한 HTTP 왕복이 생긴다(Next.js 흔한 안티패턴).

게다가 `CLAUDE.md`의 CRITICAL 규칙 **"모든 API 로직은 `src/app/api/` 라우트 핸들러에서만 처리할 것"**을 문자 그대로 지키면 서버 컴포넌트가 `lib/store`를 직접 못 읽는다. 규칙과 설계가 충돌한다.

**확정 — 경계 규칙:**

```
서버 컴포넌트 (page.tsx)  ──직접──▶  lib/store · lib/domain     ← HTTP 왕복 없음
                                          │
클라이언트 컴포넌트         ──HTTP──▶  app/api/**  ──▶  lib/…
(업로드·PATCH·리프레시·필터)
```

- 초기 렌더 데이터는 서버 컴포넌트가 `lib/`를 **직접 호출**한다.
- API 라우트는 **클라이언트에서 발생하는 상호작용**(파일 업로드, 상태 수정, 외부 소비)만 담당한다.
- `T0`에서 CLAUDE.md의 해당 CRITICAL 규칙을 다음으로 교체한다:
  > CRITICAL: 비즈니스 로직은 `src/lib/`에만 둔다. 라우트 핸들러와 서버 컴포넌트는 `src/lib/`를 호출만 하고 계산하지 않는다. 서버 컴포넌트는 자기 API 라우트를 fetch하지 않는다.

#### 🟡 A4. ExcelJS가 20개월째 정체돼 있다

확인 결과: **`exceljs@4.4.0`, 최종 수정 2024-12-20** (오늘 기준 약 20개월). 의존성 9개 — `unzipper@0.10`, `uuid@8`, `archiver@5`, `saxes@5`, `jszip`, `fast-csv` 등 오래된 트리다. `4.4.1-prerelease.0`이 있으나 정식 릴리스는 없다.

### 🔴 E1. 실제 시트에 "유령 행" 25개가 있다 — 확인된 사실

`02_촬영·기획팀` 탭의 빈 행 25개를 실제로 열어보니, **업무ID·프로젝트명은 비어 있는데 수식이 만든 값이 25개 컬럼에 들어차 있다.**

```
| (업무ID 빈칸) | (프로젝트명 빈칸) | … | FALSE | FALSE | FALSE | … |
  1900. 01. 01. | … | 1899. 12. 31. | … | 0% | … | FALSE | FALSE |
```

- `1900. 01. 01.` / `1899. 12. 31.` — 빈 셀에 걸린 날짜 수식이 엑셀 시리얼 0·1로 떨어진 것 (각 25회 등장)
- `FALSE` — 불리언 수식 결과
- `0%` — 진행률 수식 결과

**"셀에 값이 있으면 데이터 행"이라는 흔한 판정을 쓰면 유령 태스크 25건이 생긴다.** 그러면 전체 활성 업무가 1이 아니라 26이 되고, 완료율이 바닥으로 떨어지고, **1900년 기한의 "지연" 업무 25건**이 대시보드를 덮는다. 대시보드가 통째로 무의미해진다.

**확정 — 행 판정은 신원 컬럼으로만 한다:**

```
isDataRow(row) = 신원 컬럼(업무명·프로젝트명 / 담당자) 중 하나 이상에 실제 값이 있다
                 ※ 수식 결과 컬럼은 판정에 쓰지 않는다
```

추가로 `cell-normalizer`가 **1900-01-01 이전 날짜를 전부 null로** 떨어뜨린다 (엑셀 시리얼 0/1 아티팩트). T3 완료 기준에 "픽스처의 유령 행 25건이 태스크로 생성되지 않는다"를 넣는다.

### E2. ExcelJS `cell.value`는 최소 8가지 모양으로 온다

`00_통합 대시보드` 탭은 KPI가 전부 **수식**이고, `01_편집팀`에는 Google Docs·Canva **하이퍼링크** 셀이 있다. 원시값만 기대하면 `[object Object]`가 그대로 저장된다.

| 셀 종류 | `cell.value` 형태 | 처리 |
|---|---|---|
| 숫자·문자열 | 원시값 | 그대로 |
| 날짜 | `Date` | KST 기준 `YYYY-MM-DD` |
| **수식** | `{ formula, result }` | **`result`를 쓴다** (`result`도 `Date`·`richText`일 수 있어 재귀로 푼다) |
| **수식 (결과 없음)** | `{ formula }` — `result` 키 자체가 없다 | null + warning |
| **공유 수식** | `{ sharedFormula, result? }` | 위 두 줄과 동일 |
| **하이퍼링크** | `{ text, hyperlink }` | `text`는 값, `hyperlink`는 별도 필드 |
| 리치텍스트 | `{ richText: [...] }` | 조각을 이어붙임 |
| 오류 | `{ error: '#REF!' }` | null + warning |

`cell-normalizer.ts`가 이 8가지를 **전부** 처리하고, 각각 테스트를 쓴다. 미처리 형태가 오면 `warnings`에 기록하고 null로 떨어뜨린다 — 절대 `String(value)`로 뭉개지 않는다.

**아래 두 줄은 실측으로 추가됐다** — 최초본은 `{formula, result}`만 알고 있었는데, `01_편집팀`의 KPI 행과 데이터 행에 `result` 키가 아예 없는 `{ formula }`와 공유 수식 슬레이브 `{ sharedFormula: 'C10' }`이 실제로 있었다. `value.result`를 그냥 읽으면 `undefined`가 아래로 흐르고, `String(value)`로 뭉개면 `[object Object]`가 저장된다. 둘 다 실제로 일어난다.

### E3. 퍼센트는 0.66으로 저장된다

엑셀에서 `66%`는 셀 값이 **`0.66`**이다. 그대로 `progress`에 넣으면 전 조직 진행률이 1% 미만으로 표시된다. 서식이 percent면 ×100, 이미 정수(0~100)면 그대로 — **두 경우를 서식으로 구분**하고 양쪽 테스트를 쓴다.

### E4. KST 날짜 계산

서버가 UTC로 돌면 `new Date().toISOString().slice(0,10)`은 **KST 00:00~09:00 구간에서 하루 전 날짜**를 준다. D-DAY·마감 임박·지연 판정이 전부 하루씩 어긋난다.

**확정**: `today`는 `Asia/Seoul` 기준으로 산출하는 함수 하나(`lib/domain/kst-today.ts`)를 두고, 모든 도메인 함수는 이 값을 **인자로 주입**받는다. 도메인 함수 안에서 시간을 읽지 않는다.

### E5. `source_key` 충돌은 조용히 덮어쓴다

업무ID가 없는 탭은 `slug(업무명)+담당자`가 키다. 같은 팀에 동명 업무가 두 건이면 **한 건이 다른 건을 덮어쓰고 아무도 모른다.** 미리보기의 "신규 N건"은 오히려 *줄어들어서* 감지가 더 어렵다.

**확정**: 파싱 단계에서 키 중복을 직접 검출해 **"중복 키 N건"을 경고로 따로 표시**한다. 자동 병합하지 않고 사람에게 보여준다.

### 보안

#### 🔴 S1. 수식 주입 — 우리가 만든 xlsx가 무기가 될 수 있다

**이게 가장 위험하다.** `/extract`가 만든 배정표 xlsx는 **조직 사람들에게 배포되는 파일**이다. 독스 본문의 값이 그대로 셀에 들어가는데, `=`·`+`·`-`·`@`·탭·개행으로 시작하는 문자열은 엑셀이 **수식으로 해석**한다. `=cmd|'/c calc'!A1` 같은 값이 문서에 있으면 받는 사람 PC에서 실행된다.

**확정 — 양방향 처리:**
- **쓰기**: 모든 문자열 셀을 명시적으로 텍스트 타입으로 넣고, 위험 문자로 시작하면 `'` 프리픽스를 붙인다. `assignment-writer.ts` 한 곳에서 강제한다.
- **읽기**: 수식 셀은 `result`만 쓰고 `formula` 문자열은 **저장하지도, 화면에 렌더하지도 않는다.**

#### 🔴 S2. 압축 폭탄 (zip bomb)

`.xlsx`와 `.docx`는 둘 다 ZIP이다. **수십 KB 파일이 수 GB로 팽창**할 수 있고, 서버가 OOM으로 죽는다. 4MB 업로드 제한은 **압축된 크기**만 막을 뿐 이걸 못 막는다.

**확정 — 3중 상한:**
```
압축 해제 총량      ≤ 50MB       (ZIP 중앙 디렉토리가 신고한 값. 압축을 풀지 않고 읽는다)
ZIP 엔트리 수       ≤ 512
시트 수             ≤ 20
셀 수/시트          ≤ 100,000    ※ `dimensions` 사각형 기준 (T5 확정)
셀 수/워크북        ≤ 300,000    ※ 같은 기준. 시트당 상한만으로는 20 × 100,000이 통과한다
파싱 타임아웃        8초          (Vercel 함수 타임아웃보다 짧게)
```
초과 시 파싱을 **중단하고 명확한 에러**를 낸다. 부분 결과를 저장하지 않는다.

**⚠ 실측 판정 (T1)** — 근거: `scripts/smoke/RESULT.md`「S2 한도 판정」

- **시트 수 ≤ 20 — PASS.** 실측 5개다.
- **셀 수 — 원래 문구(`행 × 열`)대로 세면 FAIL이다.** `00_통합 대시보드`의 `rowCount × columnCount`가 **26,026**으로 20,000을 넘어 **정상 업무 파일이 압축 폭탄으로 오탐되고 `ARCHIVE_LIMIT_EXCEEDED`로 거부된다.** 원인은 데이터가 아니라 내보내기 형식이다 — 이 시트의 `dimensions`는 `A1:J60`(600셀)인데 Google Sheets가 기본 1000행 그리드를 통째로 내보내고 ExcelJS의 `rowCount`가 서식만 있는 행까지 세서 `rowCount`가 1001이 된다. 값이 있는 셀은 144개뿐이다.
- 같은 파일을 다른 기준으로 재면 최대 시트 값이 갈린다 — 값 있는 셀 **1,565**(PASS, 7.8%) / `dimensions` 사각형 **4,260**(PASS, 21.3%) / `rowCount × columnCount` **26,026**(FAIL, 130%). `02_촬영·기획팀`의 72컬럼은 세 기준 어디서도 문제가 아니다. 걸리는 건 대시보드 탭의 빈 행 패딩 하나뿐이다.
- **따라서 원래의 "행 × 열 ≤ 20,000 셀/시트"는 그대로 쓸 수 없다.** T5 착수 전에 (a) 세는 기준을 `dimensions` 사각형 또는 값 있는 셀로 바꾸거나 — 실측 여유가 각각 4.7배·12.8배지만 압축 폭탄이 `dimensions`를 위조할 수 있어 방어 강도는 `row×col`보다 약하다 — (b) `row×col`을 유지하되 상한을 올리거나(Google Sheets 기본 그리드 1000행 × 26열 = 26,000을 감안하면 최소 5만 이상) 해야 한다. 실측이 뒷받침하는 조합은 **(a)+(b)** 다. **최종 숫자는 T5에서 방어 로직과 함께 확정한다** (`TICKETS.md` T5 완료 기준 6과 함께 고친다).

**✅ T5 확정 — `dimensions` 사각형 기준, 시트당 100,000 / 워크북 300,000.** 위 실측 기록은
왜 숫자가 바뀌었는지의 근거이므로 남긴다. T1이 권한 **(a)+(b) 조합**을 그대로 택했다.

- **세는 기준은 (a) `dimensions` 사각형이다.** `workbook-reader.ts`가 이미 `worksheet.dimensions`로
  `SheetGrid.rowCount × columnCount`를 잡고 있으므로 새로 세는 코드가 필요 없다.
  ExcelJS의 `worksheet.rowCount`(서식만 있는 행까지 세는 값)는 쓰지 않는다 — 그것이 26,026 오탐의 원인이다.
- **상한은 (b) 상향한다.** 시트당 100,000은 실측 최대 시트(`02_촬영·기획팀` 4,260셀)의 23배이고,
  **Google Sheets 기본 그리드 1000행 × 26열 = 26,000**보다 위다. 한 탭만 내보낸 파일이 빈 그리드를
  통째로 달고 와도 통과해야 한다. 20,000은 이 선 아래라 처음부터 성립하지 않았다.
- **워크북 합계 300,000을 따로 둔다.** 시트당 상한만 두면 20시트 × 100,000 = 2,000,000셀이 통과하고,
  셀 하나가 객체 하나라 그 지점에서 메모리가 죽는다. 실측 워크북 전체는 같은 기준으로 8,732셀이다.
- **`dimensions`는 워크북 안의 XML 속성이라 위조할 수 있다.** 그래서 이 상한 하나에 기대지 않는다 —
  압축 해제 총량 50MB와 압축본 4MB 상한(**팽창비 12.5:1**)이 위조된 `dimensions`를 뒷받침할 실제
  바이트가 존재하지 않게 만든다. (a)의 약한 방어 강도를 (b)가 아니라 **바이트 상한이** 메운다.
- 구현은 `src/lib/upload/upload-limits.ts`(상수)·`zip-inspector.ts`(중앙 디렉토리만 읽음)·`upload-guard.ts`(판정).

#### 🟡 S3. 매직넘버만으로는 xlsx와 docx를 구분 못 한다

계획의 "매직넘버 검증"은 불충분하다. **둘 다 `PK\x03\x04`(ZIP)로 시작**한다. `.docx`를 `/upload`에, `.xlsx`를 `/extract`에 넣으면 매직넘버 검사를 통과하고 파서가 예상 못 한 지점에서 터진다.

**확정**: ZIP 내부 엔트리로 판별한다 — `xl/workbook.xml`이 있으면 xlsx, `word/document.xml`이 있으면 docx. 확장자·MIME·매직넘버는 **1차 필터일 뿐** 최종 판별은 내부 구조로 한다.

#### 🔴 S4. `?as=` 역할 전환이 프로덕션에 나가면 인증 우회다

T6에서 넣기로 한 `?as=admin`은 **URL만 치면 관리자가 되는 기능**이다. T8에서 인증을 붙인 뒤에도 남아 있으면 완전한 권한 우회다.

**확정 — 이중 차단:**
```
if (process.env.NODE_ENV === 'production' && driver !== 'memory') → ?as= 무시
```
즉 **메모리 드라이버에서만** 동작한다. Supabase에 붙는 순간 자동으로 죽는다. T8 완료 기준에 "프로덕션 빌드 + Supabase 연결 상태에서 `?as=admin`이 무시된다"를 명시한다.

**T8에서 규칙이 한 줄 늘어난다** (「8. 권한」의 결정 E·`ADR-026`). 위 이중 차단은 그대로 남고,
그 **앞에** 세션 갈래가 붙는다.

```
세션이 있으면              → 세션의 role이 이긴다. ?as=는 무시된다 (개발 환경에서도)
세션이 없고 프로덕션+실저장소 → member                (위 규칙 그대로, S4)
세션이 없고 데모·폴백        → ?as= 해석              (위 규칙 그대로, ADR-013)
```

「프로덕션에서만 무시」로 두면 개발 서버에서 로그인한 `member`가 `?as=admin`으로 남의 팀을
읽는다. **세션이 있는데 URL이 이기는 경우는 없다.**

#### 🟡 S5. 키 관리와 RLS 함정 두 가지

- **`service_role` 키에 `NEXT_PUBLIC_` 접두사를 붙이면 브라우저에 그대로 노출된다.** 이건 실제로 가장 흔한 Supabase 사고다. → ESLint 규칙 또는 CI 스크립트로 `NEXT_PUBLIC_.*SERVICE_ROLE` 패턴을 **빌드 실패**로 막는다.
- **`security definer` 함수는 `search_path`를 고정하지 않으면 권한 상승 경로가 된다.** A2에서 정한 `my_role()`·`my_team()`에 반드시 `set search_path = ''`를 붙이고 스키마를 명시적으로 적는다.

#### 🟡 S6. `raw`·`parse_result`에 개인정보가 통째로 들어간다

시트에는 **실명, 출연자 연락처(내부용), 문의자 SNS 계정**이 있다. 설계상 `tasks.raw jsonb`가 원본 행을 통째로 보관하고 `uploads.parse_result`도 마찬가지다. `tasks` SELECT 권한이 전원에게 열려 있으므로(A1) **부원 누구나 API로 연락처를 긁을 수 있다.**

**확정:**
- `GET /api/tasks`는 **`raw`를 절대 직렬화하지 않는다.** 응답 스키마에서 제외 (zod로 강제).
- `extras` 중 민감 키(`연락처`, `계정`, `이메일`, `전화`)는 **admin·lead에게만** 내려보낸다. 키 이름 패턴 기반 마스킹 목록을 `lib/domain/`에 둔다.
- 확정 후 `parse_result`는 비운다(A8과 동일 조치).
- **에러 메시지·로그에 셀 값을 담지 않는다.** 위치(`시트명!행:열`)와 사유만 남긴다.

#### 🟡 S7. 하이퍼링크 셀의 `javascript:` 스킴

`01_편집팀`에는 URL 셀이 실제로 있다. 사이드 패널에서 `<a href={hyperlink}>`로 렌더하면 `javascript:` URL이 XSS가 된다.

**확정**: `http`·`https`만 허용하는 스킴 검사를 통과한 링크만 앵커로 렌더하고, 나머지는 **텍스트로만** 표시. 외부 링크에는 `rel="noopener noreferrer"`.

React가 기본 이스케이프하므로 태스크 제목·비고의 XSS 위험은 낮다. 단 **주간 브리핑 마크다운을 HTML로 렌더하게 되면** 그때 sanitize가 필요하다 — 현재 계획은 "복사"만이라 해당 없음. 렌더로 바꾸면 재검토.

### 에러 핸들링

#### X1. 에러 코드 체계

`{ error: { code, message } }`만 있고 코드 목록이 없었다. 확정:

```
FILE_TOO_LARGE · FILE_TYPE_MISMATCH · ARCHIVE_LIMIT_EXCEEDED · PARSE_TIMEOUT
WORKBOOK_CORRUPT · NO_KNOWN_TAB · SETTINGS_TAB_MISSING
DOCUMENT_CORRUPT · NO_OUTLINE_TASK
UPLOAD_NOT_FOUND · UPLOAD_ALREADY_COMMITTED · TASK_NOT_FOUND
STORAGE_READONLY · STORAGE_UNAVAILABLE · FORBIDDEN · VALIDATION_FAILED
```

`message`는 **사용자에게 보여줄 한국어 문장**이고, 스택·내부 경로·셀 값을 담지 않는다.

#### X2. 실패 강도 3단계 — 뭉개지 말 것

| 강도 | 예 | 동작 |
|---|---|---|
| **경고** (진행) | 미등록 enum, 담당자 오타, 날짜 파싱 실패 1건 | 값 보존 + `warnings[]`, 미리보기에 표시, 확정 가능 |
| **부분 실패** (진행) | 탭 하나 판별 실패 | 해당 탭만 건너뛰고 나머지 확정. **어떤 탭이 빠졌는지 명시** |
| **중단** (불가) | 아카이브 한도 초과, 워크북 손상, 타임아웃 | 저장소 무변경, 코드+사유 반환 |

**중요**: "알려진 탭이 하나도 없음"은 중단이다. 빈 결과를 성공으로 처리하면 **기존 데이터가 0건으로 덮이는** 최악의 사고가 난다. 부분 업로드를 지원하기 때문에 이 구분이 더 중요하다.

#### X3. 빈 상태 ≠ 에러 상태

계획엔 빈 상태만 있었다. 셋을 구분한다:

```
데이터 없음      → "아직 데이터가 없습니다"  [샘플 불러오기] [시트 업로드]
저장소 연결 실패  → "읽기 전용 — 저장소 연결 실패"  배너 + 편집 비활성 (A2)
조회 실패        → error.tsx 바운더리 + [다시 시도]
필터 결과 0건    → "조건에 맞는 업무가 없습니다"  [필터 초기화]
```

Next.js `error.tsx`를 `app/`과 `app/teams/`에 둔다. 하나 터졌다고 전체 화면이 백지가 되면 안 된다.

#### X4. 업로드 실패의 되돌림

`committing` 중 실패하면 **일부만 반영된 상태**가 남는다. 4MB 규모에서 트랜잭션을 감당할 수 있으므로 upsert를 **단일 트랜잭션**으로 묶는다(메모리 드라이버는 스냅샷 후 교체). 실패 시 `previewing`으로 되돌아가 재시도 가능 — 이미 상태 전이도에 있는 경로다.

**후속 (T5 step 4에서 확정) — 두 구현의 원자성이 다르다. 이름으로 감추지 않는다.**

- **메모리 드라이버는 원안 그대로 스냅샷-교체**다. 내부 배열을 깊은 복사해 두고 확정 도중
  예외가 나면 호출 전 상태로 되돌린다 (`TaskRepository.runAtomically?`). 실제 원자성이다.
- **Supabase는 원자적이지 않다.** `supabase-js`에 트랜잭션 API가 없어 `tasks` upsert ·
  `goal_metrics` upsert · 단계 교체 · 이벤트 insert가 각각 별개의 왕복이다. 진짜 트랜잭션을
  걸려면 Postgres 함수(RPC)를 새로 만들어야 하는데, 그 길은 (a) `ADR-006`이 SQL로 밀어내지
  않기로 한 로직을 SQL로 되돌리고 (b) 새 마이그레이션 적용이라는 **사용자 개입**을 만든다.
  그래서 지금은 **멱등 재시도**로 대신한다 — 실패하면 `parse_result`를 남긴 채 `failed`로
  두고, 같은 입력으로 다시 확정하면 정확히 같은 결과에 수렴한다.
- **멱등이 성립하는 근거**: upsert 키가 `(team_id, source_key)`이고, 단계는 통째 교체이며,
  이벤트는 `updated`인 건에만 생긴다. 두 번째 시도에서 이미 반영된 건은 `unchanged`가 되고
  `last_progress_at`도 움직이지 않는다. 재시도 경로(`committing → failed → previewing`)는
  이미 상태 전이도에 있다.
- **후속 경로**: 부분 반영이 실제로 문제를 일으키면(확정 도중 실패가 관측되거나 확정 규모가
  커지면) 확정 경로를 **RPC로 승격**한다. 그때는 `ADR-006`을 먼저 고쳐 "확정 한 경로만
  예외"임을 명시한다 — 집계를 SQL로 되돌리는 것이 아니다.
