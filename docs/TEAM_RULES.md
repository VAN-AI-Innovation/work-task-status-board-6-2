# VAN AI Innovation 협업 규칙

학회(https://github.com/VAN-AI-Innovation)에서 공지한 규칙을 정리한 문서다.
원문은 노션의 **「스프린트 매니저 사용 방법」**, **「Git 협업 가이드라인」** 두 페이지.

> 공지 원문: "1. 스프린트 매니저 사용 필수 — 작업 관리는 반드시 스프린트 매니저를 통해서 진행.
> 2. 노션 및 Git 가이드라인 숙지 — 노션에 업로드된 프로젝트 설정 내용과 'Git 협업 가이드라인'을
> 작업 전에 반드시 꼼꼼하게 정독."

---

## 1. 이 프로젝트에서 확정된 사항

원문 두 문서가 서로 어긋나는 부분이 있어, 운영진 안내와 갠플(개인 프로젝트) 조건에 맞춰 확정한 값이다.

| 항목 | 확정값 | 근거 |
|---|---|---|
| 브랜치 전략 | `feature` → **`main` 직접 PR** (dev 없음) | 운영진 안내: "갠플이니 dev 없이 main으로 바로 PR 가능. 충돌을 완전히 배제하려면 dev→main 추천" → 갠플이라 병렬 충돌이 없어 dev 생략 |
| 브랜치 명명 | `type/#number` (예: `feat/#12`) | Git 협업 가이드라인 5장 공식 표기 |
| 리뷰 | **셀프 리뷰** 후 머지 | 갠플이라 "최소 1명 승인"이 불가능. 스프린트 매니저 요약 체크리스트의 "리뷰 승인(또는 셀프 리뷰)" 적용 |

## 2. Git 협업 가이드라인

### 2.1 브랜치

- `main` — 실제 배포 기준 브랜치. **항상 배포 가능한 안정 상태** 유지.
- `feature` — 기능 개발·버그 수정 등 개별 작업 단위. 작업 완료 후 PR로 병합.
- `dev` — 여러 feature를 통합해 검증하는 브랜치. **이 프로젝트에서는 사용하지 않는다** (위 확정 사항 참고).

명명 규칙: `type/#number` — `feat/#1`, `fix/#22`

### 2.2 작업 프로세스

1. **Issue 생성** — 작업 시작 전 이슈를 발행해 작업 내용을 정의
2. **Branch 생성** — `main`에서 최신 코드를 pull 받은 후 feature 브랜치 생성
3. **Commit & Push** — 작업 단위별로 커밋 규칙을 지켜 커밋하고 원격에 push
4. **Pull Request 생성** — 작업 완료 시 `main`으로 PR
5. **Review & Merge** — 리뷰(셀프 리뷰) 후 `main`에 merge. **머지 후 브랜치는 삭제**

### 2.3 커밋 메시지 컨벤션

형식: `{type}: {Description}` — 제목만으로도 변경 내용을 알 수 있게.

| Type | 설명 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 (README, 위키 등) |
| `style` | 코드 의미에 영향을 주지 않는 변경 (세미콜론, 포맷팅 등) |
| `refactor` | 코드 리팩토링 |
| `test` | 테스트 코드 추가 및 수정 |
| `chore` | 빌드 업무, 패키지 매니저 설정 등 기타 작업 |

### 2.4 Pull Request 규칙

- 제목: `[Type] 작업 요약` (예: `[Feat] 카카오 로그인 기능 구현`)
  - 커밋은 소문자 `feat:`, PR 제목은 대괄호 `[Feat]` — 형식이 다르니 주의.
- 본문 필수 포함 항목:
  - 변경 사항에 대한 간략한 설명
  - 관련 Issue 번호 (`#이슈번호`)
  - 테스트 통과 여부 및 스크린샷 (UI 변경 시)

### 2.5 브랜치 보호

- 🚫 `main` 브랜치로의 **직접 push 절대 금지**
- ✅ 모든 코드는 반드시 Pull Request를 거쳐야 머지 가능

> **적용 시점 (2026-08-13 운영진 확인)**
> Q. 기본적인 프로젝트 구조와 프로젝트 계획 문서들도 PR을 따로 올려야 하나요?
> 아니면 이런 기본 틀과 문서는 main에 푸시하고 이후 본격 이슈와 작업들부터 PR 올리면 되나요?
> **A. 후자.**
>
> 즉 아래 두 가지는 `main`에 직접 push한다:
> - 프로젝트 초기 스캐폴딩 (설정 파일, 하네스, 가드레일, README 등 기본 틀)
> - 프로젝트 계획·규약 문서 (`docs/PLAN.md`, `docs/TEAM_RULES.md` 등)
>
> **본격적인 작업 티켓부터는 예외 없이** 이슈 발행 → `type/#번호` 브랜치 → PR → 셀프 리뷰 → 머지를 따른다.
> 이 프로젝트에서는 **T0(저장소 위생 정리)부터** 이 절차가 적용된다.

## 3. 스프린트 매니저 (Notion DB)

스프린트 매니저와 GitHub Issue·PR을 하나의 워크플로우로 묶어, 모든 작업이 티켓 단위로 추적되고
상태가 일관되게 유지되도록 한다.

### 3.1 티켓 생성 원칙

- 스프린트 시작 시 해당 스프린트에서 작업할 **모든 티켓을 미리 생성**한다.
  - 도중에 추가되는 것은 허용하지만, 처음에 떠올린 작업은 누락 없이 등록하는 것이 기본.
- **1 티켓 = 1 GitHub 이슈.** 여러 작업이 묶여 있으면 분리한다.
  - 예: "API 설계 + 구현 + 테스트" → 3개 티켓
- 필수 속성: 이름, 상태, 담당자, 카테고리, 스프린트, 시작일, 마감일, 예상시간, 선행작업(해당 시)

### 3.2 작업 수행 워크플로우

```
티켓 생성 (상태: 시작 전)
   ↓
GitHub 이슈 등록 + 노션 상태 "진행 중"으로 변경
   ↓
이슈 번호 기반 브랜치 생성 → 작업 → PR 생성
   ↓
리뷰 승인 (셀프 리뷰) → 병합
   ↓
노션 상태 "완료"로 변경
```

**진행 중 전환 (작업 착수 시점)**
- [ ] GitHub 저장소에 이슈 등록 (제목·본문·라벨 포함)
- [ ] 노션 티켓 상태를 "진행 중"으로 변경
- [ ] 이슈 번호 기반 브랜치 생성

**완료 전환 (병합 시점)**
- [ ] PR 병합 완료
- [ ] 노션 티켓 상태를 "완료"로 변경

### 3.3 티켓 작성 템플릿

**DB 속성 필드**

- 담당자 · 스프린트 · 카테고리 · 시작일 · 마감일 · 상태: 기존 속성대로
- **예상시간**: `XS(1~3시간)` / `S(반나절)` / `M(1일)` / `L(2~3일)` / `XL(4~6일)`
  - 스프린트 하나(1주) 안에 들어가야 함. **XL이면 쪼개는 게 원칙.**
- **선행작업**: 이 티켓을 시작하기 전에 완료되어야 할 티켓을 relation으로 연결. 없으면 비워둠.

**본문 섹션** (작업 템플릿 선택 시 자동 생성)

- **목적** — "왜 이 티켓이 필요한가"를 한두 줄. 상위 마일스톤과 연결.
- **범위 In/Out** — 다룰 것과 다루지 않을 것을 명확히. **Out 없으면 스코프가 무한대.**
- **산출물** — 노션 페이지 링크 또는 파일 경로를 구체적으로. "분석"이 아니라 "분석 결과 노션 페이지".
- **완료 기준** — 객관 검증 가능한 체크리스트 3~5개. **"주관적 판단" 금지.**
- **참고자료** — (선택) 관련 링크·논문·문서.
- **리스크·미결** — 모르는 것을 숨기지 말고 적어둘 것.

### 3.4 프로젝트 공통 Definition of Done

모든 티켓이 `완료`로 이동하기 전에 충족해야 할 공통 체크리스트 (티켓별 완료 기준과는 별개).

- [ ] 산출물 링크가 티켓 본문에 명시됨
- [ ] 다른 팀원이 산출물을 열어 재현·확인 가능
- [ ] 후속 티켓이 착수 가능한 상태
- [ ] 디스코드 해당 스레드에 "완료 + 산출물 링크" 한 줄 공유
- [ ] 노션 상태 `완료`로 변경

### 3.5 Notion 전용 워크플로우 (코드가 없는 작업)

논문·RAGFlow 설정·내부 조사 등 GitHub 저장소에 코드·PR이 올라가지 않는 작업용.

**핵심 차이**: GitHub 이슈/브랜치/PR 단계 없음. 리뷰는 노션 코멘트 또는 디스코드 스레드에서 진행.
나머지는 3.2와 동일.

## 4. 티켓 분량 기준

> 한 사람당 각 업무에 대하여 **마감기한을 반드시 명시**하여 초안 마감기한 전까지 완료할 티켓
> (+깃허브 이슈)을 각각 **최소 5개씩** 미리 작성합니다. 각각 티켓에 대한 마감기한은
> **3일 정도의 주기**로 가져가는 것이 좋습니다. 초안 마감기한 안에는 다 끝내는 건 아니더라도
> 작업이 **최소 90% 이상 진행 및 프로그램 실행이 가능**하여야 합니다.

## 5. 과제 요구사항 — 6-2. 전사 업무 현황판 고도화

### Front-end

1. 전체 부서의 업무 진행 상황을 한눈에 볼 수 있는 대시보드 그리드 레이아웃
2. 차트 라이브러리(Chart.js/D3)를 활용한 부서별 진행률 도넛/바 차트 렌더링
3. 마감 기한이 임박하거나 지난(Overdue) 태스크를 붉은색으로 강조하는 조건부 스타일링
4. 특정 태스크 블록 클릭 시 세부 정보를 우측에서 슬라이딩해 보여주는 사이드 패널
5. 데이터 실시간 업데이트를 위한 리프레시 버튼 연동 및 로딩 상태 관리

### Back-end

1. 각 팀이 사용하는 외부 툴(Jira, Notion 등)의 상태 변경 Webhook을 수신하는 서버 엔드포인트
2. 다기종(Jira, Notion)에서 들어오는 각기 다른 페이로드 데이터를 중앙 대시보드 포맷으로 정제하는 파서(Parser)
3. 정제된 태스크 데이터를 저장하고 업데이트 상태를 기록하는 중앙화 DB 테이블
4. 부서별 전체 태스크 모수 대비 완료율, 지연율을 계산하는 통계 집계 쿼리 로직
5. 집계된 통계 데이터를 프론트엔드 대시보드 차트 규격에 맞춰 응답하는 GET API
6. 외부 툴과 자체 DB 간 데이터 누락(Webhook 실패 등) 방지를 위한 주기적 동기화(Sync) 배치 워커
7. 태스크 마감 기한이 하루 남았을 때 담당자에게 리마인드 알림을 발송하는 스케줄러
8. 클라이언트 새로고침 없이 대시보드 현황을 실시간으로 갱신하기 위한 웹소켓(Socket.io) 서버 구성
9. 상태 업데이트 이벤트 발생 시 웹소켓을 통해 접속 중인 클라이언트들에게 브로드캐스팅하는 로직
10. 지나치게 오래된(예: 1년 전) 완료 태스크 데이터를 아카이빙 테이블로 분리하는 파티셔닝 작업
