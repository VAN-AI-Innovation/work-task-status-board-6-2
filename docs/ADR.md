# Architecture Decision Records

> 근거 문서는 `docs/PLAN.md`. 여기에는 **되돌리기 비싼 결정과 그 대가**만 남긴다.
> 결정이 바뀌면 PLAN.md를 고치고 해당 ADR에 후속 항목을 덧붙인다 (기존 항목은 지우지 않는다).

## 철학

**담당자가 준 지시 2건(엑셀→조회 / 독스→엑셀)이 과제 원문보다 우선한다.**
실제 시트·독스에서 확인된 사실만 근거로 삼고, 추측으로 기능을 늘리지 않는다.
잘라야 하면 부가 기능부터 자르고 두 파이프라인은 사수한다.

---

### ADR-001: 입력 UI를 만들지 않는다 — 시트 업로드 기반의 해석 계층
**결정**: 데이터 입력은 Google Sheets에 남기고, 이 웹은 내보낸 `.xlsx`를 업로드받아 해석·조회만 한다.
**이유**: 담당자가 "엑셀시트 **입력 시**"라고 규정했다. 입력 UI를 만들면 팀원의 업무 습관을 바꿔야 하고
채택률이 0이 된다. 부수적으로 CRUD 화면 전체가 범위에서 빠져 초안 마감이 현실적이 된다.
**트레이드오프**: 업로드하지 않으면 데이터가 낡는다. 실시간이 아니다. 이 약점은 감출 수 없으므로
모든 페이지에 "마지막 반영: N일 전"을 상시 표시하고 5일 초과 시 경고색으로 **드러낸다.**

### ADR-002: 공통 컬럼 + `extras jsonb` + `task_stages` 자식 테이블
**결정**: 팀별 16/70/20 컬럼을 하나의 `tasks` 테이블에 담고, 매핑되지 않은 컬럼은 전부 `extras`로
흘려보낸다. 단계별 컬럼 그룹은 `task_stages`로 언피벗한다.
**이유**: 팀별 전용 테이블 3개는 통합 대시보드가 3-way UNION이 되고, 완전 EAV는 집계 쿼리가 지옥이다.
**"매핑 안 된 컬럼은 자동으로 `extras`"라는 성질이 70컬럼 대응의 전부**이며, 시트에 새 컬럼이 생겨도
파서가 깨지지 않는다.
**트레이드오프**: `extras` 안의 값은 SQL로 질의·집계하기 어렵다. 화면에서도 라벨-값 나열
(사이드 패널)로만 보여준다 — 표에 70컬럼을 뿌리지 않기로 한 결정과 짝이다.

### ADR-003: 엑셀 라이브러리는 ExcelJS 단독, 버전 `4.4.0` 고정
**결정**: 읽기·쓰기 모두 `exceljs@4.4.0`(캐럿 없이 정확히 고정). SheetJS는 쓰지 않는다.
**이유**: (a) 독스→배정표에서 **데이터 검증 드롭다운이 붙은 xlsx**를 만들어야 하는데 —
배정표는 사람이 이어서 입력할 파일이므로 이게 실질 가치다 — SheetJS로는 어렵다.
(b) `cell.isMerged`/`cell.master`로 병합셀을 명시적으로 다룰 수 있다.
(c) npm 레지스트리의 `xlsx`는 여전히 `0.18.5`로 프로토타입 오염 CVE 버전 그대로다(최신은 자체 CDN 배포).
**트레이드오프**: ExcelJS는 **2024-12-20 이후 정체**돼 있고 의존성 트리가 오래됐다(`unzipper@0.10`,
`uuid@8`, `archiver@5` 등). 이 프로젝트가 다루는 xlsx는 **신뢰된 내부 파일**이라 감수하되,
**교체 비용을 2파일로 묶는다** — ExcelJS import는 `lib/sheet/workbook-reader.ts`(읽기)와
`lib/xlsx/assignment-writer.ts`(쓰기) **두 곳에서만**. 나머지 코드는 `{ sheetName, cells[][], merges[] }`
같은 자체 타입만 안다. `next.config.ts`에 `serverExternalPackages: ['exceljs']`.

### ADR-004: Supabase를 처음부터 붙이고, 메모리 드라이버는 시연 안전망으로 남긴다
**결정**: 메모리로 만들었다가 옮기는 2단계를 쓰지 않는다. T4에서 바로 Supabase 스키마를 잡는다.
`TaskRepository` 인터페이스와 메모리 드라이버는 유지하되 역할을 **시연 안전망**으로 바꾼다.
**이유**: 이관 티켓이 통째로 사라진다. 메모리 드라이버의 값어치는 셋 — Supabase 무료 티어의 7일
미접속 일시중지 대비, 심사자가 **`.env` 없이 클론 즉시 실행**(`STORAGE_DRIVER=memory`),
두 구현이 같은 계약 테스트를 통과하므로 도메인 로직 검증이 저장소와 분리된다.
**트레이드오프**: 저장소 구현을 둘 유지해야 한다. 배열 몇 개라 비용은 작지만 계약 테스트를
게을리하면 두 구현이 갈라진다 — 그래서 계약 테스트가 T4 완료 기준에 있다.

### ADR-005: 폴백은 읽기 전용이다
**결정**: Supabase 연결 실패 시 memory로 자동 폴백하되, 모든 쓰기 경로(업로드 확정, PATCH)는
`503 STORAGE_READONLY`를 반환하고 UI는 편집을 비활성화한다. 배너 문구는
**"읽기 전용 — 저장소 연결 실패"**로, 의도된 데모 모드(`STORAGE_DRIVER=memory`)와 구분한다.
**이유**: 폴백 중에 쓰기를 받으면 메모리에 저장되고 재시작 시 사라진다. 사용자는 저장됐다고 믿는다.
**조용한 데이터 유실**이 조회 불가보다 훨씬 나쁘다.
**트레이드오프**: 장애 중 편집이 아예 막힌다. 의도한 대로다.

### ADR-006: 집계는 SQL이 아니라 `lib/domain/`의 JS 순수 함수
**결정**: `TaskRepository`는 저장·조회만 한다. 완료율·지연율·KPI·알림·목표 달성률은 전부
순수 함수이며 SQL 집계를 쓰지 않는다. `now`는 항상 인자로 주입한다.
**이유**: SQL로 집계하면 메모리 구현과 결과가 갈라지고 "두 구현이 같은 계약 테스트를 통과한다"가
깨진다. 조직 전체 업무는 **수백~수천 행 규모**라 SQL 집계의 성능 이점이 없다.
**트레이드오프**: 행이 수만을 넘어가면 전량 로드가 부담이 된다. 그 시점은 이 과제 범위 밖이고,
넘어가면 재검토한다.

### ADR-007: 서버 컴포넌트는 `lib/`를 직접 호출한다 — API 라우트는 클라이언트 상호작용 전용
**결정**: 초기 렌더 데이터는 서버 컴포넌트가 `lib/store`·`lib/domain`을 직접 호출한다.
자기 API 라우트를 `fetch`하지 않는다. API는 파일 업로드·상태 수정·외부 소비만 담당한다.
**이유**: 서버 컴포넌트에서 자기 API를 fetch하면 불필요한 HTTP 왕복이 생긴다.
초기 CLAUDE.md의 "모든 API 로직은 `src/app/api/`에서만"을 문자 그대로 지키면 서버 컴포넌트가
`lib/store`를 못 읽어 규칙과 설계가 충돌했다. **규칙을 "비즈니스 로직은 `src/lib/`에만"으로 교체**했다.
**트레이드오프**: 같은 데이터에 진입 경로가 둘(서버 직접 호출 / API)이라 응답 스키마를 두 번
신경 써야 한다. 특히 `raw` 제외·민감 키 마스킹은 API 쪽에서 zod로 강제한다.

### ADR-008: 업로드는 미리보기 → 확정 2단계
**결정**: 파싱 결과를 `uploads.parse_result`에 넣고, 사용자가 확정하면 그것을 소스로 upsert한다.
확정 전에는 저장소에 아무것도 쓰지 않는다. 확정 후 `parse_result`는 비우고 `summary`만 남긴다.
upsert는 단일 트랜잭션으로 묶는다.
**이유**: 즉시 반영은 단순하지만 잘못된 파일 하나로 DB가 오염되고 되돌리기 어렵다.
DB에 파싱 결과를 두면 **서버 세션 상태 없이** 2단계가 성립한다.
**트레이드오프**: 왕복이 한 번 늘고 `parse_result`가 일시적으로 커진다(70컬럼 × N행).
Postgres TOAST로는 감당되지만 메모리 드라이버에선 RAM에 상주하므로 확정 즉시 비운다.
또 하나 — **"단일 트랜잭션"은 메모리 드라이버에서만 참이다.** `supabase-js`에 트랜잭션 API가
없어 Supabase 확정은 왕복 여럿으로 쪼개지고, 대신 **멱등 재시도**로 부분 반영을 수렴시킨다
(근거와 RPC 승격 경로는 `PLAN.md` `X4`의 후속 문단).

### ADR-009: 「지연」은 상태값이 아니라 파생 판정이고, 상태 문자열은 `semantic`으로 한 번 감싼다
**결정**: 시트의 10단계 진행 상태를 `enum_options.semantic`으로 매핑하고(planned·in_progress·review·
approval·rework·pending_release·done·hold·cancelled), 화면의 5색은
`toDisplayStatus(semantic, flags)`가 다시 매핑한다. `isOverdue`는 **다른 색을 덮어쓴다.**
**이유**: 판정 로직이 한글 상태 문자열을 직접 알면 시트에서 이름이 바뀔 때 코드가 깨진다.
지연을 상태값 중 하나로 취급하면 "진행 중이면서 마감이 지난" 업무를 놓치고 완료율이 틀린다.
**트레이드오프**: 매핑층이 둘(원문→semantic→5색)이라 처음 읽을 때 간접적이다.
대신 시트가 바뀌어도 고칠 곳이 `enum_options` 한 곳이다.

### ADR-010: 독스 입력은 `.docx` 단일. 마크다운 리더는 테스트 픽스처 전용
**결정**: 제품이 받는 입력은 `.docx` 하나(mammoth). `markdown-reader.ts`는 남기되 **제품 경로가 아니며**
같은 `OutlineNode[]`를 뱉는다.
**이유**: (a) `.docx`는 바이너리라 픽스처로 최악이다 — git diff가 안 되고 테스트가 뭘 검증하는지 읽을 수 없다.
`.md` 픽스처로 아웃라인 로직을 검증하고 `.docx`는 리더 계층만 스모크 테스트한다.
(b) mammoth의 Google Docs 스타일 인식이 흔들릴 때(H8) 이미 만들어둔 탈출구가 된다.
**트레이드오프**: 리더가 둘이라 "같은 출력을 낸다"는 테스트를 추가로 져야 한다. 추가 비용은 파일 하나다.
**선행 확인**: 실제 Google Docs를 `.docx`로 내보내 heading이 `h1~h3`으로 인식되는지 T1(사전 스모크 테스트)에서 확인한다.

### ADR-011: 데이터 행 판정은 신원 컬럼으로만 한다
**결정**: `isDataRow(row)` = 신원 컬럼(업무명·프로젝트명 / 담당자) 중 하나 이상에 실제 값이 있다.
**수식 결과 컬럼은 판정에 쓰지 않는다.** 추가로 1900-01-01 이전 날짜는 전부 null로 떨어뜨린다.
**이유**: 실제 `02_촬영·기획팀` 탭에 **유령 행 25개**가 있다 — 업무ID·프로젝트명은 비어 있는데
수식이 만든 `FALSE`·`0%`·`1900. 01. 01.`이 25개 컬럼에 들어차 있다. "셀에 값이 있으면 데이터 행"이라는
흔한 판정을 쓰면 유령 태스크 25건이 생기고, **1900년 기한의 "지연" 업무 25건**이 대시보드를 덮는다.
**트레이드오프**: 신원 컬럼이 비어 있는 진짜 업무는 누락된다. 그런 행은 애초에 사람도 식별할 수 없다.

### ADR-012: 생성한 xlsx의 수식 주입을 쓰기 쪽에서 막는다
**결정**: `assignment-writer.ts`에서 모든 문자열 셀을 명시적 텍스트 타입으로 쓰고,
`=`·`+`·`-`·`@`·탭·개행으로 시작하면 `'` 프리픽스를 붙인다. 읽기 쪽은 수식 셀의 `result`만 쓰고
`formula` 문자열은 저장도 렌더도 하지 않는다.
**이유**: `/extract`가 만든 배정표는 **조직 사람들에게 배포되는 파일**이다. 독스 본문의 값이 그대로
셀에 들어가는데 `=cmd|'/c calc'!A1` 같은 문자열은 받는 사람 PC에서 실행된다.
**트레이드오프**: `=`로 시작하는 정당한 텍스트도 앞에 `'`가 붙는다. 사람이 지우면 그만이다.

### ADR-013: `?as=` 역할 전환은 정식 데모 기능이되, 메모리 드라이버에서만 동작한다
**결정**: 로그인(T8) 이전에도 `?as=admin|lead|member`로 세 역할의 진입 화면을 시연한다.
단 `NODE_ENV === 'production' && driver !== 'memory'`면 **무시**한다.
**이유**: 초안 심사 시점에 권한 구분을 보여줄 수단이 필요하다(H7 헤지). 그러나 T8 이후에도 남아 있으면
**URL만 치면 관리자가 되는 완전한 인증 우회**다. Supabase에 붙는 순간 자동으로 죽게 만든다.
**트레이드오프**: 프로덕션+Supabase 환경에서는 이 데모 경로를 쓸 수 없다. 의도한 대로다.

### ADR-014: PC 우선 — 1280px 기준, 1024px까지 유지
**결정**: 기준 폭 1280px로 설계하고 1024px까지 레이아웃을 유지한다. 그 아래는 **깨지지 않고 읽히는
수준**까지만 대응하고 별도 모바일 레이아웃을 만들지 않는다.
**이유**: 촬영·기획팀 70컬럼을 다루려면 넓은 화면이 전제다. 이 결정이 표 설계 전체를 단순하게 만든다.
**트레이드오프**: 부원이 폰으로 "내 마감"을 보는 경험이 최적이 아니다. 초안 범위에서 감수한다.

### ADR-015: UI 톤을 라이트에서 다크로 뒤집되, 안티패턴 규율은 한 줄도 풀지 않는다 (`ADR-018`로 번복)
**결정**: `PLAN.md`가 「사용자 확정」으로 못박아 둔 라이트 톤을 T6 착수 시점에 **다크로 교체**한다.
바뀌는 것은 배경의 명도 하나뿐이고 **무채색 원칙·시맨틱 2색(빨강=지연, 앰버=주의)·AI 슬롭
안티패턴 표는 전부 유지**한다. 색은 `globals.css`의 `@theme` 토큰 한 곳에서만 오고, 화면 코드는
`bg-canvas`·`text-ink` 같은 토큰 클래스로만 색을 부른다 — Tailwind 팔레트 클래스(`neutral-`·`red-`)와
hex 리터럴을 쓰지 않는다.
**이유**: 확정값을 뒤집은 것은 그 값을 확정한 당사자다. 근거를 남기지 않으면 다음 사람이
「PLAN.md에 라이트라고 적혀 있다」를 보고 되돌린다. 색 토큰을 한 곳으로 모은 것은 미관이 아니라
**이미 한 번 뒤집힌 프로젝트**이기 때문이다 — 팔레트 클래스가 파일마다 흩어져 있으면 다음에
뒤집을 때 같은 일을 파일 수만큼 반복한다. 참고로 제시된 이미지는 보라 액센트의 파이낸스
대시보드였으나 **참고한 것은 구조(사이드바·상단 바·KPI 타일 행·차트 카드)이지 색이 아니다.**
액센트를 하나라도 들이면 시맨틱 2색이 셋이 되어 지연이 묻힌다.
**트레이드오프**: 다크에서 **명도 방향이 뒤집힌다.** 라이트에서 「진행 = 가장 진한 무채색」이었던
배지가 다크에서는 배경에 묻히므로 반전 배지(`bg-ink text-canvas`)가 됐고, 차트 계열색도 단순 반전이
아니라 패널 배경 위에서 구분되도록 다시 잡아야 했다. 라이트로 되돌리려면 그 두 표를 함께 다시 뒤집는다.

### ADR-016: 저장소 필터 `?status=`와 화면 필터 `?display=`를 합치지 않는다
**결정**: 5색 상태 칩은 `?display=planned|in_progress|review|done|overdue|muted`라는 **새 쿼리 키**를
쓴다. 기존 `?status=`는 그대로 두고 두 축을 섞지 않는다. `?overdue=1`(판정 필터)도 `?display=overdue`(칩)와
합치지 않는다.
**이유**: 둘은 **다른 축**이다. `?status=`는 시트 원문 문자열(`진행 중`)이고 저장소가 그대로 비교한다.
칩이 보내는 값은 `toDisplayStatus`가 semantic과 파생 플래그로 판정한 결과이며, 그 판정은
`ADR-006`에 따라 SQL이 아니라 `lib/domain`의 순수 함수가 한다. 칩이 `?status=in_progress`를 보내면
저장소에 그런 문자열이 없어 **조용히 0건**이 되고, 사용자는 필터가 아니라 데이터를 의심한다.
`?overdue=1`을 흡수하지 않은 것도 같은 이유다 — 앞은 `buildReadContext`가 거는 판정 필터이고
뒤는 칩이라, 합치면 기존 `UC-11` 공유 링크와 칩 UI가 서로를 덮어쓴다.
**트레이드오프**: 「상태로 거른다」는 한 가지 일에 URL 키가 셋(`status`·`display`·`overdue`)이라
처음 읽을 때 장황하다. 대신 어느 키가 어느 계층에서 걸리는지가 이름만 보고 갈린다.

### ADR-017: 팀 라우트 슬러그는 ASCII이고, 경로가 `?team=`을 이긴다
**결정**: `/teams/edit` · `/teams/shoot` · `/teams/marketing`. 소문자 한 모양만 받고 모르는 슬러그는
**404**다. 경로가 정한 팀이 `?team=`을 **덮어쓰며**, 나아가 그 화면이 만드는 링크에는 `?team=`을 싣지 않는다.
**이유**: 이 화면의 존재 이유가 **링크 복사·공유(`UC-11`)** 다. `/teams/편집팀`은 복사하면
`/teams/%ED%8E%B8%EC%A7%91%ED%8C%80`이 되어 사람이 읽을 수 없고 메신저·이슈 본문에서 줄이 깨진다.
팀 키(`edit`·`shoot`·`marketing`)는 이미 `TeamKey`로 코드 전체에 있어 새 어휘를 만드는 것도 아니다.
404로 두는 것은 전사 대시보드로 넘기면 **오타 링크가 조용히 다른 화면을 보여 주고 사람이 데이터를
의심하기** 때문이고, 대문자를 받지 않는 것은 같은 화면의 URL이 둘이 되면 공유된 두 링크가 같은 곳인지
눌러 봐야 알기 때문이다. `/teams/edit?team=shoot`이 촬영팀을 보여주는 링크는 거짓말이다.
**트레이드오프**: 화면에 뜨는 팀 이름(`편집팀`)과 URL의 단어(`edit`)가 다르다. 한글을 모르는
사람에게는 이점이지만, 팀 이름만 아는 사람이 URL을 손으로 칠 수는 없다. 팀 이름·슬러그 표는
`src/lib/view/team-slug.ts` 한 곳에 있어 사본이 갈라지지 않는다.


### ADR-018: 톤을 라이트로 되돌리고, 톤은 하나만 유지한다 (`ADR-015` 번복)
**결정**: `ADR-015`가 다크로 뒤집었던 톤을 **라이트로 되돌린다.** 다크 토큰·다크 전용 규칙은
남기지 않는다 — 토글도 두지 않고 **라이트 하나만** 존재한다. 바뀌는 것은 `globals.css`의
`@theme` 값과 차트 계열색(`chart-series.ts`) **두 곳뿐**이고, 무채색 원칙·시맨틱 2색·AI 슬롭
안티패턴 표는 `ADR-015`와 마찬가지로 **한 줄도 풀지 않는다.**
**이유**: 톤을 확정한 당사자가 T6 완료 후 화면을 보고 다시 라이트를 골랐다 (2026-08-22).
같은 사람이 같은 축을 두 번 뒤집었으므로 근거를 남기지 않으면 다음에 또 왕복한다 — **이 항목은
취향이고, 취향은 사용자의 것이다.** 토글을 두지 않는 이유는 `ADR-015`가 다크 단일을 고른 이유와
같다: 톤이 둘이면 배지 명도 방향·차트 계열색·스크린샷 기준이 전부 두 벌이 되고, 리뷰에서
「이 화면이 맞느냐」를 판정할 기준 자체가 흔들린다.
두 번 뒤집고 알게 된 것: **토큰을 한 곳에 모아 둔 결정이 값을 했다.** 화면 코드에 hex가 하나도
없어서 이번 전환에서 색 때문에 손댄 파일은 `globals.css`와 `chart-series.ts` 둘뿐이고,
`status-badge.ts`의 배지 표는 **한 글자도 고치지 않았다** — 배지가 색이 아니라 의미(`bg-ink`=
가장 진한 것, `bg-raise`=배경에 가까운 것)로 적혀 있어 토큰 값만 뒤집히면 명도 방향이 저절로
따라온다. 다음에 또 뒤집는 사람도 이 두 파일만 보면 된다.
**트레이드오프**: 흰 배경에서는 시맨틱 2색의 **텍스트 값과 배경값을 따로 잡아야 한다.**
다크에서 쓰던 `#f87171`(지연)·`#fbbf24`(주의)는 흰 바탕에서 대비가 모자라 읽히지 않으므로
텍스트는 어둡게(`#c2181b`·`#8a5a06`), 배경은 옅게(`#fdeced`·`#fdf3e0`) 나눠 잡았다. 같은
「빨강 하나」지만 값은 두 개다.

### ADR-019: 대시보드는 12열 flow에 zone 셋으로 깔고, 상태 분포는 도넛이 아니라 스택 바다
**결정**: 대시보드 섹션을 세로로 쌓지 않고 **12열 그리드에 흘려보낸다**(flow). 각 섹션은
`SECTION_SPAN`으로 폭을, `SECTION_ZONE`으로 zone(`summary`·`detail`·`table`)을 갖는다.
zone 순서는 **역할 배열에서 그 zone이 처음 등장하는 순서**로 정해지고, zone 안에서는
`SECTION_ORDER`의 순서를 그대로 따른다. `detail` zone(목표·브리핑·승인 대기)은 `<details>`로
접혀 한 줄이 된다. 그리고 **상태 분포는 도넛을 버리고 가로 스택 바 한 줄**로 그린다 —
Chart.js가 아니라 `div` 비율이라 클라이언트 컴포넌트도 아니다.
**이유**: 사용자가 T6 화면을 보고 든 불만이 셋이었고 셋 다 **높이** 문제다. (1) 도넛이 세로
300px를 쓰면서 KPI 타일과 같은 사실을 두 번 말한다 — 특히 건수가 적으면 단색 링이 되어 정보량이
0이다. (2) 알림 패널이 12칸을 다 쓰는 바람에 항목 이름과 건수 사이가 화면 폭만큼 벌어진다.
(3) 그래서 요약을 보려면 스크롤을 내려야 한다. **대시보드는 스크롤하지 않고 한 번에 읽는
화면이다** — 그것이 이 화면이 매일 열리는 이유다. 1280×900 기준으로 `summary`와 접힌 `detail`이
첫 화면에 들어가고 업무 표만 아래로 내려간다.
배치의 구체값은 `UI_GUIDE.md`「대시보드는 한 화면이다」에 그림으로 있다. 팀별 현황 표와
완료율 막대를 **한 칸에 세운 것**과 상태 분포를 **폭 전체**로 둔 것이 그중 둘인데, 앞은
알림(6칸)과 높이를 맞추려는 것이고 뒤는 8px 막대 한 줄이 좁은 칸에서 조각 구분을 잃기
때문이다.

zone을 도입하되 `SECTION_ORDER`를 그대로 둔 것이 요점이다. 역할별 진입 화면(완료 기준 7)이 묻는
것은 **「무엇이 맨 위냐」**이고, zone 순서를 역할 배열에서 유도하면 그 성질이 보존된다 —
`admin`은 `summary`(KPI)부터, `lead`도 `summary`(알림)부터, `member`는 `table`(업무 표)부터
시작한다. **어느 역할도 섹션을 잃지 않는다**는 불변식도 그대로다. 삭제는 권한이고 권한은 T8이다.
**짝과 쌓기**: 자동 배치(first-fit)는 빈칸을 줄이지만 **무엇과 무엇이 나란히 서야 하는지**를
모른다. 그래서 화면이 `groups`로 짝을 정하고(대시보드: 팀별 현황 + 팀별 완료율 / 알림 +
상태 분포), 한 칸 안에 섹션을 **세로로 쌓을 수도** 있다(팀 화면: 알림 오른쪽에 상태 분포 +
목표 대비 성과). 짝이 정해진 행에는 다른 섹션이 끼어들지 않는다 — 화면이 의도한 조합이기
때문이다. 역할별 순서는 그대로다: 짝의 자리는 **그 짝에 속한 섹션 중 역할 배열에서 가장
먼저 오는 것**이 정한다.

**상태 분포는 세 번 바뀌었다**: 도넛 → 스택 바 → **가로 막대**. 도넛은 세로 300px를 쓰면서
KPI와 같은 사실을 두 번 말했고, 스택 바는 반대로 세로를 거의 안 먹어서 **옆에 세울 카드가
없었다** — 알림처럼 길어지는 카드 옆에 두면 그쪽이 통째로 비었다. 가로 막대는 세로를 채우고,
값이 비율이 아니라 건수라 조각이 작아도 축을 보고 읽을 수 있다. (**후속**: 알림 묶음을
아코디언으로 접으면서 「알림이 길어지는 카드」라는 전제가 뒤집혔다. 상태 분포는 이제 옆 카드를
따라 늘어나지 않고 **확정 높이**를 쓴다 — `status-bars.tsx` 머리말.)

**행 높이**: 같은 행의 카드는 `items-stretch`로 테두리를 맞추되, 늘어난 높이는 **콘텐츠가**
먹는다 — 완료율 차트는 컨테이너를 따라 길어지고(`maintainAspectRatio: false`), 알림은 목록이
늘어나며 넘치면 목록만 스크롤한다. 그리고 **높이가 변하는 카드 옆에는 함께 늘어날 수 있는
카드만 세운다.** 알림은 데이터에 따라 길어지므로 짧고 고정된 카드를 옆에 두면 그쪽이 통째로
빈다 — 팀 화면이 그 경우라 거기서는 알림을 혼자 세웠다.

**펼침은 제자리에서 일어난다**: 접힌 카드는 펼쳐도 폭이 그대로이고 아래로만 자란다.
12칸으로 넓히던 초기안은 셋이 나란히 접힌 줄에서 하나만 폭 전체를 차지해 **화면이 통째로
재배치된 것처럼** 보였다. 그리고 **접히는 카드가 있는 행은 높이를 맞추지 않는다** — 맞추면
펼치는 순간 옆 칸까지 함께 늘어나 그쪽이 빈 채로 남는다.

**트레이드오프**: `detail` zone이 접혀 있어 **목표·브리핑·승인 대기는 한 번 눌러야 보인다.**
0건 묶음을 지우지 않는 것과 같은 이유로 접힌 제목과 요약 수치는 항상 남긴다 — 접힌 것과 없는
것이 화면에서 같아 보이면 안 된다. 그리고 도넛을 버려서 **조각별 각도 비교**를 잃었다. 스택 바는
비율을 길이로만 주므로 작은 조각이 도넛보다 덜 보이는데, 애초에 이 화면에서 작은 조각은
「지연 몇 건」이고 그 숫자는 KPI 타일이 가장 큰 글자로 말하고 있다.

### ADR-020: 브랜드 남색은 **구조와 조작**에 쓴다. **데이터에는 한 번도 쓰지 않는다**
**결정**: 대표색 **`#1e3a5f`(남색)** 를 토큰 `--color-brand`(+ `brand-strong` hover ·
`brand-soft` 옅은 바탕)로 들인다. 쓰는 자리는 둘이다.

- **구조** — 페이지 제목·섹션 제목·접힌 카드의 제목·표 헤더 바탕. 화면의 뼈대가 어디서
  갈라지는지를 말하는 글자들이다.
- **조작** — 로고, 사이드바의 현재 화면, 활성 필터 칩, 「적용」 버튼, 역할 전환, 기본 버튼,
  링크 hover, 표 행 hover, 입력 포커스 테두리.

**쓰지 않는 자리는 하나다: 데이터.** 차트 계열색·상태 배지·KPI 수치·표의 값·알림 건수는
전부 무채색과 시맨틱 2색(빨강=지연, 앰버=주의) 그대로다.

**이유**: 사용자에게 대표색이 있고 화면에 그 색이 없으면 이 도구가 어느 팀 것인지 알 수 없다.
다만 색을 **데이터에** 들이면 `UI_GUIDE.md`의 「눈에 띄는 것은 문제뿐」이 즉시 깨진다 — 정상
업무가 남색을 가지면 화면의 절반이 색을 갖고 지연 빨강이 묻힌다. 그래서 **역할로 갈랐다**:
남색은 「여기가 어디이고 무엇을 누를 수 있나」를, 빨강은 「무엇이 문제인가」를 말한다.
두 축이 겹치지 않아 한 화면에 있어도 서로를 가리지 않는다 — 업무 표를 보면 헤더는 남색이고
그 아래 지연 배지만 붉은데, 둘을 헷갈리는 사람은 없다.

처음에는 **조작 요소에만** 뒀다가, 사용자가 「남색이 왼쪽 메뉴에만 있는 느낌」이라고 해
**구조까지** 넓혔다. 넓힌 것은 제목과 표 헤더이고, **데이터 경계는 한 칸도 움직이지 않았다.**

「보라·인디고 브랜드 색상」 안티패턴과 충돌하지 않는다. 그 항목이 가리키는 것은 **AI 템플릿이
기본값처럼 쓰는 보라 액센트**이고, 여기 남색은 사용자가 가진 실제 대표색이다. 그래도 규율은
기계적으로 확인할 수 있게 남긴다 — **브랜드 토큰이 `chart-series.ts`나 `status-badge.ts`에
들어가면 이 ADR을 어긴 것이다.** 그 두 파일이 데이터의 색을 정한다.

**트레이드오프**: 강조가 **두 언어**가 됐다. 「진행」 배지(`bg-ink`=검정 채움)와 기본
버튼(`bg-brand`=남색 채움)이 형태가 같고 색만 다르다 — 배지는 표 안에만, 버튼은 표 밖에만
있어 나란히 서는 자리는 없지만, 새 컴포넌트를 만들 때 **「이건 데이터인가, 구조·조작인가」를
먼저 물어야 한다.** 그 질문에 답하지 않고 색을 고르면 규칙이 조용히 무너진다.

### ADR-021: 배정표의 `우선순위`는 문서의 `P0`이 아니라 시트 enum 값으로 쓴다
**결정**: 「워크로드 공유」 절의 `P0`~`P3`을 `긴급`·`높음`·`보통`·`낮음`으로 **옮겨 적어**
배정표 `우선순위` 셀에 넣는다. 매핑되지 않는 값과 조인 실패는 **빈칸**이고 경고도 내지 않는다.
문서 원문은 버리지 않고 행이 `priorityRaw`로 들고 있되 **셀에는 쓰지 않는다.**
**이유**: 이 배정표의 존재 이유는 사람이 채워서 `/upload`에 **다시 올리는 것**이다
(`PLAN.md`「독스 추출 루프」의 닫히는 고리). 그런데 `우선순위` 컬럼에는 시트 `공통_우선순위`
드롭다운이 붙어 나가므로 `P0`은 목록 밖 값이다 — 엑셀이 셀에 경고를 띄우고, 재업로드하면
`collectUnregisteredEnumWarnings`가 `UNREGISTERED_PRIORITY`를 낸다. **두 번 다 사용자가
자기 잘못이라고 읽는데 실은 우리가 만든 파일이 틀린 것이다.** 조인 실패를 경고로 만들지
않은 것은 `TICKETS.md` T7이 이미 「조인 실패는 무시」로 정해 뒀기 때문이다 — 「워크로드 공유」
절에 없는 과제가 대부분이고, 그것들은 우선순위가 **없는 것이지 잘못된 것이 아니다.**
**트레이드오프**: 문서에서 `P0`을 본 사람이 배정표에서 `긴급`을 보고 **같은 것인지 확신하지
못한다.** 매핑표를 `PLAN.md`「T7 착수 시 확정」에 두는 것으로 갈음하고, 배정표에 `P0` 컬럼을
따로 만들지는 않았다 — 컬럼 11개는 `PLAN.md`가 고정한 값이고, 재업로드 시 시트 파서가
모르는 컬럼은 `extras`로 흘러가 아무도 보지 않는다.

### ADR-022: `/extract`는 아무것도 저장하지 않는다 — 미리보기·내려받기 두 라우트로 끝낸다
**결정**: 독스 추출 경로에 **`ADR-008`의 미리보기→확정 2단계를 쓰지 않는다.** `uploads` 행도
`doc_extractions` 행도 만들지 않고, 라우트 둘이 각각 stateless로 끝난다 —
`POST /api/uploads/doc`(`.docx` → 행 JSON)와 `POST /api/export/assignment`(행 JSON → xlsx 바이트).
**이유**: `TICKETS.md` T7 범위 Out에 「DB 저장」이 있어 **확정할 저장소가 애초에 없다.**
`ADR-008`의 2단계는 「잘못된 파일 하나로 DB가 오염되는 것」을 막는 장치인데, 오염될 DB가 없으면
그 장치는 왕복만 한 번 늘린다. 스코프보다 무거운 이유가 하나 더 있다 — `uploads` 행을 만들면
`parse_result`에 **문서 본문이 통째로** 남는다. 워크로드 문서에는 사람 이름이 들어 있고
(`S6`), 시트 업로드에서는 확정 직후 `parse_result`를 비워 그 노출을 닫았지만 여기서는 **확정이
없어서 비울 시점도 없다.** 애초에 쓰지 않는 것이 가장 짧은 방어다.
**트레이드오프**: 사용자가 미리보기를 본 뒤 xlsx를 받으려면 **행 JSON이 브라우저를 한 번
왕복한다.** 서버가 두 번 파싱하지 않는 대신 클라이언트가 중간 산출물을 들고 있는 셈이라,
탭을 닫으면 다시 올려야 한다. 추출 이력도 남지 않는다 — 누가 언제 어떤 문서를 뽑았는지
추적할 수 없다. 이력이 필요해지면 `doc_extractions` 테이블이 이미 스키마에 있으므로
**이 ADR을 먼저 뒤집고** 그때 쓴다.

**따라 나온 것 — 이 화면은 읽기 전용 모드에서도 살아 있다.** `ADR-005`는 폴백 중 모든 쓰기
경로를 `503`으로 막는데, 저장하지 않기로 한 결과 `/extract`에는 막을 쓰기가 없다. 그래서
화면이 `readOnly`를 패널에 넘기지 않고 드롭존도 잠그지 않는다 — 잠그면 「저장소가 죽어도
배정표는 뽑을 수 있다」는 이 결정의 부수 효과를 화면이 스스로 부정한다. 배너는 그대로
띄운다: 배너가 고지하는 것은 **저장소 상태**이지 이 화면의 가용성이 아니다.

### ADR-023: 계약 테스트는 자기 행만 센다 — 원격 DB는 계약이 혼자 쓰는 저장소가 아니다
**결정**: 계약 스위트가 저장소를 **`scopeToContractRows`로 감싸서** 본다. `sourceKey`·
`periodLabel`에 `contract::` 접두사가 붙은 행만 조회에 잡히고, `limit`은 그 뒤에 센다.
전역 값이라 접두사로 좁힐 수 없는 `getLastSyncedAt`만 다르게 푼다 — 계약이 `2099`
시간대(`CONTRACT_EPOCH`)를 점유하고, 그보다 이른 값은 남의 업로드로 보아 `null`로 돌린다.
`reset`은 그대로 접두사 범위만 지운다(원본 저장소가 받는다 — `clear()` 같은 구현별 수단이
껍데기에 없다).
**이유**: supabase 구현의 계약 테스트는 **실업무 데이터와 같은 원격 DB에 붙어 돈다.** 계약은
「2건 넣었으니 `listTasks()`가 2건이다」로 단언하는데 `listTasks()`는 화면이 쓰는 그 함수라
남의 행도 정직하게 센다. 그래서 실업무 행이 **한 줄만 생겨도** 계약 10건이 영구히 실패했고
(이슈 #20), 저장소와 무관한 작업까지 기본 게이트에서 막혔다. 지우는 쪽을 넓히는 것은 답이
아니다 — 테스트가 사용자의 실업무 데이터를 날린다. **지울 때 자기 것만 지우니, 셀 때도 자기
것만 세는 것이 짝이 맞는다.** 계약이 확인하려던 것("내가 넣은 것이 들어갔나")은 그대로다.
**트레이드오프**: 계약이 쓰는 업로드 시각이 **미래(2099)** 다. 스위트가 도는 동안 원격 DB에
2099년 `updated_at`을 가진 행이 존재하고, 실행이 도중에 죽으면 남아서 화면의 「마지막 반영」이
미래로 보인다 — `afterAll(resetContractRows)`로 정상 종료 시에는 남지 않게 했고, 다음 실행의
`reset`이 어차피 지운다. 대안이었던 「17번을 memory에서만 돌린다」는 `T4` 완료 기준 8(두 구현이
같은 계약을 통과)에서 한 항목을 빼는 것이라 택하지 않았다. 실제로 두 구현이 갈라졌던 자리가
바로 17번이다(목표 지표만 담긴 업로드를 supabase만 반영하지 않았다).
**또 하나**: `limit`을 저장소에 넘기지 않고 받아서 자른다 — 넘기면 남의 행이 앞자리를 채워
「2건 중 2건」이 「2건 중 0건」이 된다. 그 대신 계약이 서버 측 `.limit()`을 더는 밟지 않으므로,
`supabase-task-store.test.ts`에 「서버 측 limit」 테스트를 따로 뒀다(`sourceKeys`로 좁혀
실업무 행 수와 무관하게 정해지는 단언이다).

### ADR-024: 조회는 사용자 JWT로 나간다 — `service_role`은 업로드 확정·시드에만
**결정**: 조회 경로(대시보드·팀 탭·조회 라우트 6종·`PATCH /api/tasks/[id]`)는 anon 키에
**사용자 JWT를 실어** 나간다. `service_role`을 쓰는 곳은 **업로드 확정과 `/api/uploads/seed`
둘뿐**이다. 프로세스 전역 싱글턴인 `getStorage()`는 `service_role` 경로 전용으로 남기고,
조회용 **요청 스코프** 핸들을 `src/lib/store/viewer-storage.ts`가 요청마다 새로 만든다.
**이유**: `TICKETS.md` T8 완료 기준 5가 못박은 것이다 — **전부 `service_role`로 처리하면 RLS를
만들어도 의미가 없다.** `service_role`은 RLS를 통째로 우회하므로, 그 키로만 붙는 한 정책
파일은 주석과 다를 바가 없고 완료 기준 1·2는 **서버 코드의 if문 하나에만** 걸리게 된다.
그것이 뚫리면 남는 방어가 없다. 반대로 업로드 확정을 사용자 JWT로 보낼 수는 없다 — 확정은
시트 전체를 쓰고 거기에는 **올린 사람의 범위 밖 행**이 반드시 섞인다(팀장이 전사 시트를 올린다).
싱글턴에 JWT를 밀어 넣지 않는 이유는 더 단순하다: 캐시가 프로세스 전역이라 **한 사용자의
토큰이 다음 요청의 다른 사용자에게 샌다.** 그 캐시가 번들마다 갈라져 있던 결함을 T6 감사에서
이미 한 번 고쳤고(`store-factory.ts`의 전역 심볼), 같은 자리에 요청 상태를 얹으면 그 수정이
그대로 사고가 된다.
**트레이드오프**: 저장소 진입점이 **둘**이 된다 — `getStorage()`(쓰기·전역)와
`viewer-storage`(조회·요청 스코프). 새 라우트를 만들 때 「이건 어느 쪽인가」를 매번 물어야
하고, 틀리면 조용히 지나간다 — `service_role`로 조회하면 **에러 없이 더 많이 보인다.**
판별식은 하나다: **올린 사람의 범위 밖 행을 써야 하면 `service_role`, 그 밖은 전부 사용자 JWT다.**
부수 비용으로 요청마다 Supabase 클라이언트를 하나 만든다(HTTP 클라이언트라 연결 풀이 아니다).

### ADR-025: `security definer` 함수는 셋이다 — `my_member_id()`가 `member` 범위를 진다
**결정**: `public.my_role()`·`public.my_team()`에 **`public.my_member_id()`를 더해 셋**을 둔다.
셋 다 `language sql` · `stable` · `security definer` · **`set search_path = ''`** 이고 테이블
이름에 스키마를 명시한다. `member` 범위 정책은 `tasks.owner_member_id = public.my_member_id()`로
쓴다.
**이유**: `PLAN.md`·`ARCHITECTURE.md`가 적어 둔 함수는 둘인데 **`member` 범위를 그 둘로는
표현할 수 없다.** `member`가 보는 것은 「본인이 담당인 건」이고, 그 판정에 필요한 것은 역할도
팀도 아니라 **내 `members` 행의 id**다. 정책 안에서 `members`를 직접 select하면 `members`의
정책이 다시 걸린다 — `profiles`를 감싼 것과 **똑같은 재귀 함정**이고, 감싸지 않으면 정책이
행마다 서브쿼리를 돌아 조회가 느려진다. `set search_path = ''`를 고정하는 이유는 미관이
아니다: 고정하지 않으면 호출자가 같은 이름의 테이블을 자기 스키마에 만들어 함수를 속일 수
있고, 그것은 **권한 상승 경로다**(`S5`). 완료 기준 4가 두 함수만 이름을 적고 있지만, 셋째
함수도 같은 규율 아래 있다 — 하나라도 빠지면 그 하나가 문이 된다.
**트레이드오프**: 로그인한 사람마다 **정책이 함수를 세 번 부른다.** `stable`이라 문장 안에서는
결과가 캐시되지만, 조회 하나에 `profiles`·`members` 조회가 얹히는 것은 사실이다. 수백~수천 행
규모에서 감수한다(`ADR-006`이 SQL 집계를 밀어낸 것과 같은 근거다). 더 아픈 쪽은 **`null`이 셋
다 정상값**이라는 것이다 — 로그인했지만 프로필이 없거나(`my_role()`), `admin`이라 팀이
없거나(`my_team()`), 시트 이름이 안 붙었거나(`my_member_id()`). 정책은 `null`을 「모두 허용」이
아니라 **「아무것도 아님」**으로 다뤄야 하고, SQL의 `=`는 `null`에 대해 참을 내지 않으므로
그 성질이 우리 편이다. 뒤집어 쓰는 순간(`is not distinct from` 따위) 전원에게 열린다.

### ADR-026: 세션이 있으면 `?as=`는 환경과 무관하게 진다 — `ADR-013`을 좁힌다
**결정**: `?as=` 해석에 갈래를 하나 **앞에** 얹는다. **세션이 있으면 세션의 role이 이기고
`?as=`는 무시된다 — 개발 환경에서도.** 세션이 없을 때의 규칙은 `ADR-013` 그대로다:
프로덕션+실저장소면 `member`, 데모·폴백이면 `?as=` 해석.

```
세션이 있으면              → 세션의 role이 이긴다
세션이 없고 프로덕션+실저장소 → member        (ADR-013 그대로)
세션이 없고 데모·폴백        → ?as= 해석      (ADR-013 그대로)
```

**이 항목은 `ADR-013`을 번복하지 않는다. 조건을 하나 더 얹어 좁힌다** — 데모 모드에서 `?as=`는
그대로 살아 있고, 그것이 `.env` 없이 클론한 심사자가 세 역할을 보는 유일한 길이다
(`PRD.md` 성공 기준 1번). 그래서 `proxy`도 자격증명이 없거나 `STORAGE_DRIVER=memory`면
로그인으로 보내지 않는다.
**이유**: `ADR-013`의 차단은 `NODE_ENV === 'production'`에 걸려 있다. 인증이 붙은 뒤에도 그대로
두면 **개발 서버에서 로그인한 `member`가 `?as=admin`으로 남의 팀을 읽는다.** 개발 서버라도
붙는 DB는 실제 원격이고 거기에는 실명·연락처가 있다(`S6`). 더 근본적으로, 세션은 서버가
서명한 사실이고 `?as=`는 **사용자가 타이핑한 문자열**이다. 둘이 부딪힐 때 문자열이 이기는
설계는 인증이 아니다.
**트레이드오프**: 실저장소에 붙어 개발하는 동안 **역할 전환이 로그아웃→재로그인이 된다.**
계정 셋을 오가야 하므로 `?as=`로 탭만 바꾸던 T6 시절보다 느리다. 대신 그 불편이 곧 완료 기준
2의 증명이다 — 화면을 바꾸는 유일한 길이 로그인이면, 화면이 바뀌었다는 것은 서버가 실제로
다르게 답했다는 뜻이다. 역할별 화면을 빠르게 대조하려면 `STORAGE_DRIVER=memory`로 돌린다.

### ADR-027: 인증의 문은 **폼과 라우트 핸들러**다 — 서버 액션을 쓰지 않고, `proxy`는 API와 화면을 다르게 막는다
**결정**: 로그인·로그아웃을 서버 액션이 아니라 **라우트 핸들러**(`POST /api/auth/login` ·
`POST /api/auth/logout`)로 만들고, 본문은 **폼 하나만** 받는다(JSON을 함께 받지 않는다).
응답은 항상 `303 See Other`다. 그리고 `proxy`가 미인증을 막는 방법을 **경로로 가른다**:
화면은 `307 → /login?next=…`, `/api/**`는 **`401 UNAUTHENTICATED` JSON**이다.
**이유**: 서버 액션이면 요청 본문이 Next 내부 포맷이라 **`curl`로 세션 쿠키를 만들 수 없다.**
그런데 `TICKETS.md` T8 완료 기준 2가 **「`curl`로 직접 검증한다」**를 명시한다 — 이 프로젝트에서
가장 중요한 한 줄(「`member`의 타인 건 `PATCH`가 거부된다」)의 **증명 방법이 로그인 구현에
달려 있다.** 검증할 수 없는 방어는 방어라고 말할 수 없으므로, 로그인은 검증 가능한 모양이어야
한다. 덤으로 JS 없이도 로그인이 된다(평범한 `<form method="post">`). `api`와 `page`를 가르는
것은 다른 이유다: `fetch`가 `302`를 따라가면 **로그인 HTML을 JSON으로 파싱하려 들고**, 그
실패는 「서버가 이상한 걸 줬다」로 보여 원인이 인증이라는 사실이 화면에서 사라진다.
공개 경로(`/login`·`/api/auth/*`·`/api/health`·정적 자산)는 **정확 일치 또는 그 아래**만
통과시킨다 — 접두사만 보면 `/api/authorize`가 `/api/auth`에, `/logins`가 `/login`에 걸려 뚫린다.
**트레이드오프**: 로그인 실패를 **화면 리다이렉트로만** 알린다(`/login?error=invalid`).
JSON API로 로그인하려는 클라이언트는 없고, 그래서 이 엔드포인트를 프로그램으로 부르는 쪽은
리다이렉트를 직접 읽어야 한다. 그리고 **실패 사유를 구분해 주지 않는다** — 「없는 계정」과
「비밀번호 틀림」이 둘 다 `invalid`다. 사용자는 무엇이 틀렸는지 모른 채 다시 쳐야 하지만,
구분해 답하면 이 엔드포인트가 **계정 존재 확인 도구**가 된다. 사람의 불편이 그쪽보다 싸다.

### ADR-028: 이력은 자기 정책을 갖지 않는다 — `task_events`는 부모 `tasks`의 범위를 다시 탄다
**결정**: `task_events`의 select 정책을 `exists (select 1 from public.tasks t where t.id =
task_events.task_id)` **한 줄로** 쓴다. 역할·팀·담당자 조건을 여기에 되풀이하지 않고,
`tasks_select_scope`가 통과시킨 부모를 가진 이력만 보인다. 조회는 다른 경로와 마찬가지로
**사용자 JWT**로 나가고(`ADR-024`), `service_role`로 대신 읽는 우회로를 만들지 않는다.
읽는 자리는 `TaskRepository.listEvents`이며 주간 보고의 「이번 주 변경 건수」가 그 소비자다.
**이유**: 이력의 범위는 **업무의 범위와 같은 사실이지 별개의 사실이 아니다.** 「내가 볼 수 없는
업무의 변경 이력」은 존재할 이유가 없고, 그것을 두 곳에 적으면 **한쪽만 고쳐지는 날이 온다** —
`tasks` 범위를 다음에 넓히거나 좁힐 때 이력이 따라오지 않고, 그 어긋남은 에러로 뜨지 않는다.
정책이 조용히 더 보여 주는 쪽으로 틀어지면 아무도 모른다. 같은 판단을 T8이 `task_stages`에서
이미 한 번 했고(`task_stages_select_via_task`), **같은 문제에 같은 모양을 쓰는 것이 이 스키마의
읽는 법이다.** 재귀도 아니다 — `tasks` 정책은 `task_events`를 보지 않는다.
**버린 갈래 둘.** (a) **라우트가 권한을 검증하고 `service_role`로 읽기** — `ADR-024`가 세운
경계에 구멍이 난다. 그 결정의 핵심은 「전부 `service_role`로 처리하면 RLS를 만들어도 의미가
없다」이고, 예외를 하나 열면 다음 사람이 그 예외를 근거로 둘째를 연다. 더 나쁜 것은 실패
방향이다 — **`service_role` 조회는 틀려도 에러 없이 더 많이 보인다.** (b) **`task_events`에
범위 조건을 직접 적기**(`my_role()`·`my_team()`·`my_member_id()` 되풀이) — 위의 「두 벌」이
그대로 일어나고, 덤으로 정책이 행마다 함수를 세 번 더 부른다.
**트레이드오프**: 이력 조회 하나에 **`tasks` 정책이 통째로 얹힌다.** `exists` 서브쿼리가 행마다
돌고 그 안에서 `my_role()`·`my_team()`·`my_member_id()`가 평가된다 — `stable`이라 문장 안에서는
캐시되지만 공짜는 아니다. 수백~수천 행 규모에서 감수한다(`ADR-006`이 SQL 집계를 밀어낸 것과
같은 근거다). 그리고 **`tasks`에서 지워진 업무의 이력은 함께 보이지 않게 된다** — 부모가 없으면
`exists`가 거짓이다. 감사 목적으로 그 이력을 봐야 할 날이 오면 **이 ADR을 먼저 뒤집고** 서버
전용 경로를 연다. 지금은 화면에 그것을 읽는 자리가 없다.

### ADR-029: 설정하지 않은 것은 연결 실패가 아니다 — 키가 하나도 없으면 데모다 (`ADR-005`를 좁힌다)
**결정**: `createStorage`의 데모 갈래를 한 줄 넓힌다. `STORAGE_DRIVER=memory`에 더해
**`STORAGE_DRIVER`를 정하지 않았고 Supabase 키(`NEXT_PUBLIC_SUPABASE_URL`·
`NEXT_PUBLIC_SUPABASE_ANON_KEY`·`SUPABASE_SERVICE_ROLE_KEY`)가 하나도 없으면** `mode: 'demo'`이고
쓰기가 산다. 갈리는 자리 둘은 **그대로 사고(`fallback`·읽기 전용)로 남긴다** —
`STORAGE_DRIVER=supabase`라고 **적어 두고** 키가 없는 경우, 그리고 키가 **일부만** 있는 경우다.

```
STORAGE_DRIVER=memory                    → demo      (그대로)
STORAGE_DRIVER 미설정 + 키가 하나도 없음   → demo      ← 이 항목이 넓힌 자리
STORAGE_DRIVER 미설정 + 키가 일부만 있음   → fallback  (설정하다 만 것이다)
STORAGE_DRIVER=supabase + 키 없음·불통     → fallback  (ADR-005 그대로)
```

**이 항목은 `ADR-005`를 번복하지 않는다. 폴백이 걸리는 조건을 좁힐 뿐이고, 걸렸을 때의 규칙
(모든 쓰기 `503` · 「읽기 전용 — 저장소 연결 실패」 배너)은 한 줄도 바뀌지 않는다.**
**이유**: `.env` 없이 클론한 심사자에게 지금까지 보인 것은 **사고 배너**였다. 붙어 볼 저장소
자체가 없는데 앱이 「연결에 실패했다」고 말하고, `[샘플 데이터 불러오기]`·업로드 확정·상태 수정이
전부 `503`으로 거부됐다 — `PRD.md` 성공 기준 1번과 `TICKETS.md` T9 완료 기준 2가 **문서로만
성립하고 실행으로는 성립하지 않았다**(T9 step 7 실측: `mode=fallback` · seed `503` · 배너
「읽기 전용 — 저장소 연결 실패」). `ADR-005`가 막으려던 것은 **조용한 데이터 유실**인데, 설정이
아예 없는 환경에는 유실될 실데이터가 없다. 거기서 폴백을 거는 것은 방어가 아니라 **없는 사고를
알리는 일**이다. `route-guard.ts`는 이미 같은 판단을 하고 있었다 — 자격증명이 없으면
`demo-open`이다(`ADR-026` 결정 E). **문은 열려 있는데 저장소만 사고라고 말하는 상태**가
어긋남이었고, 이 항목이 그 어긋남을 좁힌다.
**두 파일의 조건은 여전히 완전히 같지 않고, 같을 필요도 없다.** `route-guard`는 자격증명이
없으면 `STORAGE_DRIVER`와 무관하게 문을 연다(붙을 Auth 서버가 없는데 로그인을 요구하면 아무도
들어오지 못한다). 지켜야 하는 것은 **한 방향**이고 `store-factory.test.ts`가 그것을 잰다 —
**저장소가 `demo`로 본 환경은 proxy도 반드시 `demo-open`이다.** 뒤집힌 경우(문은 열리고 저장소는
읽기 전용)는 어긋남이 아니라 `ADR-005` 그대로다.
**트레이드오프**: 환경변수를 통째로 빠뜨린 배포가 **사고 배너 대신 「샘플 데이터 모드」로 뜬다.**
그 화면에서는 쓰기가 받아들여지고 재시작 때 사라진다 — `ADR-005`가 이름 붙인 바로 그 유실이다.
다만 그 상태는 **`proxy`가 이미 로그인을 요구하지 않는 상태**이기도 하다: 자격증명이 없는 배포는
데모라는 판정이 이 코드베이스에 먼저 있었고, 저장소만 다르게 답하고 있었을 뿐이다. 실수를
알아채는 근거는 배너가 아니라 **로그인 화면이 사라진 것**이 되고, 그 편이 더 눈에 띈다.
키를 **일부만** 빠뜨린 쪽은 여전히 사고로 잡히므로, 가장 흔한 오타(한 줄 누락)는 그대로 걸린다.


### ADR-030: 승인 상태 게이트는 **`security definer` 함수 셋 전부**에 건다 — 하나만 고치면 새는 자리가 있다
**결정**: `profiles`에 `status`(`pending`·`active`·`rejected`, 기본값 `active`)를 더하고,
**`my_role()`·`my_team()`·`my_member_id()` 셋 모두**가 `status = 'active'`인 행만 보게
한다(`0005_signup_approval.sql` 2절). **RLS 정책은 한 줄도 고치지 않는다** — `0003`의 11개와
`0004`의 1개가 그대로 남고, 새 정책도 0개다. 셋이 전부 `null`을 돌려주면 그 정책들이 저절로
막는다.
**이유**: 이슈 #29의 착수 초안은 「`my_role()`이 `status='active'`일 때만 역할을 돌려준다」
**하나**였다. 그대로 두면 **새는 자리가 있다.** `0003`의
`goal_metrics_select_scope`·`team_period_goals_select_scope`는 두 번째 갈래가

```sql
or (public.my_team() is not null and team_id = public.my_team())
```

라서 **`my_role()`을 보지 않는다.** 대기 상태인 사람의 `team_id`가 `marketing`이면 승인 전에
마케팅·관리팀 목표 지표가 통째로 보인다. 「함수 하나만 고치면 정책 전부가 막힌다」는 문장은
**정책이 전부 그 함수를 본다는 전제** 위에서만 참이고, 그 전제가 실제로는 깨져 있었다.
정책을 새로 짜지 않은 것은 그 판단이 옳았기 때문이다 — 새 상태를 더할 때 막을 자리를
빠뜨리지 않으려면 게이트가 **정책 수(12)가 아니라 함수 수(3)만큼** 있어야 한다. 다만
「몇 곳인가」를 셀 때 **정책이 무엇을 부르는지 실제로 읽어야 한다.**
기본값이 `active`인 것도 결정이다. 이 컬럼은 **기존 행 전부를 채우며** 추가되므로, `pending`을
기본값으로 두면 마이그레이션을 적용하는 순간 운영 중인 계정 전원이 잠긴다.
**트레이드오프**: 상태 축이 **함수 안에 숨는다.** 정책 SQL만 읽으면 「승인 대기」라는 개념이
어디에도 보이지 않고, `my_role()`의 본문을 열어야 그 조건이 나온다. 대신 그 대가로 정책 12개가
새 축을 하나도 모른 채 정확히 막는다. 다음에 상태를 하나 더 늘리는 사람은 **정책이 아니라
함수 셋을 고치고**, 그 셋 중 하나라도 빠뜨리면 위와 같은 자리가 다시 열린다는 것을 안다 —
확인 방법은 정책 본문을 훑어 `my_role()`을 **부르지 않는** 갈래를 찾는 것이다.

### ADR-031: 접근 제어를 RLS 정책이 아니라 `security definer` 함수에 모은다 — `profiles`·`members`에 UPDATE GRANT를 주지 않는다
**결정**: 승인·거절·재요청·역할 변경과 요청 목록·명부 조회를 **함수 여섯**으로 만든다
(`pending_requests` · `member_directory` · `approve_join` · `reject_join` · `request_join` ·
`set_role`, 그리고 둘이 공유하는 내부 헬퍼 `can_review_join`). `profiles`·`members`에
`insert`·`update`·`delete` GRANT를 **한 칸도 주지 않고**, 이 변경이 더한 RLS 정책은 **0개**다.
실행 권한은 `revoke … from public, anon, authenticated` 뒤에 여섯 개만 `authenticated`에
되돌려준다 — `can_review_join`과 트리거용 `handle_new_user`는 그 목록에 없다.
**이유**: 이슈 #29의 착수 초안은 「승인·승격에 맞는 RLS 정책과 컬럼 GRANT를 새로 단다」였다.
그 길을 실제로 그려 보면 `profiles`의 `update`에 필요한 `with check`가 **경우의 곱**이 된다 —
누가(admin·lead) · 대상이 어느 팀인가 · 어느 컬럼을 바꾸는가(`status`·`role`·`team_id`) ·
어느 값으로 가는가(`pending→active`는 되고 `rejected→active`는 안 된다). **하나만 빠뜨리면
그것이 권한 상승이고, 빠뜨렸다는 사실은 에러로 뜨지 않는다.** 게다가 승인은 두 테이블을
동시에 건드린다(`profiles.status` + `members.auth_user_id`) — 정책으로 나누면 한쪽만 성공한
상태가 존재할 수 있고, 그 사람은 `active`인데 담당자에 안 붙은 채로 자기 업무 0건을 본다.
함수로 모으면 호출자 검사가 **한 곳**이고 트랜잭션도 하나다. 테스트가 겨눌 자리도 하나다.
읽기 둘(`pending_requests`·`member_directory`)이 정책이 아닌 이유는 다르다 — 리더가 요청자를
알아보려면 **이메일**이 필요한데 `auth.users.email`은 `authenticated`가 읽을 수 없다. 정책으로는
낼 수 없고 `definer` 함수만 낼 수 있다.
**`ADR-024`를 어기지 않는다.** 이 함수들은 전부 **사용자 JWT**로 불린다(`rpc()`). 검사가
`auth.uid()`에 기대므로 `service_role`로 부르면 오히려 판정이 깨진다 — 인증·팀·멤버 라우트에
`service_role`이 닿지 않는 것을 `security-rules.ts`의 규칙 1이 파일 내용으로 잰다.
**트레이드오프**: **정책보다 덜 선언적이다.** `pg_policies`를 훑어도 이 규칙들이 보이지 않고,
「누가 무엇을 할 수 있나」를 알려면 `plpgsql` 본문을 읽어야 한다. 자격 미달이 `0행`이 아니라
`raise exception`이라 앱이 그것을 번역해야 하고(전부 `403 FORBIDDEN`), 사유를 갈라 알리지
않기로 해서 **연결 사고도 권한 거부와 같은 모양으로 보인다.** 또 함수 시그니처가 곧 계약이라
인자 이름 하나만 달라도 앱의 `rpc()` 호출이 조용히 실패한다. 그 대가로 얻는 것은 **바꿀 수
있는 자리가 여섯 개로 셀 수 있다**는 것이다.

### ADR-032: 계정은 `signUp()`으로만 만들고, 새 계정의 `role`·`status`는 **트리거가 하드코딩**한다
**결정**: `POST /api/auth/signup`은 anon 키 + 사용자 세션 클라이언트의 `auth.signUp()`만
부른다. 관리자 쪽 API(`service_role`이 필요한 계정 생성)를 쓰지 않는다. 그리고 **앱은
`profiles` 행을 만들지 않는다** — `auth.users`에 행이 생기면 트리거 `handle_new_user()`가
`role='member'` · `status='pending'`을 **박아 넣는다.** 두 값은 `raw_user_meta_data`에서
읽지 않는다. metadata에서 받는 것은 `display_name`과 `team_id` 둘뿐이고, `team_id`는
`teams`에 실재하는 값일 때만 들어간다(없으면 `null`이고 트리거를 실패시키지 않는다).
**이유**: 두 가지가 같은 축이다 — **새 계정의 권한을 누가 정하는가.**
관리자 API는 `service_role`이 **익명 사용자가 부르는 경로**에 닿게 만들고, 그것 말고도 둘을
건너뛴다: **이메일 확인**(누구나 남의 이메일로 계정을 선점할 수 있다)과 **Supabase 내장
rate limit**(가입 폼이 스팸 계정 양산기가 된다). `signUp()`은 둘 다 준다.
`role`·`status`를 metadata에서 읽지 않는 이유는 더 짧다 — **`user_metadata`는 사용자가 고칠 수
있는 자리다.** 가입 요청 본문에 `role: "admin"`을 끼워 넣는 것만으로 권한 상승이 된다.
`viewer-session.ts`가 같은 이유로 JWT의 그 필드를 거부하고 있었고, DB 쪽에도 같은 규율이
필요했다. 앱이 `profiles`를 함께 쓰기 시작하면 그 두 값을 **앱이 정하게 되고**, 그 자리가
곧 다음 사람의 권한 상승 경로다. 그래서 라우트는 metadata에 그 키를 **싣지도 않는다** —
실어 보내면 다음 사람이 「트리거도 그것을 읽는다」고 착각한다.
**트레이드오프**: **가입 결과가 Supabase 설정에 따라 갈린다.** Confirm email이 켜져 있으면
`signUp()`이 세션을 돌려주지 않아 사용자는 `/pending`이 아니라 「메일함을 여세요」 화면으로
간다. 코드가 그 설정을 알지 못하게 **응답의 세션 유무로만** 갈랐고, 그래서 화면 갈래가 하나
늘었다. 그리고 최초 `admin`은 **SQL로만 심을 수 있다** — 화면에도 `set_role`에도 `admin`으로
가는 길이 없다(`ADR-031`). 계정 하나가 뚫렸을 때 admin이 번식하지 않는 대가로, 관리자를
세우는 절차가 `README`의 SQL 한 문단이 됐다.

### ADR-033: 유출 비밀번호 검사를 직접 구현한다 — k-익명성으로 접두사 5글자만, 그리고 **fail-open**
**결정**: 가입 시점에 비밀번호를 SHA-1로 해싱해 **앞 5글자만** `api.pwnedpasswords.com/range/`에
보내고, 나머지 35글자는 **나가지 않고** 응답 목록과 로컬에서 대조한다
(`src/lib/auth/pwned-password.ts`). `Add-Padding: true`를 붙이고 **건수가 0인 줄은 패딩이라
세지 않는다.** 조회 실패(타임아웃 2초·네트워크 오류·4xx/5xx·깨진 본문)는 전부 **통과**로
접는다. 최소 길이는 `MIN_PASSWORD_LENGTH = 10`이고 화면과 서버가 그 한 상수를 본다.
**이유**: Supabase의 **Leaked password protection은 Pro 플랜 전용**이라 이 프로젝트에서 켤 수
없다 — 대시보드에서 시도하면 `available on Pro Plans and up`으로 거절당한다(T8 감사가 이미
기록한 항목이다). 같은 방어를 직접 지는 것이 유일한 길이었다.
**전체 해시를 보내면 이 방어가 곧 유출 경로가 된다.** 접두사 하나에 수백 건이 걸리므로 상대는
「이 사람이 그중 무엇을 쓰는지」를 알 수 없고, 접두사를 한 글자만 늘려도 그 k가 줄어든다 —
5는 API 형식이자 **방어의 세기**이며, `security-rules.ts`의 규칙 6이 그 숫자가 늘어나는 것을
파일 내용으로 막는다. 패딩을 켜는 이유는 붙이지 않으면 응답 크기가 결과에 따라 달라져 **본문을
못 봐도 길이만으로** 유출 여부를 추측당하기 때문이고, 그 대가로 가짜 항목이 `:0`으로 섞여
오므로 건수를 반드시 봐야 한다(안 보면 패딩이 곧 오탐이다). SHA-1을 쓰는 것은 약해서가 아니라
**API가 그 형식이기 때문**이다 — 저장용 해시가 아니다(비밀번호 저장은 Supabase Auth가 한다).
**fail-open인 이유**: 외부 서비스가 죽었다고 회원가입 전체가 멈추면 **그 서비스의 장애가 곧
이 서비스의 장애가 된다.** 이 검사는 **덤이지 문이 아니다** — 문은 최소 길이와 승인 절차
(`status`)가 진다. 승인이 없는 시스템이었다면 이 판단은 달랐다.
**트레이드오프**: **가용성과 강도를 맞바꿨다.** 조회가 실패하는 동안에는 유출된 비밀번호가
그대로 통과하고, 앱은 그 사실을 사용자에게도 로그에도 남기지 않는다(`S6` — 이 파일에는 로그가
한 줄도 없다). 그리고 이 검사는 **가입 시점에만** 걸린다 — 이 프로젝트에 비밀번호 변경 흐름이
없어서 걸 자리가 없다. 그 흐름을 만드는 사람은 같은 함수를 그 자리에도 불러야 하고, 부르지
않아도 아무 경고가 나지 않는다. 마지막으로 가입 요청 하나가 **바깥 서비스를 한 번 탄다** —
2초 상한을 뒀지만 가입 폼의 응답 시간이 남의 서비스에 달려 있는 것은 사실이다.

### ADR-034: 리더 이상의 도구를 부원에게서 감춘다 — 「보면 안 되는가」가 아니라 「그 자리에 있는가」
**결정**: `/report`(주간 보고)와 `/extract`(독스 → 배정표)를 `admin`·`lead`에게만 연다
(`src/lib/domain/staff-tools.ts`). 화면은 `notFound()`, 라우트 셋
(`GET /api/report/weekly`·`POST /api/uploads/doc`·`POST /api/export/assignment`)은 `403`이며,
사이드바는 같은 함수로 항목을 감춘다. **세션이 없으면 좁히지 않는다** — 로그인 전 역할은
`resolveViewerRole`이 `member`로 두므로, 그 값으로 좁히면 `.env` 없이 클론한 심사자에게 두
화면이 통째로 사라진다 (`team-visibility.ts`와 같은 규칙).
**이유**: T9 결정 N이 「역할로 막지 않는다」고 정했고 그 근거는 **범위**였다 — 「범위 밖 행은
애초에 보고서에 들어가지 않는다」. 그 근거는 지금도 참이고 그래서 팀장은 그대로 연다.
바뀐 것은 근거가 아니라 **묻는 질문**이다. 주간 보고는 회의에 들고 가는 문서이고 배정표는
남에게 일을 나눠 주려고 뽑는 표다 — 부원에게는 **쓸 자리가 없다.** 「자기 업무만 담긴 보고서를
볼 수 있다」는 사실이지만, 아무도 쓰지 않는 메뉴 둘이 사이드바에 서 있는 것은 매번 「내 것이
아닌 곳」을 확인하게 만든다 (`team-visibility.ts`가 팀 탭에서 같은 판단을 한다).
403이 아니라 404인 것은 `/members`·`/team/requests`와 같다 — 403 화면은 「리더 전용 기능이
존재한다」를 알려 준다.
**트레이드오프**: **화면에서 감추는 것이 방어처럼 보이기 시작한다.** 그래서 라우트 셋에 같은
함수를 걸었지만, 두 라우트(`uploads/doc`·`export/assignment`)는 저장소를 부르지 않기로 한
자리라(`ADR-022`) `resolveViewerRole` 대신 **세션만** 본다 — `?as=`를 여기서는 해석하지
않는다. 세션이 있으면 어차피 그것이 이기므로(`ADR-026`) 실질은 같지만, 역할을 정하는 경로가
**두 모양**이 됐다. 그리고 부원이 자기 주간 정리를 뽑을 길이 사라졌다: 그 요구가 다시 오면
`canReadWeeklyReport` 한 함수만 바꾸면 되도록 두 함수를 갈라 뒀다.

### ADR-035: 담당자 재지정을 연다 — 컬럼 GRANT 한 줄과 기존 `with check`로 족하다
**결정**: `PATCH /api/tasks/[id]`의 허용 필드에 `ownerMemberId`를 더하고(셋이 됐다),
`0008`이 `grant update (owner_member_id, owner_name_raw) on tasks to authenticated`를 준다.
**RLS 정책은 한 글자도 손대지 않는다.** 앱에서는 `canAssignOwner`(admin·lead)가 한 겹 더 서고,
이름(`ownerNameRaw`)은 **클라이언트에서 받지 않고** 라우트가 `assignableMembers`로 좁힌 명부에서
유도한다. 후보는 **그 업무의 팀 사람**뿐이다.
**이유**: 새 `security definer` 함수(RPC)를 만들 이유가 없었다. `tasks_update_scope`의
`with check`가 이미 정확히 필요한 것을 말하고 있다 — 부원의 조건이
`owner_member_id = my_member_id()`라서 **담당자를 남에게 넘기는 update가 DB에서 그 자리에
거부된다.** 팀장은 `team_id = my_team()`에 묶여 팀 밖으로 밀어낼 수 없다. 즉 여는 것은
컬럼뿐이고 「누가 어느 행을」은 이미 서 있다. 이름을 함께 여는 것은 표와 패널이 읽는 담당자가
그 칸이기 때문이다 — 하나만 바꾸면 「담당자는 A인데 이름은 B」인 행이 남고, 그것은 데이터가
틀린 것으로 보인다. 상태·진행률과 달리 역할 검사를 한 겹 더 두는 이유는 **묻는 것이 다르기**
때문이다: 진행률은 「자기 일의 진행을 적는다」이고 담당자는 「일을 누구에게 맡긴다」이다.
**트레이드오프**: **다음 업로드가 되돌린다.** 시트가 진실의 원천이라는 규칙 그대로이고
(`ADR-001`) `status`·`progress`가 이미 지고 있는 성질이지만, 담당자는 그 사실이 더 아프게
드러나는 칸이라 폼이 그것을 한 줄로 적는다. 그리고 컬럼 GRANT이므로 **부원이 자기 업무의
`owner_name_raw`만 바꾸는 요청은 DB가 막지 않는다**(정책은 통과한다 — 담당자 id는 그대로여야
하므로 남에게 넘기지는 못한다). 앱이 그 모양을 애초에 받지 않지만(zod가 그 키를 거부한다),
층이 하나인 자리가 생긴 것은 사실이다. `security definer` 함수로 옮기면 그 구멍이 닫히는
대신 규칙이 정책과 함수 두 곳으로 갈린다 — 지금은 갈리지 않는 쪽을 골랐다.

### ADR-036: 주간 보고를 문서로 그린다. 다만 마크다운을 HTML로 바꾸지는 않는다
**결정**: `/report` 화면이 `toReportBlocks`(`src/lib/view/report-blocks.ts`)가 낸 **블록**을
React 엘리먼트로 그린다 — 표는 `<table>`, 목록은 `<ul>`. 원문 마크다운은 접힌 `<details>`에
그대로 남고 복사·`.md` 내려받기가 내는 것도 그 문자열이다. PDF는 `window.print()`와
`globals.css`의 `@media print`가 만든다.
**이유**: T9 결정 O가 막은 것은 **HTML로 바꾸는 것**이었고 그 근거는 sanitize다 — 이 문자열은
시트 셀 값에서 오므로 HTML이 되는 순간 셀 값이 DOM이 된다(`S7`). 그 금지는 그대로 선다:
이 경로에 `dangerouslySetInnerHTML`도 마크다운 라이브러리도 sanitize 의존성도 없고, 파서가
내는 것은 **문자열이 담긴 자료구조**이며 React가 텍스트를 이스케이프한다. 결정 O가 함께 든
「용도가 붙여넣기라 렌더가 아무것도 더해 주지 않는다」는 근거는 **틀린 것으로 드러났다** —
회의에 들고 가려면 `| --- | ---: |`가 표로 보여야 하고, 그것 없이는 「PDF로 저장」이 고정폭
덤프가 된다. PDF 라이브러리를 넣지 않는 이유는 셋이다: 한글 폰트를 번들에 실어야 하고, 같은
문서를 만드는 경로가 둘이 되며(화면과 파일이 갈라진다), 브라우저가 이미 그 일을 한다.
파서가 **세지 않는다**는 것도 요점이다 — 숫자는 전부 `buildWeeklyReport`가 낸 것이라 화면과
API가 여전히 같은 보고서를 말한다 (`ADR-006`).
**트레이드오프**: **생산자와 소비자가 묶였다.** 이 파서는 범용이 아니라 우리 마크다운 하나만
알므로, `buildWeeklyReport`가 새 모양(중첩 목록·코드 블록)을 내면 그것은 문단으로 떨어진다.
버리지는 않지만 예쁘지도 않다 — 그래서 테스트가 손으로 지은 문자열이 아니라 **실제 보고서**를
넣어 보고, 생산자가 바뀌면 거기서 깨진다. 그리고 인쇄 규칙이 `aside`·`nav`·`header`를 통째로
접으므로, 앞으로 그 태그로 **문서의 일부**를 쓰면 종이에서 사라진다.

### ADR-037: 조직도의 이메일을 팀으로 가르지 않는다 — 연락처는 열고, 업무는 그대로 닫는다
**결정**: `0008`이 `member_directory()`를 고쳐 `admin`·`lead`에게 **모든 행의 이메일**을
내려보낸다. `0007`이 두던 「남의 팀은 `null`」 갈래를 지운다. `where` 절은 그대로라
`member`는 여전히 한 행도 받지 못하고, 남의 팀 카드의 **패널은 열리지 않는다**
(`members/page.tsx`의 `openable`).
**이유**: `0007`은 「남의 팀 사람의 이메일을 팀장이 알아야 할 이유가 없다」고 적었다. 그
전제가 틀렸다 — 조직 안에서 남의 팀 사람에게 메일을 보내는 것은 늘 하는 일이고, 이메일은
**연락처**이지 그 사람의 업무를 들여다보는 열쇠가 아니다. 이름만 남은 조직도는 「누가 있는지」만
말하고 「어떻게 닿는지」는 말하지 않는 반쪽이 된다.
**막아야 할 것은 그대로 막혀 있다.** 남의 팀 업무 진행 상황은 `tasks_select_scope`(`0003`)와
`viewer-scope.ts`가 지고 둘 다 손대지 않았다. 이 변경으로 늘어나는 것은 **연락처 한 칸**뿐이다.
**트레이드오프**: 팀장 계정 하나가 뚫리면 **전사 이메일 명부가 함께 샌다**(`S6`). 그 대가로
얻는 것이 「조직도가 연락처 구실을 한다」이고, 두 값을 저울에 올린 결과다 — 조직 규모가
커져 이 균형이 달라지면 되돌릴 자리는 `member_directory()`의 `case` 하나다. 그리고 `0007`과
`0008`이 **같은 함수를 반대 방향으로** 고치므로, 두 파일을 순서대로 적용해야 한다는 제약이
하나 늘었다(둘 다 `create or replace`라 재적용은 안전하다).

### ADR-038: 주간 보고에 제출·검토 흐름을 둔다 — **제출 시점의 본문을 얼린다**
**결정**: `report_submissions` 테이블(`(team_id, week_start)` 유니크)과 `security definer`
함수 셋(`submit_report`·`review_report`·`list_reports`)을 둔다 (`0010`). 팀장은 계산된 본문을
**고칠 수 있고** 특이사항을 함께 올린다. 어드민은 팀별 제출을 **한 장으로 병합해** 보고,
사유를 적어 반려한다. 재보고는 새 행이 아니라 같은 행의 갱신이며 `review_note`를 지운다.
**이유**: 보고서는 원래 `buildWeeklyReport`가 볼 때마다 새로 계산하는 물건이라 저장할 자리가
없었다. 팀장이 **고쳐서** 올릴 수 있게 되는 순간 「제출한 것」과 「지금 계산되는 것」이
갈리고, 그때 저장하지 않으면 **어드민이 보는 내용이 팀장이 올린 내용과 달라진다** — 그것은
보고 체계로서 성립하지 않는다. 그래서 문자열을 얼린다.
특이사항 칸을 따로 둔 것이 이 기능의 요점이다: 계산된 숫자는 어드민도 이미 같은 데이터에서
볼 수 있고, **보고가 보고인 이유는 숫자에 안 담기는 사정**이다. 그래서 병합 문서에서도 팀마다
특이사항이 본문보다 먼저 선다.
정책이 아니라 함수에 모은 것은 `ADR-031`과 같은 근거다 — 이 테이블에서 바뀌는 것은 값이
아니라 **상태 전이**이고(「팀장은 자기 팀만」·「어드민만 반려」·「재보고하면 사유가 지워진다」),
그것을 RLS + 컬럼 GRANT로 쪼개면 한 규칙이 세 곳에 흩어진다. 그래서 이 테이블에는 **정책이
하나도 없다**(RLS만 켜 둔다 — `uploads`와 같은 자리).
**트레이드오프**: **본문을 고칠 수 있다는 것은 숫자를 고칠 수 있다는 뜻이다.** 시트가 진실의
원천이라는 규칙(`ADR-001`)과 부딪히지는 않는다 — 고친 본문은 시트로 돌아가지 않고 그 주의
제출본으로만 남는다. 그래도 어드민이 받는 문서가 데이터와 어긋날 수 있으므로, 화면이
「계산된 내용에서 고친 상태입니다」를 적고 **되돌리기 버튼**을 둔다. 그리고 병합 문서는
**세지 않는다** — 팀별 본문을 잇기만 하므로, 어떤 팀이 숫자를 고쳐 올리면 전사 합계라는 것이
애초에 존재하지 않는다(그 합계를 만들면 팀이 올린 것과 또 갈린다). 마지막으로 제출은
**주 단위 한 건**이라 같은 주에 두 번째 보고를 남길 수 없다 — 이력이 필요해지면 유니크 제약을
풀고 「어느 것이 지금 보고인가」를 정하는 규칙을 새로 만들어야 한다.
