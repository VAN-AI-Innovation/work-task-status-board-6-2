# Architecture Decision Records

> 근거 문서는 `docs/PLAN.md`. 여기에는 **되돌리기 비싼 결정과 그 대가**만 남긴다.
> 결정이 바뀌면 PLAN.md를 고치고 해당 ADR에 후속 항목을 덧붙인다 (기존 항목은 지우지 않는다).

## 철학

**담당자가 준 지시 2건(엑셀→조회 / 독스→엑셀)이 과제 원문보다 우선한다.**
실제 시트·독스에서 확인된 사실만 근거로 삼고, 추측으로 기능을 늘리지 않는다.
잘라야 하면 부가 기능부터 자르고 두 파이프라인은 사수한다.

---

### ADR-001: 입력 UI를 만들지 않는다 — 시트 업로드 기반의 해석 계층
**결정**: 데이터 입력은 Google Sheets에 남기고, 이 웹은 내보낸 `.xlsx`를 업로드받아 해석·조회만 한다.
**이유**: 담당자가 "엑셀시트 **입력 시**"라고 규정했다. 입력 UI를 만들면 팀원의 업무 습관을 바꿔야 하고
채택률이 0이 된다. 부수적으로 CRUD 화면 전체가 범위에서 빠져 초안 마감이 현실적이 된다.
**트레이드오프**: 업로드하지 않으면 데이터가 낡는다. 실시간이 아니다. 이 약점은 감출 수 없으므로
모든 페이지에 "마지막 반영: N일 전"을 상시 표시하고 5일 초과 시 경고색으로 **드러낸다.**

### ADR-002: 공통 컬럼 + `extras jsonb` + `task_stages` 자식 테이블
**결정**: 팀별 16/70/20 컬럼을 하나의 `tasks` 테이블에 담고, 매핑되지 않은 컬럼은 전부 `extras`로
흘려보낸다. 단계별 컬럼 그룹은 `task_stages`로 언피벗한다.
**이유**: 팀별 전용 테이블 3개는 통합 대시보드가 3-way UNION이 되고, 완전 EAV는 집계 쿼리가 지옥이다.
**"매핑 안 된 컬럼은 자동으로 `extras`"라는 성질이 70컬럼 대응의 전부**이며, 시트에 새 컬럼이 생겨도
파서가 깨지지 않는다.
**트레이드오프**: `extras` 안의 값은 SQL로 질의·집계하기 어렵다. 화면에서도 라벨-값 나열
(사이드 패널)로만 보여준다 — 표에 70컬럼을 뿌리지 않기로 한 결정과 짝이다.

### ADR-003: 엑셀 라이브러리는 ExcelJS 단독, 버전 `4.4.0` 고정
**결정**: 읽기·쓰기 모두 `exceljs@4.4.0`(캐럿 없이 정확히 고정). SheetJS는 쓰지 않는다.
**이유**: (a) 독스→배정표에서 **데이터 검증 드롭다운이 붙은 xlsx**를 만들어야 하는데 —
배정표는 사람이 이어서 입력할 파일이므로 이게 실질 가치다 — SheetJS로는 어렵다.
(b) `cell.isMerged`/`cell.master`로 병합셀을 명시적으로 다룰 수 있다.
(c) npm 레지스트리의 `xlsx`는 여전히 `0.18.5`로 프로토타입 오염 CVE 버전 그대로다(최신은 자체 CDN 배포).
**트레이드오프**: ExcelJS는 **2024-12-20 이후 정체**돼 있고 의존성 트리가 오래됐다(`unzipper@0.10`,
`uuid@8`, `archiver@5` 등). 이 프로젝트가 다루는 xlsx는 **신뢰된 내부 파일**이라 감수하되,
**교체 비용을 2파일로 묶는다** — ExcelJS import는 `lib/sheet/workbook-reader.ts`(읽기)와
`lib/xlsx/assignment-writer.ts`(쓰기) **두 곳에서만**. 나머지 코드는 `{ sheetName, cells[][], merges[] }`
같은 자체 타입만 안다. `next.config.ts`에 `serverExternalPackages: ['exceljs']`.

### ADR-004: Supabase를 처음부터 붙이고, 메모리 드라이버는 시연 안전망으로 남긴다
**결정**: 메모리로 만들었다가 옮기는 2단계를 쓰지 않는다. T4에서 바로 Supabase 스키마를 잡는다.
`TaskRepository` 인터페이스와 메모리 드라이버는 유지하되 역할을 **시연 안전망**으로 바꾼다.
**이유**: 이관 티켓이 통째로 사라진다. 메모리 드라이버의 값어치는 셋 — Supabase 무료 티어의 7일
미접속 일시중지 대비, 심사자가 **`.env` 없이 클론 즉시 실행**(`STORAGE_DRIVER=memory`),
두 구현이 같은 계약 테스트를 통과하므로 도메인 로직 검증이 저장소와 분리된다.
**트레이드오프**: 저장소 구현을 둘 유지해야 한다. 배열 몇 개라 비용은 작지만 계약 테스트를
게을리하면 두 구현이 갈라진다 — 그래서 계약 테스트가 T4 완료 기준에 있다.

### ADR-005: 폴백은 읽기 전용이다
**결정**: Supabase 연결 실패 시 memory로 자동 폴백하되, 모든 쓰기 경로(업로드 확정, PATCH)는
`503 STORAGE_READONLY`를 반환하고 UI는 편집을 비활성화한다. 배너 문구는
**"읽기 전용 — 저장소 연결 실패"**로, 의도된 데모 모드(`STORAGE_DRIVER=memory`)와 구분한다.
**이유**: 폴백 중에 쓰기를 받으면 메모리에 저장되고 재시작 시 사라진다. 사용자는 저장됐다고 믿는다.
**조용한 데이터 유실**이 조회 불가보다 훨씬 나쁘다.
**트레이드오프**: 장애 중 편집이 아예 막힌다. 의도한 대로다.

### ADR-006: 집계는 SQL이 아니라 `lib/domain/`의 JS 순수 함수
**결정**: `TaskRepository`는 저장·조회만 한다. 완료율·지연율·KPI·알림·목표 달성률은 전부
순수 함수이며 SQL 집계를 쓰지 않는다. `now`는 항상 인자로 주입한다.
**이유**: SQL로 집계하면 메모리 구현과 결과가 갈라지고 "두 구현이 같은 계약 테스트를 통과한다"가
깨진다. 조직 전체 업무는 **수백~수천 행 규모**라 SQL 집계의 성능 이점이 없다.
**트레이드오프**: 행이 수만을 넘어가면 전량 로드가 부담이 된다. 그 시점은 이 과제 범위 밖이고,
넘어가면 재검토한다.

### ADR-007: 서버 컴포넌트는 `lib/`를 직접 호출한다 — API 라우트는 클라이언트 상호작용 전용
**결정**: 초기 렌더 데이터는 서버 컴포넌트가 `lib/store`·`lib/domain`을 직접 호출한다.
자기 API 라우트를 `fetch`하지 않는다. API는 파일 업로드·상태 수정·외부 소비만 담당한다.
**이유**: 서버 컴포넌트에서 자기 API를 fetch하면 불필요한 HTTP 왕복이 생긴다.
초기 CLAUDE.md의 "모든 API 로직은 `src/app/api/`에서만"을 문자 그대로 지키면 서버 컴포넌트가
`lib/store`를 못 읽어 규칙과 설계가 충돌했다. **규칙을 "비즈니스 로직은 `src/lib/`에만"으로 교체**했다.
**트레이드오프**: 같은 데이터에 진입 경로가 둘(서버 직접 호출 / API)이라 응답 스키마를 두 번
신경 써야 한다. 특히 `raw` 제외·민감 키 마스킹은 API 쪽에서 zod로 강제한다.

### ADR-008: 업로드는 미리보기 → 확정 2단계
**결정**: 파싱 결과를 `uploads.parse_result`에 넣고, 사용자가 확정하면 그것을 소스로 upsert한다.
확정 전에는 저장소에 아무것도 쓰지 않는다. 확정 후 `parse_result`는 비우고 `summary`만 남긴다.
upsert는 단일 트랜잭션으로 묶는다.
**이유**: 즉시 반영은 단순하지만 잘못된 파일 하나로 DB가 오염되고 되돌리기 어렵다.
DB에 파싱 결과를 두면 **서버 세션 상태 없이** 2단계가 성립한다.
**트레이드오프**: 왕복이 한 번 늘고 `parse_result`가 일시적으로 커진다(70컬럼 × N행).
Postgres TOAST로는 감당되지만 메모리 드라이버에선 RAM에 상주하므로 확정 즉시 비운다.
또 하나 — **"단일 트랜잭션"은 메모리 드라이버에서만 참이다.** `supabase-js`에 트랜잭션 API가
없어 Supabase 확정은 왕복 여럿으로 쪼개지고, 대신 **멱등 재시도**로 부분 반영을 수렴시킨다
(근거와 RPC 승격 경로는 `PLAN.md` `X4`의 후속 문단).

### ADR-009: 「지연」은 상태값이 아니라 파생 판정이고, 상태 문자열은 `semantic`으로 한 번 감싼다
**결정**: 시트의 10단계 진행 상태를 `enum_options.semantic`으로 매핑하고(planned·in_progress·review·
approval·rework·pending_release·done·hold·cancelled), 화면의 5색은
`toDisplayStatus(semantic, flags)`가 다시 매핑한다. `isOverdue`는 **다른 색을 덮어쓴다.**
**이유**: 판정 로직이 한글 상태 문자열을 직접 알면 시트에서 이름이 바뀔 때 코드가 깨진다.
지연을 상태값 중 하나로 취급하면 "진행 중이면서 마감이 지난" 업무를 놓치고 완료율이 틀린다.
**트레이드오프**: 매핑층이 둘(원문→semantic→5색)이라 처음 읽을 때 간접적이다.
대신 시트가 바뀌어도 고칠 곳이 `enum_options` 한 곳이다.

### ADR-010: 독스 입력은 `.docx` 단일. 마크다운 리더는 테스트 픽스처 전용
**결정**: 제품이 받는 입력은 `.docx` 하나(mammoth). `markdown-reader.ts`는 남기되 **제품 경로가 아니며**
같은 `OutlineNode[]`를 뱉는다.
**이유**: (a) `.docx`는 바이너리라 픽스처로 최악이다 — git diff가 안 되고 테스트가 뭘 검증하는지 읽을 수 없다.
`.md` 픽스처로 아웃라인 로직을 검증하고 `.docx`는 리더 계층만 스모크 테스트한다.
(b) mammoth의 Google Docs 스타일 인식이 흔들릴 때(H8) 이미 만들어둔 탈출구가 된다.
**트레이드오프**: 리더가 둘이라 "같은 출력을 낸다"는 테스트를 추가로 져야 한다. 추가 비용은 파일 하나다.
**선행 확인**: 실제 Google Docs를 `.docx`로 내보내 heading이 `h1~h3`으로 인식되는지 T1(사전 스모크 테스트)에서 확인한다.

### ADR-011: 데이터 행 판정은 신원 컬럼으로만 한다
**결정**: `isDataRow(row)` = 신원 컬럼(업무명·프로젝트명 / 담당자) 중 하나 이상에 실제 값이 있다.
**수식 결과 컬럼은 판정에 쓰지 않는다.** 추가로 1900-01-01 이전 날짜는 전부 null로 떨어뜨린다.
**이유**: 실제 `02_촬영·기획팀` 탭에 **유령 행 25개**가 있다 — 업무ID·프로젝트명은 비어 있는데
수식이 만든 `FALSE`·`0%`·`1900. 01. 01.`이 25개 컬럼에 들어차 있다. "셀에 값이 있으면 데이터 행"이라는
흔한 판정을 쓰면 유령 태스크 25건이 생기고, **1900년 기한의 "지연" 업무 25건**이 대시보드를 덮는다.
**트레이드오프**: 신원 컬럼이 비어 있는 진짜 업무는 누락된다. 그런 행은 애초에 사람도 식별할 수 없다.

### ADR-012: 생성한 xlsx의 수식 주입을 쓰기 쪽에서 막는다
**결정**: `assignment-writer.ts`에서 모든 문자열 셀을 명시적 텍스트 타입으로 쓰고,
`=`·`+`·`-`·`@`·탭·개행으로 시작하면 `'` 프리픽스를 붙인다. 읽기 쪽은 수식 셀의 `result`만 쓰고
`formula` 문자열은 저장도 렌더도 하지 않는다.
**이유**: `/extract`가 만든 배정표는 **조직 사람들에게 배포되는 파일**이다. 독스 본문의 값이 그대로
셀에 들어가는데 `=cmd|'/c calc'!A1` 같은 문자열은 받는 사람 PC에서 실행된다.
**트레이드오프**: `=`로 시작하는 정당한 텍스트도 앞에 `'`가 붙는다. 사람이 지우면 그만이다.

### ADR-013: `?as=` 역할 전환은 정식 데모 기능이되, 메모리 드라이버에서만 동작한다
**결정**: 로그인(T8) 이전에도 `?as=admin|lead|member`로 세 역할의 진입 화면을 시연한다.
단 `NODE_ENV === 'production' && driver !== 'memory'`면 **무시**한다.
**이유**: 초안 심사 시점에 권한 구분을 보여줄 수단이 필요하다(H7 헤지). 그러나 T8 이후에도 남아 있으면
**URL만 치면 관리자가 되는 완전한 인증 우회**다. Supabase에 붙는 순간 자동으로 죽게 만든다.
**트레이드오프**: 프로덕션+Supabase 환경에서는 이 데모 경로를 쓸 수 없다. 의도한 대로다.

### ADR-014: PC 우선 — 1280px 기준, 1024px까지 유지
**결정**: 기준 폭 1280px로 설계하고 1024px까지 레이아웃을 유지한다. 그 아래는 **깨지지 않고 읽히는
수준**까지만 대응하고 별도 모바일 레이아웃을 만들지 않는다.
**이유**: 촬영·기획팀 70컬럼을 다루려면 넓은 화면이 전제다. 이 결정이 표 설계 전체를 단순하게 만든다.
**트레이드오프**: 부원이 폰으로 "내 마감"을 보는 경험이 최적이 아니다. 초안 범위에서 감수한다.

### ADR-015: UI 톤을 라이트에서 다크로 뒤집되, 안티패턴 규율은 한 줄도 풀지 않는다 (`ADR-018`로 번복)
**결정**: `PLAN.md`가 「사용자 확정」으로 못박아 둔 라이트 톤을 T6 착수 시점에 **다크로 교체**한다.
바뀌는 것은 배경의 명도 하나뿐이고 **무채색 원칙·시맨틱 2색(빨강=지연, 앰버=주의)·AI 슬롭
안티패턴 표는 전부 유지**한다. 색은 `globals.css`의 `@theme` 토큰 한 곳에서만 오고, 화면 코드는
`bg-canvas`·`text-ink` 같은 토큰 클래스로만 색을 부른다 — Tailwind 팔레트 클래스(`neutral-`·`red-`)와
hex 리터럴을 쓰지 않는다.
**이유**: 확정값을 뒤집은 것은 그 값을 확정한 당사자다. 근거를 남기지 않으면 다음 사람이
「PLAN.md에 라이트라고 적혀 있다」를 보고 되돌린다. 색 토큰을 한 곳으로 모은 것은 미관이 아니라
**이미 한 번 뒤집힌 프로젝트**이기 때문이다 — 팔레트 클래스가 파일마다 흩어져 있으면 다음에
뒤집을 때 같은 일을 파일 수만큼 반복한다. 참고로 제시된 이미지는 보라 액센트의 파이낸스
대시보드였으나 **참고한 것은 구조(사이드바·상단 바·KPI 타일 행·차트 카드)이지 색이 아니다.**
액센트를 하나라도 들이면 시맨틱 2색이 셋이 되어 지연이 묻힌다.
**트레이드오프**: 다크에서 **명도 방향이 뒤집힌다.** 라이트에서 「진행 = 가장 진한 무채색」이었던
배지가 다크에서는 배경에 묻히므로 반전 배지(`bg-ink text-canvas`)가 됐고, 차트 계열색도 단순 반전이
아니라 패널 배경 위에서 구분되도록 다시 잡아야 했다. 라이트로 되돌리려면 그 두 표를 함께 다시 뒤집는다.

### ADR-016: 저장소 필터 `?status=`와 화면 필터 `?display=`를 합치지 않는다
**결정**: 5색 상태 칩은 `?display=planned|in_progress|review|done|overdue|muted`라는 **새 쿼리 키**를
쓴다. 기존 `?status=`는 그대로 두고 두 축을 섞지 않는다. `?overdue=1`(판정 필터)도 `?display=overdue`(칩)와
합치지 않는다.
**이유**: 둘은 **다른 축**이다. `?status=`는 시트 원문 문자열(`진행 중`)이고 저장소가 그대로 비교한다.
칩이 보내는 값은 `toDisplayStatus`가 semantic과 파생 플래그로 판정한 결과이며, 그 판정은
`ADR-006`에 따라 SQL이 아니라 `lib/domain`의 순수 함수가 한다. 칩이 `?status=in_progress`를 보내면
저장소에 그런 문자열이 없어 **조용히 0건**이 되고, 사용자는 필터가 아니라 데이터를 의심한다.
`?overdue=1`을 흡수하지 않은 것도 같은 이유다 — 앞은 `buildReadContext`가 거는 판정 필터이고
뒤는 칩이라, 합치면 기존 `UC-11` 공유 링크와 칩 UI가 서로를 덮어쓴다.
**트레이드오프**: 「상태로 거른다」는 한 가지 일에 URL 키가 셋(`status`·`display`·`overdue`)이라
처음 읽을 때 장황하다. 대신 어느 키가 어느 계층에서 걸리는지가 이름만 보고 갈린다.

### ADR-017: 팀 라우트 슬러그는 ASCII이고, 경로가 `?team=`을 이긴다
**결정**: `/teams/edit` · `/teams/shoot` · `/teams/marketing`. 소문자 한 모양만 받고 모르는 슬러그는
**404**다. 경로가 정한 팀이 `?team=`을 **덮어쓰며**, 나아가 그 화면이 만드는 링크에는 `?team=`을 싣지 않는다.
**이유**: 이 화면의 존재 이유가 **링크 복사·공유(`UC-11`)** 다. `/teams/편집팀`은 복사하면
`/teams/%ED%8E%B8%EC%A7%91%ED%8C%80`이 되어 사람이 읽을 수 없고 메신저·이슈 본문에서 줄이 깨진다.
팀 키(`edit`·`shoot`·`marketing`)는 이미 `TeamKey`로 코드 전체에 있어 새 어휘를 만드는 것도 아니다.
404로 두는 것은 전사 대시보드로 넘기면 **오타 링크가 조용히 다른 화면을 보여 주고 사람이 데이터를
의심하기** 때문이고, 대문자를 받지 않는 것은 같은 화면의 URL이 둘이 되면 공유된 두 링크가 같은 곳인지
눌러 봐야 알기 때문이다. `/teams/edit?team=shoot`이 촬영팀을 보여주는 링크는 거짓말이다.
**트레이드오프**: 화면에 뜨는 팀 이름(`편집팀`)과 URL의 단어(`edit`)가 다르다. 한글을 모르는
사람에게는 이점이지만, 팀 이름만 아는 사람이 URL을 손으로 칠 수는 없다. 팀 이름·슬러그 표는
`src/lib/view/team-slug.ts` 한 곳에 있어 사본이 갈라지지 않는다.


### ADR-018: 톤을 라이트로 되돌리고, 톤은 하나만 유지한다 (`ADR-015` 번복)
**결정**: `ADR-015`가 다크로 뒤집었던 톤을 **라이트로 되돌린다.** 다크 토큰·다크 전용 규칙은
남기지 않는다 — 토글도 두지 않고 **라이트 하나만** 존재한다. 바뀌는 것은 `globals.css`의
`@theme` 값과 차트 계열색(`chart-series.ts`) **두 곳뿐**이고, 무채색 원칙·시맨틱 2색·AI 슬롭
안티패턴 표는 `ADR-015`와 마찬가지로 **한 줄도 풀지 않는다.**
**이유**: 톤을 확정한 당사자가 T6 완료 후 화면을 보고 다시 라이트를 골랐다 (2026-08-22).
같은 사람이 같은 축을 두 번 뒤집었으므로 근거를 남기지 않으면 다음에 또 왕복한다 — **이 항목은
취향이고, 취향은 사용자의 것이다.** 토글을 두지 않는 이유는 `ADR-015`가 다크 단일을 고른 이유와
같다: 톤이 둘이면 배지 명도 방향·차트 계열색·스크린샷 기준이 전부 두 벌이 되고, 리뷰에서
「이 화면이 맞느냐」를 판정할 기준 자체가 흔들린다.
두 번 뒤집고 알게 된 것: **토큰을 한 곳에 모아 둔 결정이 값을 했다.** 화면 코드에 hex가 하나도
없어서 이번 전환에서 색 때문에 손댄 파일은 `globals.css`와 `chart-series.ts` 둘뿐이고,
`status-badge.ts`의 배지 표는 **한 글자도 고치지 않았다** — 배지가 색이 아니라 의미(`bg-ink`=
가장 진한 것, `bg-raise`=배경에 가까운 것)로 적혀 있어 토큰 값만 뒤집히면 명도 방향이 저절로
따라온다. 다음에 또 뒤집는 사람도 이 두 파일만 보면 된다.
**트레이드오프**: 흰 배경에서는 시맨틱 2색의 **텍스트 값과 배경값을 따로 잡아야 한다.**
다크에서 쓰던 `#f87171`(지연)·`#fbbf24`(주의)는 흰 바탕에서 대비가 모자라 읽히지 않으므로
텍스트는 어둡게(`#c2181b`·`#8a5a06`), 배경은 옅게(`#fdeced`·`#fdf3e0`) 나눠 잡았다. 같은
「빨강 하나」지만 값은 두 개다.

### ADR-019: 대시보드는 12열 flow에 zone 셋으로 깔고, 상태 분포는 도넛이 아니라 스택 바다
**결정**: 대시보드 섹션을 세로로 쌓지 않고 **12열 그리드에 흘려보낸다**(flow). 각 섹션은
`SECTION_SPAN`으로 폭을, `SECTION_ZONE`으로 zone(`summary`·`detail`·`table`)을 갖는다.
zone 순서는 **역할 배열에서 그 zone이 처음 등장하는 순서**로 정해지고, zone 안에서는
`SECTION_ORDER`의 순서를 그대로 따른다. `detail` zone(목표·브리핑·승인 대기)은 `<details>`로
접혀 한 줄이 된다. 그리고 **상태 분포는 도넛을 버리고 가로 스택 바 한 줄**로 그린다 —
Chart.js가 아니라 `div` 비율이라 클라이언트 컴포넌트도 아니다.
**이유**: 사용자가 T6 화면을 보고 든 불만이 셋이었고 셋 다 **높이** 문제다. (1) 도넛이 세로
300px를 쓰면서 KPI 타일과 같은 사실을 두 번 말한다 — 특히 건수가 적으면 단색 링이 되어 정보량이
0이다. (2) 알림 패널이 12칸을 다 쓰는 바람에 항목 이름과 건수 사이가 화면 폭만큼 벌어진다.
(3) 그래서 요약을 보려면 스크롤을 내려야 한다. **대시보드는 스크롤하지 않고 한 번에 읽는
화면이다** — 그것이 이 화면이 매일 열리는 이유다. 1280×900 기준으로 `summary`와 접힌 `detail`이
첫 화면에 들어가고 업무 표만 아래로 내려간다.
배치의 구체값은 `UI_GUIDE.md`「대시보드는 한 화면이다」에 그림으로 있다. 팀별 현황 표와
완료율 막대를 **한 칸에 세운 것**과 상태 분포를 **폭 전체**로 둔 것이 그중 둘인데, 앞은
알림(5칸)과 높이를 맞추려는 것이고 뒤는 8px 막대 한 줄이 좁은 칸에서 조각 구분을 잃기
때문이다.

zone을 도입하되 `SECTION_ORDER`를 그대로 둔 것이 요점이다. 역할별 진입 화면(완료 기준 7)이 묻는
것은 **「무엇이 맨 위냐」**이고, zone 순서를 역할 배열에서 유도하면 그 성질이 보존된다 —
`admin`은 `summary`(KPI)부터, `lead`도 `summary`(알림)부터, `member`는 `table`(업무 표)부터
시작한다. **어느 역할도 섹션을 잃지 않는다**는 불변식도 그대로다. 삭제는 권한이고 권한은 T8이다.
**짝과 쌓기**: 자동 배치(first-fit)는 빈칸을 줄이지만 **무엇과 무엇이 나란히 서야 하는지**를
모른다. 그래서 화면이 `groups`로 짝을 정하고(대시보드: 팀별 현황 + 팀별 완료율 / 알림 +
상태 분포), 한 칸 안에 섹션을 **세로로 쌓을 수도** 있다(팀 화면: 알림 오른쪽에 상태 분포 +
목표 대비 성과). 짝이 정해진 행에는 다른 섹션이 끼어들지 않는다 — 화면이 의도한 조합이기
때문이다. 역할별 순서는 그대로다: 짝의 자리는 **그 짝에 속한 섹션 중 역할 배열에서 가장
먼저 오는 것**이 정한다.

**상태 분포는 세 번 바뀌었다**: 도넛 → 스택 바 → **가로 막대**. 도넛은 세로 300px를 쓰면서
KPI와 같은 사실을 두 번 말했고, 스택 바는 반대로 세로를 거의 안 먹어서 **옆에 세울 카드가
없었다** — 알림처럼 길어지는 카드 옆에 두면 그쪽이 통째로 비었다. 가로 막대는 세로를 채우고
옆 카드를 따라 늘어나며, 값이 비율이 아니라 건수라 조각이 작아도 축을 보고 읽을 수 있다.

**행 높이**: 같은 행의 카드는 `items-stretch`로 테두리를 맞추되, 늘어난 높이는 **콘텐츠가**
먹는다 — 완료율 차트는 컨테이너를 따라 길어지고(`maintainAspectRatio: false`), 알림은 목록이
늘어나며 넘치면 목록만 스크롤한다. 그리고 **높이가 변하는 카드 옆에는 함께 늘어날 수 있는
카드만 세운다.** 알림은 데이터에 따라 길어지므로 짧고 고정된 카드를 옆에 두면 그쪽이 통째로
빈다 — 팀 화면이 그 경우라 거기서는 알림을 혼자 세웠다.

**펼침은 제자리에서 일어난다**: 접힌 카드는 펼쳐도 폭이 그대로이고 아래로만 자란다.
12칸으로 넓히던 초기안은 셋이 나란히 접힌 줄에서 하나만 폭 전체를 차지해 **화면이 통째로
재배치된 것처럼** 보였다. 그리고 **접히는 카드가 있는 행은 높이를 맞추지 않는다** — 맞추면
펼치는 순간 옆 칸까지 함께 늘어나 그쪽이 빈 채로 남는다.

**트레이드오프**: `detail` zone이 접혀 있어 **목표·브리핑·승인 대기는 한 번 눌러야 보인다.**
0건 묶음을 지우지 않는 것과 같은 이유로 접힌 제목과 요약 수치는 항상 남긴다 — 접힌 것과 없는
것이 화면에서 같아 보이면 안 된다. 그리고 도넛을 버려서 **조각별 각도 비교**를 잃었다. 스택 바는
비율을 길이로만 주므로 작은 조각이 도넛보다 덜 보이는데, 애초에 이 화면에서 작은 조각은
「지연 몇 건」이고 그 숫자는 KPI 타일이 가장 큰 글자로 말하고 있다.

### ADR-020: 브랜드 남색은 **구조와 조작**에 쓴다. **데이터에는 한 번도 쓰지 않는다**
**결정**: 대표색 **`#1e3a5f`(남색)** 를 토큰 `--color-brand`(+ `brand-strong` hover ·
`brand-soft` 옅은 바탕)로 들인다. 쓰는 자리는 둘이다.

- **구조** — 페이지 제목·섹션 제목·접힌 카드의 제목·표 헤더 바탕. 화면의 뼈대가 어디서
  갈라지는지를 말하는 글자들이다.
- **조작** — 로고, 사이드바의 현재 화면, 활성 필터 칩, 「적용」 버튼, 역할 전환, 기본 버튼,
  링크 hover, 표 행 hover, 입력 포커스 테두리.

**쓰지 않는 자리는 하나다: 데이터.** 차트 계열색·상태 배지·KPI 수치·표의 값·알림 건수는
전부 무채색과 시맨틱 2색(빨강=지연, 앰버=주의) 그대로다.

**이유**: 사용자에게 대표색이 있고 화면에 그 색이 없으면 이 도구가 어느 팀 것인지 알 수 없다.
다만 색을 **데이터에** 들이면 `UI_GUIDE.md`의 「눈에 띄는 것은 문제뿐」이 즉시 깨진다 — 정상
업무가 남색을 가지면 화면의 절반이 색을 갖고 지연 빨강이 묻힌다. 그래서 **역할로 갈랐다**:
남색은 「여기가 어디이고 무엇을 누를 수 있나」를, 빨강은 「무엇이 문제인가」를 말한다.
두 축이 겹치지 않아 한 화면에 있어도 서로를 가리지 않는다 — 업무 표를 보면 헤더는 남색이고
그 아래 지연 배지만 붉은데, 둘을 헷갈리는 사람은 없다.

처음에는 **조작 요소에만** 뒀다가, 사용자가 「남색이 왼쪽 메뉴에만 있는 느낌」이라고 해
**구조까지** 넓혔다. 넓힌 것은 제목과 표 헤더이고, **데이터 경계는 한 칸도 움직이지 않았다.**

「보라·인디고 브랜드 색상」 안티패턴과 충돌하지 않는다. 그 항목이 가리키는 것은 **AI 템플릿이
기본값처럼 쓰는 보라 액센트**이고, 여기 남색은 사용자가 가진 실제 대표색이다. 그래도 규율은
기계적으로 확인할 수 있게 남긴다 — **브랜드 토큰이 `chart-series.ts`나 `status-badge.ts`에
들어가면 이 ADR을 어긴 것이다.** 그 두 파일이 데이터의 색을 정한다.

**트레이드오프**: 강조가 **두 언어**가 됐다. 「진행」 배지(`bg-ink`=검정 채움)와 기본
버튼(`bg-brand`=남색 채움)이 형태가 같고 색만 다르다 — 배지는 표 안에만, 버튼은 표 밖에만
있어 나란히 서는 자리는 없지만, 새 컴포넌트를 만들 때 **「이건 데이터인가, 구조·조작인가」를
먼저 물어야 한다.** 그 질문에 답하지 않고 색을 고르면 규칙이 조용히 무너진다.
